= Actualización de versión

== Descripción

El _script_ `upgrade-provisioner.py` actualiza un _cluster_ creado con _Stratio Cloud Provisioner_ 0.7.x y Kubernetes 1.32 a la versión 0.9.9, con Kubernetes 1.35. Cada entorno tiene su propio procedimiento paso a paso:

* xref:operations-manual:upgrade/aws-eks.adoc[EKS] en AWS (gestionado).
* xref:operations-manual:upgrade/azure-vms.adoc[Azure VMs] (no gestionado).
* xref:operations-manual:upgrade/gcp-gke.adoc[GKE] en GCP (gestionado).

Esta página reúne lo que es común a los tres entornos:

* Los componentes actualizados y sus versiones.
* Los requisitos comunes.
* El uso de la opción `--private`.
* Las opciones y los _prompts_ del _script_.
* Las fases del proceso de actualización.
* La verificación final.

Para ejecutar la actualización, sigue el procedimiento de tu entorno.

IMPORTANT: Antes de empezar, lee por completo esta página y la del procedimiento de tu entorno. Algunos pasos no tienen vuelta atrás, y varias decisiones se toman antes de lanzar el _script_. Si tienes alguna duda, abre una incidencia con el equipo de Platform antes de continuar.

IMPORTANT: Solo se admiten _clusters_ con la versión 1.32 de Kubernetes. Si tu _cluster_ tiene una versión anterior, sigue primero el procedimiento de actualización correspondiente hasta alcanzar la versión admitida.

El _script_ y todas sus dependencias están en la imagen de Docker `cloud-provisioner-upgrade:0.9.9`, así que no necesitas instalarlas en tu máquina:

== Requisitos comunes

Estos requisitos son los mismos en los tres entornos. Cada procedimiento añade los suyos en su apartado de requisitos.

* Técnicos:
** Tener Docker instalado en el sistema.
** Tener un fichero _kubeconfig_ con acceso al _cluster_ (en `.kube/config`).
** Tener el fichero `secrets.yml` (cifrado con Ansible Vault) que se utilizó al crear el _cluster_, y su contraseña de Ansible Vault. La contraseña se pasa como argumento obligatorio (`-p`/`--vault-password`) al ejecutar el _script_ dentro del contenedor, y no tiene valor por defecto.
** Tener un directorio local llamado `backup` para las copias de seguridad (montado en el contenedor en `/upgrade/backup`), en el directorio de trabajo desde el que lanzas el contenedor. Usa siempre ese mismo nombre en todos los _clusters_ y clientes, para que la ubicación sea predecible al dar soporte. El _script_ gestiona su propia estructura de subcarpetas dentro de ese directorio: una por ejecución, con una marca de tiempo y dentro de un nivel `upgrade/` adicional, de modo que la ruta real de cada copia es `/upgrade/backup/upgrade/<marca_de_tiempo>/`. No hace falta que el directorio esté vacío ni volver a crearlo entre ejecuciones: basta con que exista como punto de montaje.
** Comprobar que el registro de contenedores y el repositorio de Helm de destino contienen las imágenes y los _charts_ del Universo 15.1 (consulta <<_qué_se_actualiza, qué se actualiza>>). Para saber de dónde descarga el _script_ cada cosa, consulta el <<_origen_de_charts_e_imágenes, origen de los _charts_ y las imágenes>>.
+
IMPORTANT: El repositorio que hay que comprobar *no es necesariamente el que el _cluster_ tiene configurado actualmente*. El _script_ pregunta de forma interactiva si quieres indicar uno nuevo (consulta los <<_prompts_interactivos, _prompts_ interactivos>>); si indicas uno distinto, ese pasa a ser el repositorio que se utiliza durante toda la actualización, incluido el _chart_ de _cluster-operator_. Comprueba el _chart_ del repositorio que realmente vayas a usar en esta ejecución.
+
Cuando llega el turno del _chart_ de _cluster-operator_, el _script_ lo descarga (`helm pull`) desde ese repositorio para aplicar sus CRD (si el _chart_ las incluye). Lo descarga antes de cambiar sus valores y su `HelmRelease`: si la descarga falla, _cluster-operator_ se queda como estaba. El _dry-run_ no realiza esta descarga, por lo que no la comprueba. Si el _chart_ no incluye CRD, el _script_ continúa sin problemas; lo que detiene la actualización en este paso es que la descarga falle (porque el _chart_ o la versión no están en el repositorio, o porque las credenciales del repositorio no son válidas). El _script_ descarga de la misma forma el _chart_ de flux2: de ese repositorio, en modo privado, y, si no, de su repositorio público.

* Funcionales:
+
Antes de ejecutar la actualización, comprueba que el _cluster_ cumple las siguientes condiciones. Si alguna no se cumple, *no lances la actualización* hasta resolverla:
+
** `KeosCluster` listo:
+
[source,bash]
----
kubectl get keosclusters.installer.stratio.com -A
----
+
*Salida esperada:*
+
*** `READY = true`
*** `PHASE = Provisioned`

** Nodos en buen estado:
+
[source,bash]
----
kubectl get nodes
----
+
*Salida esperada:* todos los nodos con `STATUS = Ready`.

** _Pods_ de Cluster API y de _cluster-operator_:
+
[source,bash]
----
kubectl get pods -n capi-system
kubectl get pods -n kube-system -l app.kubernetes.io/name=keoscluster-controller-manager
----
+
*Salida esperada:* todos los _pods_ en estado `Running`.

** _Logs_ de Cluster API y de _cluster-operator_:
+
[source,bash]
----
kubectl logs -n capi-system -l cluster.x-k8s.io/provider=cluster-api --tail=-1 --since=1h | grep '^E'
kubectl logs -n kube-system -l app.kubernetes.io/name=keoscluster-controller-manager --tail=-1 --since=1h | grep -P '\tERROR\t'
----
+
NOTE: Si aparece algún error, revísalo antes de continuar.

** _HelmReleases_:
+
[source,bash]
----
kubectl get helmrelease -A
----
+
*Salida esperada:* todos con `READY = True`.

** [[comprobación_automática]]Comprobación automática: al arrancar, antes de pedir confirmación, el _script_ hace su propia comprobación de salud, independiente de las anteriores:
+
--
* Comprueba `KeosCluster.status.ready`.
* Comprueba que ningún _pod_ del _cluster_ esté en `CrashLoopBackOff`, `ImagePullBackOff`, `ErrImagePull` o `CreateContainerConfigError`, ni en una fase distinta de `Running`, `Succeeded` o `Pending`.
* Comprueba que los _controllers_ de Cluster API y del proveedor tengan 2 réplicas disponibles.
* Comprueba que ninguna `Machine` esté fuera de las fases `Running`, `Provisioning`, `Pending` o `ScalingUp`.
* *No comprueba directamente el estado de los `HelmRelease`, sino solo el de los _pods_, como indicador indirecto.* Por eso, la comprobación manual anterior (`kubectl get helmrelease -A`) sigue siendo necesaria: no es redundante.
* Si encuentra algún problema, *aborta la actualización antes de empezar*, salvo que se indique `--skip-preflight-checks` (asumiendo el riesgo) o `--dry-run` (que solo informa de que abortaría).
--

== Notas importantes

=== Uso de la opción `--private`

La opción `--private` *fuerza* el uso de repositorios privados para:

* Las imágenes de contenedores (`private_registry`).
* Los _charts_ de Helm (`private_helm_repo`).

Ambos son campos de `ClusterConfig.spec`. El _script_ usa el modo privado si el campo ya es `true` o si pasas `--private`: la opción solo puede activarlo, nunca desactivarlo.

Esto implica que:

* Si `ClusterConfig.spec.private_registry=true`, el _script_ sigue usando el registro privado aunque *no pases* `--private`.
* Si `ClusterConfig.spec.private_helm_repo=true`, el _script_ sigue usando el repositorio privado de Helm aunque *no pases* `--private`.
* *Si pasas* `--private`, los dos valores se fuerzan a `true` durante la actualización, y el `ClusterConfig` se actualiza con esos valores.

==== Casos habituales

[%header,cols="2,2,3"]
|===
| Estado actual en `ClusterConfig`
| Ejecución
| Resultado

| `private_registry=true` +
`private_helm_repo=true`
| Sin `--private`
| Se siguen usando el registro privado y el repositorio privado de Helm.

| `private_registry=false` +
`private_helm_repo=false`
| Sin `--private`
| Se usan los repositorios públicos.

| `private_registry=false` +
`private_helm_repo=false`
| Con `--private`
| Se fuerza el uso de los registros y repositorios privados de Helm, y el `ClusterConfig` se actualiza a `true`.

| `private_registry=false` +
`private_helm_repo=false`, con el _cluster_ ya actualizado sin `--private`
| Relanzando con `--private`
| Pasan al registro privado las imágenes de los _charts_ y de los proveedores de Cluster API, aunque ya estén en su versión de destino, y el `ClusterConfig` se actualiza a `true`.
|===

[#_origen_de_charts_e_imágenes]

==== Origen de _charts_ e imágenes

* _Chart_ de _cluster-operator_: siempre de `KeosCluster.spec.helm_repository.url`.
* El resto de los _charts_: también de `KeosCluster.spec.helm_repository.url`, si `ClusterConfig.spec.private_helm_repo` es `true` o si pasas `--private`; si no, de su repositorio público.
* Imágenes: del registro con `keos_registry: true` en `KeosCluster.spec.docker_registries`, si `ClusterConfig.spec.private_registry` es `true` o si pasas `--private`; si no, de los registros públicos.

TIP: Usa `--private` solo si quieres usar repositorios privados y alguno de los dos campos de `ClusterConfig` está en `false`. Si los dos ya están en `true`, la opción no cambia nada.

TIP: Antes de la actualización real, ejecuta siempre el _script_ con `--dry-run` para detectar sin riesgo los problemas evidentes: una contraseña de Ansible Vault o unas credenciales de _cloud_ no válidas, la versión de `clusterctl` y los problemas de la comprobación de salud, que se listan sin abortar. Como no descarga ningún _chart_ ni comprueba el registro, no detecta un _chart_ o una imagen que falten. Además, un `--dry-run` sin errores *no garantiza* que la actualización real vaya a completarse sin problemas: el modo simula sin ejecutar ningún comando que modifique el _cluster_ (`apply`, `patch`, `delete`, `scale`, `create`, `annotate`, `label` y `clusterctl upgrade apply`), así que no se prueba ningún fallo que solo aparezca al aplicar esos cambios de verdad (un _webhook_ que rechaza un _patch_ concreto, una reconciliación de un `HelmRelease` que falla o un `clusterctl upgrade apply` real).

[#_prompts_interactivos]

=== _Prompts_ interactivos

El _script_ puede pedir hasta tres confirmaciones por teclado, en este orden. Con `--dry-run`, solo pide la segunda:

. *Continuar con la actualización*: al principio, tras las comprobaciones previas del _cluster_. Pulsa Intro para continuar; para abortar, escribe cualquier otro texto y pulsa Intro. Se omite con `-y`/`--yes`.
. *Repositorio de Helm*: justo después. Muestra el repositorio configurado en `KeosCluster.spec.helm_repository.url` y permite especificar uno nuevo. Pulsa Intro para mantener el actual. *No se puede omitir*: se pregunta siempre, incluso con `-y`.
. *Cambio de `k8s_version`* (solo si `KeosCluster.spec.k8s_version` va a cambiar): aparece al llegar a la actualización de Kubernetes, cuando los _charts_ y Cluster API ya están actualizados. Pide una confirmación explícita `[y/N]` antes de aplicar el _patch_. La `N` en mayúscula indica la respuesta por defecto: si pulsas Intro sin escribir nada, la respuesta es "no". Las respuestas no distinguen entre mayúsculas y minúsculas (por ejemplo, `y`, `yes`, `n` y `no`). Si respondes `n` o lo dejas en blanco, solo se cancela este paso (el resto de la actualización continúa). Se omite con `--start-from-k8s-version`. En Azure VMs, el mapa de imágenes se valida antes de esta pregunta: si no es correcto, el _script_ aborta, aunque respondas `n`.
+
Para detener la actualización en este punto, responde `n`. El _script_ restaura los _webhooks_ de `KeosCluster`, arranca su _controller_, reanuda el `HelmRelease`, espera a que el `KeosCluster` esté listo, devuelve _cluster-autoscaler_ a las réplicas que tenía al principio, hace el resto de la posactualización de tu entorno (en EKS, `mp_role_name` y `cluster-autoscaler-aws` con 0 réplicas; en Azure VMs, la imagen de cloud-provider-azure) y termina, sin cambiar la versión de Kubernetes. Puedes hacer el cambio de versión más tarde, en otra ejecución. *No uses `Ctrl+C` en esta pregunta*: el _script_ está en la sección crítica y su recuperación no se ejecuta, así que los _webhooks_ de `KeosCluster` se quedarían desactivados y el `HelmRelease`, suspendido.

WARNING: Si indicas un repositorio de Helm distinto, el _script_ lo guarda en `KeosCluster.spec.helm_repository.url` y en el `HelmRepository` `keos`, y lo usa para el _chart_ de _cluster-operator_ y, si es un repositorio privado, para el resto de los _charts_. Cambia este valor solo si el nuevo repositorio publica el mismo Universo de versiones (`kubernetes-universe`) que corresponde a esta versión de _Stratio Cloud Provisioner_: un repositorio de otro Universo puede resolver versiones de _charts_ incompatibles entre sí.

== Descripción general del proceso de actualización

Esta sección resume, en orden, las fases por las que pasa el _script_ al ejecutarse. No tienes que ejecutar ninguno de estos pasos: solo tienes que responder a los _prompts_ (consulta los <<_prompts_interactivos, _prompts_ interactivos>>).

. *Validación*
** Comprueba la versión de `clusterctl`, verifica que existen los secretos y el _kubeconfig_, y descifra los secretos.
** Configura las credenciales del proveedor de _cloud_ y comprueba el acceso al _cluster_. En EKS y en GKE, regenera el _kubeconfig_ si no te da acceso.
** En GKE, añade los _pods_ de `event-exporter-gke` a las excepciones de la _GlobalNetworkPolicy_ de IMDS, si no están, y reinicia el _pod_. Es el único cambio antes de la confirmación inicial.
** Hace la comprobación automática de salud (consulta la <<comprobación_automática, comprobación automática>>).
** Pide la confirmación inicial (consulta los <<_prompts_interactivos, _prompts_ interactivos>>).
** En EKS con _cluster-autoscaler_, crea la política de IAM de _cluster-autoscaler_ si no existe, asóciala a los roles `eks-nodegroup` y `nodes` y permite el acceso a IMDS a sus _pods_. Si falta alguno de los dos roles, muestra un `[WARN]` y continúa. Cualquier otro error en la política de IAM o en la _GlobalNetworkPolicy_ de IMDS detiene el _script_ en este paso.
** Pide el repositorio de Helm.

. *Preactualización*
** Si _cluster-autoscaler_ está desplegado, lo escala a 0, para evitar el escalado automático durante la actualización. En GKE, no está desplegado.
** En EKS, aplica los permisos de `aws-node` y de _cluster-autoscaler_ que pueden faltar en los _clusters_ creados con versiones anteriores.
+
NOTE: Al actualizar su _chart_, _cluster-autoscaler_ vuelve a tener 2 réplicas hasta que terminan los demás _charts_. Después, el _script_ lo vuelve a escalar a 0 y lo mantiene así hasta el final.

. *Copia de seguridad* (salvo con `--disable-backup`)
** Componentes CAPX (con `clusterctl move`).
** Configuraciones de los _webhooks_ de Capsule.
** Secretos de los _namespaces_ CAPX.

. *Preparación de Capsule*
** Excluye temporalmente los _namespaces_ de sistema de los _webhooks_ de admisión de Capsule, para que no bloqueen la actualización de los _charts_ del paso siguiente.

. *Actualización de los _charts_*
** Actualiza los _charts_ comunes (cert-manager, cluster-autoscaler, cluster-operator, flux2 y tigera-operator) y los del proveedor: aws-load-balancer-controller en EKS, si está instalado, y azuredisk-csi-driver, azurefile-csi-driver y cloud-provider-azure en Azure VMs (consulta <<_qué_se_actualiza, qué se actualiza>>). Si alguno de estos _charts_ no está en el _cluster_, el _script_ lo omite; por ejemplo, aws-load-balancer-controller, que es opcional en EKS, o _cluster-autoscaler_, si el _cluster_ se creó sin él.
** En EKS y en Azure, fija en _cluster-autoscaler_ la imagen de _upstream_ `v1.35.3`: `registry.k8s.io/autoscaling/cluster-autoscaler` sin registro privado, y `<registro>/autoscaling/cluster-autoscaler` con registro privado (`<registro>/k8s/autoscaling/cluster-autoscaler` con la _pull-through cache_ de ECR).
** Conserva los valores de _override_ (`ConfigMap` `02-<release>-helm-chart-override-values`) de cada _chart_.
** Al terminar los _charts_, vuelve a escalar _cluster-autoscaler_ a 0, si está desplegado.
** Deshace la exclusión de los _webhooks_ de Capsule.

. *Preparación de _cluster-operator_*
** Si el `HelmRelease` de _cluster-operator_ quedó suspendido en una ejecución anterior, lo reanuda. Después, espera hasta 5 minutos a que esté listo.
** Suspende el `HelmRelease` de _cluster-operator_.
** Comprueba que el `KeosCluster` está listo (`ready`) y en la fase `Provisioned` antes de entrar en la sección crítica.
** Detiene el _deployment_ `keoscluster-controller-manager`.
** Hace una copia de seguridad de las configuraciones de los _webhooks_ de `KeosCluster`.
** Desactiva los _webhooks_ de validación y de mutación de `KeosCluster`.
** Actualiza `ClusterConfig` con las nuevas versiones de los componentes.

. *Actualización de CAPI*
+
[source,bash]
----
clusterctl upgrade apply \
  --core cluster-api:v1.10.10 \
  --infrastructure <proveedor>:<versión> \
  --wait-providers
----
+
`<proveedor>:<versión>` es `aws:v2.9.3` en EKS, `azure:v1.21.3` en Azure VMs y `gcp:1.6.1-0.4.3` en GKE.
+
Se omite si todos los proveedores ya están en su versión de destino y, en modo privado (consulta el <<_uso_de_la_opción_private, uso de la opción `--private`>>), sus imágenes provienen del registro privado. Antes, si cert-manager está gestionado con Helm, el _script_ le quita la etiqueta de `clusterctl`, para que `clusterctl` no lo sustituya. Después, devuelve los _controllers_ de CAPI y del proveedor a 2 réplicas, con `priorityClassName: system-node-critical`.
+
NOTE: En las VMs de Azure, el comando también incluye los parámetros `--bootstrap kubeadm:v1.10.10` y `--control-plane kubeadm:v1.10.10`. EKS y GKE gestionan su propio _control-plane_ y no necesitan actualizarlo, pero Azure VMs usa `KubeadmControlPlane`, el proveedor de _control-plane_ de kubeadm de CAPI, que hay que actualizar por separado.

. *Actualización de la versión de Kubernetes*: cada entorno la hace de una forma distinta. Consulta el apartado "Antes de empezar" del procedimiento de tu entorno.

. *Posactualización*
** Restaura los _webhooks_ de `KeosCluster`, vuelve a arrancar `keoscluster-controller-manager` y reanuda el `HelmRelease` de _cluster-operator_.
** Comprueba que el _control-plane_ está en la nueva versión de Kubernetes y que _cluster-operator_ está listo. En EKS, los nodos de trabajo no cambian: los grupos _MachineDeployment_ se mantienen en la versión 1.32.
** Si _cluster-autoscaler_ está desplegado, lo devuelve a las réplicas que tenía al principio, o a 2 si estaba en 0.
** En EKS, si `spec.control_plane.aws.mp_role_name` está vacío y existe el rol `eks-nodegroup.cluster-api-provider-aws.sigs.k8s.io`, espera a que el `KeosCluster` esté listo y asigna ese rol al campo. Si no puede, muestra un `[WARN]` con el comando para corregirlo manualmente y termina igualmente.
** En Azure VMs, fija en cloud-provider-azure (`cloud-controller-manager` y `cloud-node-manager`) la imagen de la versión de Kubernetes que tiene el _cluster_ al terminar (por ejemplo, `v1.35.9` en la 1.35), y espera a que se despliegue.
** En EKS con _cluster-autoscaler_, instala al final una segunda instancia, `cluster-autoscaler-aws`, con el proveedor `aws` y 0 réplicas: se queda instalada, pero no se ejecuta. La instancia existente sigue escalando los grupos _MachineDeployment_.

== Verificación final

* Comprueba las imágenes de los _pods_ del _cluster_:
+
[source,bash]
----
kubectl get pods -A -o json \
| jq -r '
  .items[]
  | (
      [.spec.containers[]?.image] +
      [.spec.initContainers[]?.image]
    )
  | .[]
' \
| sort -u
----
+
*Versiones esperadas:* las imágenes de los _controllers_ de CAPI y del proveedor (`capi-controller-manager`, `capa-controller-manager`, `capz-controller-manager` o `capg-controller-manager` y, en Azure VMs, los dos _controllers_ de kubeadm) incluyen las versiones de la tabla de <<_qué_se_actualiza, qué se actualiza>>. La versión de un _chart_ no es la de sus imágenes: los _charts_ se comprueban en el paso siguiente.

* Comprueba las versiones de los _charts_:
+
[source,bash]
----
kubectl get hr -A -o json \
| jq -r '
  .items[]
  | "\(.metadata.namespace)/\(.metadata.name) -> \(.spec.chart.spec.chart)@\(.spec.chart.spec.version)"
' \
| sort -u
----
+
*Versiones esperadas:* las de la tabla de <<_qué_se_actualiza, qué se actualiza>>. El _script_ no modifica los demás _charts_ del _cluster_.

* Comprueba el estado final:
+
[source,bash]
----
kubectl get keoscluster -A -o custom-columns=NAME:.metadata.name,K8S_VERSION:.spec.k8s_version,READY:.status.ready
kubectl get nodes -o custom-columns=NAME:.metadata.name,VERSION:.status.nodeInfo.kubeletVersion
kubectl logs -n capi-system -l cluster.x-k8s.io/provider=cluster-api --tail=-1 --since=1h | grep '^E'
kubectl logs -n kube-system -l app.kubernetes.io/name=keoscluster-controller-manager --tail=-1 --since=1h | grep -P '\tERROR\t'
----
+
*Salida esperada:* `K8S_VERSION` es la versión de destino, y `READY` es `true`. Revisa cualquier error en los _logs_ antes de dar por terminada la actualización. En los _logs_ de Cluster API, pueden aparecer los errores `Unauthorized` o `connection to the workload cluster is down` mientras el _control-plane_ cambia de versión; solo son un problema si siguen apareciendo cuando la actualización ha terminado. Lo que cambia en cada entorno se encuentra en el apartado "Comprobaciones posteriores" de su procedimiento.
