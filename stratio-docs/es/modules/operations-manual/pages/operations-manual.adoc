= Manual de operaciones

== Obtención del _kubeconfig_

Para comunicarse con el _API Server_ del _cluster_ creado es necesario el fichero _kubeconfig_, que se obtendrá de forma diferente según el proveedor _cloud_ utilizado y la gestión del _control-plane_ del _cluster_.

* Para EKS, se obtendrá de la forma indicada por AWS:
+
[source,bash]
----
aws eks update-kubeconfig --region eu-west-1 --name <cluster_name> --kubeconfig ./<cluster_name>.kubeconfig
----

* Para GKE, se obtendrá de la forma indicada por GCP:
+
[source,bash]
----
gcloud container clusters get-credentials <cluster_name> --region <region> --project <project>
----
+
Este comando generará el fichero _kubeconfig_ en la ubicación indicada por la variable de entorno `KUBECONFIG`. Por defecto, estará en `$HOME/.kube/config`.

* Para Azure no gestionado, al finalizar el aprovisionamiento el _kubeconfig_ se deja en el directorio de ejecución (_workspace_):
+
[source,bash]
----
ls ./.kube/config
./.kube/config
----
+
A su vez, podrá utilizarse el alias "kw" desde el contenedor local para interactuar con el _cluster worker_ (en EKS, el _token_ utilizado solo dura 10 minutos):
+
[source,bash]
----
root@example-azure-control-plane:/# kw get nodes
NAME                                STATUS   ROLES           AGE   VERSION
example-azure-control-plane-6kp94   Ready    control-plane   60m   v1.35.8
example-azure-control-plane-fgkcc   Ready    control-plane   63m   v1.35.8
...
----

== Autenticación en EKS

Si bien no forma parte de la operativa de _Stratio KEOS_, es importante destacar la forma de permitir la https://docs.aws.amazon.com/es_es/eks/latest/userguide/add-user-role.html[autenticación de otros usuarios en un _cluster_ de EKS] (el usuario creador del _cluster_ está autenticado por defecto).

Para otorgar permisos de _kubernetes-admin_ en el _cluster_, se agregará el ARN del usuario al _ConfigMap_ indicado a continuación.

[source,bash]
----
$ kubectl -n kube-system edit cm aws-auth
..
data:
  mapUsers: |
    - groups:
      - system:masters
      userarn: <user_arn>
      username: kubernetes-admin
----

== Activar autorización por _assume role_ en AWS para un _cluster_ EKS

Este procedimiento describe cómo habilitar el método de autorización basado en _assume role_ en un _cluster_ de EKS ya creado.

=== Prerrequisitos

Antes de comenzar, asegúrate de cumplir lo siguiente:

* Tener creado un rol de IAM con los permisos necesarios (por ejemplo: _stratio-assume-role_).
** Tipo de rol: _AWS Account_.
** Permisos: los mismos que los descritos en los prerrequisitos de EKS.
* Configurar la _Trust Relationship_ del rol para permitir que el usuario que desplegó el _cluster_ pueda asumirlo.
+
Ejemplo de _Trust Relationship_:
+
[source,json]
----
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::123456789012:user/stratio-user"
      },
      "Action": "sts:AssumeRole"
    }
  ]
}
----

* Asignar al usuario una política que incluya la acción `sts:AssumeRole` sobre el rol correspondiente.
+
Ejemplo de política:
+
[source,json]
----
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "sts:AssumeRole",
      "Resource": "arn:aws:iam::123456789012:role/stratio-assume-role"
    }
  ]
}
----

NOTE: La versión mínima de _cluster-operator_ compatible con este método es la 0.5.2.

=== Configurar _assume role_ en el _cluster_ EKS

NOTE: Sustituye la cuenta, el nombre del _cluster_ (`eks-cl01`) y el _namespace_ (`cluster-eks-cl01`) por los de tu entorno.

. Crea el objeto `AWSClusterRoleIdentity`.
+
[source,yaml]
----
apiVersion: infrastructure.cluster.x-k8s.io/v1beta2
kind: AWSClusterRoleIdentity
metadata:
  name: eks-cl01-role-identity
spec:
  roleARN: arn:aws:iam::123456789012:role/stratio-assume-role
  sessionName: eks-cl01-role-identity-session
  durationSeconds: 3600
  sourceIdentityRef:
    kind: AWSClusterControllerIdentity
    name: default
  allowedNamespaces:
    list:
    - cluster-eks-cl01
----

. Asocia la identidad `AWSClusterRoleIdentity` al `AWSManagedControlPlane`.
+
[source,bash]
----
kubectl patch awsmanagedcontrolplane eks-cl01-control-plane \
  -n cluster-eks-cl01 \
  --type='merge' \
  -p '{"spec":{"identityRef":{"kind":"AWSClusterRoleIdentity","name":"eks-cl01-role-identity"}}}'
----

. Reinicia el _deployment_ de `capa-controller-manager` para que los cambios surtan efecto.
+
[source,bash]
----
kubectl rollout restart deployment capa-controller-manager -n capa-system
----

. Edita el _ConfigMap_ `aws-auth` para añadir el `iam_role`.
+
[source,yaml]
----
  mapRoles: |
    - groups:
      - system:bootstrappers
      - system:nodes
      rolearn: arn:aws:iam::123456789012:role/nodes.cluster-api-provider-aws.sigs.k8s.io
      username: system:node:{{EC2PrivateDNSName}}
    - groups:
      - capa-manager
      rolearn: arn:aws:iam::123456789012:role/stratio-assume-role
      username: stratio-assume-role
----

. Crea el `ClusterRoleBinding` para el grupo `capa-manager`.
+
[source,bash]
----
kubectl apply -f - <<EOF
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: capa-manager-access
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: capa-manager-role
subjects:
- kind: Group
  name: capa-manager
  apiGroup: rbac.authorization.k8s.io
EOF
----

. Añade permisos al `ClusterRole` del grupo `capa-manager`.
+
[source,bash]
----
kubectl patch clusterrole capa-manager-role \
  --type='json' \
  -p='[
    {"op": "add", "path": "/rules/-", "value": {"apiGroups":["apps"],"resources":["daemonsets"],"verbs":["get","list","watch","update"]}},
    {"op": "add", "path": "/rules/-", "value": {"apiGroups":[""],"resources":["pods"],"verbs":["get","list","watch"]}},
    {"op": "add", "path": "/rules/-", "value": {"apiGroups":[""],"resources":["nodes"],"verbs":["get","list","watch","patch"]}},
    {"op": "add", "path": "/rules/-", "value": {"apiGroups":[""],"resources":["pods/eviction"],"verbs":["create"]}}
  ]'
----

. Actualiza el _cluster-operator_.
.. Actualiza el _HelmRelease_ asociado al _cluster-operator_ a la versión 0.5.2 o superior.
.. Actualiza el _ConfigMap_ correspondiente a esa versión.
... Modifica el _tag_ en `00-cluster-operator-helm-chart-default-values` con la versión deseada, p. ej. 0.5.2.
.. Parchea el secreto _keoscluster-settings_ para añadir el `role_arn`.
+
[source,bash]
----
kubectl -n kube-system patch secret keoscluster-settings \
  --type=json \
  -p='[{"op":"replace","path":"/data/credentials","value":"'$(kubectl -n kube-system get secret keoscluster-settings -o jsonpath="{.data.credentials}" | base64 -d | awk 'BEGIN{ORS="\n"} {print} END{print "role_arn = arn:aws:iam::123456789012:role/stratio-assume-role"}' | base64 -w0)'"}]'
----

. Verifica la configuración y los permisos.
+
[source,bash]
----
# Revisar los logs de capi/capa
kubectl logs -f -n capa-system deployment/capa-controller-manager (o el nombre del pod)
kubectl logs -f -n capi-system deployment/capi-controller-manager (o el nombre del pod)

# Revisar los logs del cluster-operator
kubectl logs -f -n kube-system deployment/keoscluster-controller-manager (o el nombre del pod)

# Comprobar estado y configuración
kubectl get awsclusterroleidentity
kubectl get awsmanagedcontrolplane -n cluster-eks-cl01
kubectl get configmap aws-auth -n kube-system -o yaml

# Verificar permisos del rol
kubectl auth can-i get nodes --as=stratio-assume-role --as-group=capa-manager
kubectl auth can-i list nodes --as=stratio-assume-role --as-group=capa-manager
kubectl auth can-i list pods --as=stratio-assume-role --as-group=capa-manager
kubectl auth can-i update daemonsets --as=stratio-assume-role --as-group=capa-manager
----

[NOTE]
====
Si se actualiza el usuario que realiza el _assume role_, habrá que actualizar los siguientes secretos con las nuevas credenciales y, si aplica, con el nuevo rol ARN:

* _capa-manager-bootstrap-credentials_ (para CAPA).
* _keoscluster-settings_ (para el _cluster-operator_).
====

=== Operaciones del _cluster_ con _assume role_

Una vez activado, también puedes gestionar el _cluster_ utilizando _assume role_ desde la línea de comandos siguiendo estos pasos:

. *Verifica AWS CLI*: comprueba con este comando que tienes instalada la última versión.
+
[source,bash]
----
aws --version
----

. *Exporta el perfil de AWS*.
+
[source,bash]
----
export AWS_PROFILE=<nombre-del-profile>
----

. *Asume el rol y guarda las credenciales*.
+
[source,bash]
----
aws sts assume-role \
  --role-arn arn:aws:iam::<accountID>:role/<role-name> \
  --role-session-name eks-session > creds.json
----

. *Exporta las credenciales temporales*.
+
[source,bash]
----
export AWS_ACCESS_KEY_ID=$(jq -r '.Credentials.AccessKeyId' creds.json)
export AWS_SECRET_ACCESS_KEY=$(jq -r '.Credentials.SecretAccessKey' creds.json)
export AWS_SESSION_TOKEN=$(jq -r '.Credentials.SessionToken' creds.json)
----

. *Actualiza el _kubeconfig_*.
+
[source,bash]
----
aws eks update-kubeconfig --region <region> --name <nombre-del-cluster>
----

== Operación de la infraestructura

image::controllers.png[]

_Stratio KEOS_ permite realizar varias operaciones avanzadas interactuando con el _Stratio Cluster Operator_ (_infrastructure as code_ o IaC), que en su ciclo de reconciliación interactúa a su vez con los distintos proveedores para realizar las operaciones solicitadas.

=== _Self-healing_

image::self-healing.png[]

La capacidad de _self-healing_ del _cluster_ se gestiona por el recurso _MachineHealthCheck_:

[source,bash]
----
$ kubectl -n cluster-example get mhc -o yaml
...
  spec:
    clusterName: example
    maxUnhealthy: 100%
    nodeStartupTimeout: 5m0s
    selector:
      matchLabels:
        keos.stratio.com/machine-role: example-worker-node
    unhealthyConditions:
    - status: Unknown
      timeout: 1m0s
      type: Ready
    - status: "False"
      timeout: 1m0s
      type: Ready
...
----

NOTE: En Azure no gestionado habrá un _MachineHealthCheck_ para el _control-plane_ y otro para los nodos _worker_, mientras que en los gestionados (EKS, GKE) solo habrá el segundo.

==== Prueba de tolerancia a fallos en un nodo

En caso de fallo de un nodo, un _controller_ lo detecta y lo reemplaza: lo elimina y crea otro del mismo grupo, lo que garantiza que mantenga las mismas características.

Para simular un fallo en una máquina virtual, se eliminará desde la consola web del proveedor de _cloud_.

La recuperación del nodo comprende las siguientes fases y tiempos estimados (pudiendo variar según el proveedor y el _flavour_):

[source,text]
----
. Terminate VM from console: 0s
. New VM is Provisioning: 50s
. Old Machine is Deleted & the new one is Provisioned: 1m5s
. New Machine is Running & new k8s node is NotReady: 1m 50s
. New k8s node is Ready: 2m
----

NOTE: En Azure no gestionado, si el nodo reemplazado es del _control-plane_, actualiza después su _GlobalNetworkPolicy_. Consulta la <<azure-sustitucion-control-plane,sustitución de nodos del _control-plane_ en Azure no gestionado>>.

[[azure-sustitucion-control-plane]]
=== Sustitución de nodos del _control-plane_ en Azure no gestionado

En Azure no gestionado, los nodos del _control-plane_ se sustituyen en estos casos:

* Cuando el _MachineHealthCheck_ del _control-plane_ reemplaza un nodo que ha fallado.
* Cuando cambias en el _KeosCluster_ el tamaño, la imagen o los discos del _control-plane_. Son los campos `size`, `node_image`, `root_volume`, `cri_volume`, `etcd_volume` y `extra_volumes`, y el cambio sustituye todos los nodos del _control-plane_, uno a uno.
* Cuando actualizas la versión de Kubernetes.

La instalación de _Stratio KEOS_ crea la _GlobalNetworkPolicy_ `allow-all-traffic-from-control-plane`. Esta política permite el tráfico que sale de los nodos del _control-plane_ a partir de dos IP por nodo: la IP interna y la IP de túnel de Calico.

La política no se actualiza sola. Un nodo nuevo recibe otra IP de túnel y su tráfico hacia los _pods_ de otros nodos deja de estar permitido. Por ejemplo, su _API Server_ no alcanza los _webhooks_ de admisión que se ejecutan en otros nodos.

Por eso, **cada vez que se sustituya un nodo del _control-plane_, regenera la política con las IP de los nodos actuales**.

NOTE: Si actualizas la versión de Kubernetes con `upgrade-provisioner.py`, el proceso abre la política antes de actualizar el _control-plane_ y la regenera al terminar. No tienes que hacerlo tú.

==== Cambio planificado del _control-plane_

Antes de cambiar el _control-plane_ en el _KeosCluster_, abre la política al rango de IP de Calico. Así, los nodos nuevos tienen acceso desde que se unen al _cluster_.

CAUTION: Mientras la política esté abierta, permite el tráfico desde cualquier _pod_ del _cluster_ hacia todos los _pods_. Regenérala en cuanto termine la sustitución.

. Guarda una copia de la política actual:
+
[source,bash]
----
kubectl get globalnetworkpolicies.crd.projectcalico.org allow-all-traffic-from-control-plane -o yaml > allow-all-traffic-from-control-plane-backup.yaml
----

. Consulta el rango de IP de Calico:
+
[source,bash]
----
kubectl get ippools.crd.projectcalico.org -o custom-columns=NAME:.metadata.name,CIDR:.spec.cidr
----

. Añade ese rango a la política. Sustituye `<cidr_calico>` por el valor de la columna `CIDR`:
+
[source,bash]
----
kubectl patch globalnetworkpolicies.crd.projectcalico.org allow-all-traffic-from-control-plane --type json -p '[{"op":"add","path":"/spec/ingress/0/source/nets/-","value":"<cidr_calico>"}]'
----

. Aplica el cambio en el _KeosCluster_ con `kubectl patch`.

. Espera a que el _KeosCluster_ vuelva a estar listo (`ready: true`) y a que todos los nodos del _control-plane_ estén _Ready_:
+
[source,bash]
----
kubectl -n cluster-<cluster_name> get keoscluster <cluster_name> --subresource=status
kubectl get nodes -l node-role.kubernetes.io/control-plane=
----

. <<azure-regenerar-politica-control-plane,Regenera la política con los nodos actuales>>.

[[azure-regenerar-politica-control-plane]]
==== Regenerar la política con los nodos actuales

Sigue estos pasos cuando todos los nodos del _control-plane_ estén _Ready_. Sirven tanto después de un cambio planificado como después de que el _MachineHealthCheck_ reemplace un nodo.

. Guarda los nodos del _control-plane_ en un fichero:
+
[source,bash]
----
kubectl get nodes -l node-role.kubernetes.io/control-plane= -o json > cp-nodes.json
----

. Comprueba que todos los nodos tienen IP de túnel de Calico:
+
[source,bash]
----
jq '.items | length' cp-nodes.json
jq '[.items[].metadata.annotations | select(has("projectcalico.org/IPv4VXLANTunnelAddr") or has("projectcalico.org/IPv4IPIPTunnelAddr"))] | length' cp-nodes.json
----
+
*Salida esperada:* el mismo número en los dos comandos. Si no coincide, espera unos minutos y repite desde el paso 1.

. Genera el cambio de la política. Por cada nodo, incluye su IP de túnel y su IP interna con máscara `/32`:
+
[source,bash]
----
jq '{spec:{order:0,selector:"all()",ingress:[{action:"Allow",source:{nets:[.items[] | (((.metadata.annotations["projectcalico.org/IPv4VXLANTunnelAddr"] // .metadata.annotations["projectcalico.org/IPv4IPIPTunnelAddr"]) // empty) + "/32"), (.status.addresses[] | select(.type=="InternalIP") | .address + "/32")]}}]}}' cp-nodes.json > gnp-patch.json
----

. Prueba el cambio sin aplicarlo:
+
[source,bash]
----
kubectl patch globalnetworkpolicies.crd.projectcalico.org allow-all-traffic-from-control-plane --type merge --patch-file gnp-patch.json --dry-run=server -o jsonpath='{.spec.ingress[0].source.nets}'
----
+
*Salida esperada:* las IP del fichero `gnp-patch.json`, sin las de los nodos que ya no existen.

. Aplica el cambio:
+
[source,bash]
----
kubectl patch globalnetworkpolicies.crd.projectcalico.org allow-all-traffic-from-control-plane --type merge --patch-file gnp-patch.json
----
+
El cambio sustituye la lista completa de IP. Si abriste la política antes de un cambio planificado, también la cierra.

. Comprueba etcd como se indica en la <<verificacion-etcd,verificación de etcd>>.

=== Escalado estático

Aunque se desaconseja el escalado manual de un grupo de nodos existente, estas operaciones se presentan para casos sin autoescalado o para nuevos grupos de nodos.

==== Escalar un grupo de _workers_

image::escalado-manual.png[]

Para escalar manualmente un grupo de _workers_ se usa el recurso _KeosCluster_:

[source,bash]
----
kubectl -n cluster-example-eks edit keoscluster
----

[source,yaml]
----
spec:
  ...
  worker_nodes:
    - name: eks-prod-xlarge
      quantity: 9
      ...
----

Verifica el cambio consultando el estado del recurso _KeosCluster_:

[source,bash]
----
kubectl -n cluster-<cluster_name> get keoscluster <cluster_name> --subresource=status
----

NOTE: Mientras el `KeosCluster` no esté listo (`ready: false`), el _cluster_ rechaza cualquier cambio en su especificación con el mensaje "the keoscluster resource cannot be updated until it is ready". Ocurre mientras se aplica un cambio previo y también mientras _cluster-autoscaler_ añade o retira nodos de un grupo. Espera a que el `KeosCluster` esté en `ready: true` y repite el cambio.

==== Crear un nuevo grupo de _workers_

Para crear un nuevo grupo de nodos basta con añadir un nuevo elemento al _array_ _worker++_++nodes_ del recurso _KeosCluster_:

[source,yaml]
----
spec:
  ...
  worker_nodes:
    - ...
    - name: eks-prod-xlarge
      quantity: 6
      max_size: 18
      min_size: 6
      size: m6i.xlarge
      labels:
        disktype: standard
      root_volume:
        size: 50
        type: gp3
        encrypted: true
      ssh_key: stg-key
----

Nuevamente, verifica el cambio consultando el estado del recurso _KeosCluster_:

[source,bash]
----
kubectl -n cluster-<cluster_name> get keoscluster <cluster_name> --subresource=status
----

==== Escalado vertical

El escalado vertical de un grupo de nodos se realiza mediante la modificación del tipo de instancia del recurso _KeosCluster_ asociado a dicho grupo.

[source,yaml]
----
spec:
  ...
  worker_nodes:
    - name: eks-prod-xlarge
      size: m6i.2xlarge
      ...
----

=== Autoescalado

image::autoescalado.png[]

Para el autoescalado de los nodos, se utiliza _cluster-autoscaler_, que detecta los _pods_ que no pueden ejecutarse por falta de recursos y escala el grupo de nodos que considera necesario, según los filtros de los despliegues.

Esta operación se realiza en el _API Server_, donde los _controllers_ se encargan de crear las máquinas virtuales en el proveedor de _cloud_ y de añadirlas al _cluster_ como nodos _worker_ de Kubernetes.

Como el autoescalado se basa en _cluster-autoscaler_, indica el mínimo y el máximo de cada grupo de nodos en el recurso _KeosCluster_:

[source,yaml]
----
spec:
  ...
  worker_nodes:
    - name: eks-prod-xlarge
      min_size: 6
      max_size: 21
      ...
----

NOTE: En EKS, los _MachinePool_ con `min_size` y `max_size` llevan la anotación `cluster.x-k8s.io/replicas-managed-by`, que deja el número de réplicas en manos de _cluster-autoscaler_. No la quites: sin ella, CAPA puede enviar a EKS un número de réplicas desfasado.

NOTE: En EKS, el _cluster_ rechaza un cambio de `min_size`, `max_size` o `quantity` en un grupo _MachinePool_ en estos casos:

* El _nodegroup_ de EKS no está en estado `ACTIVE` (por ejemplo, porque tiene en curso un cambio hecho desde la consola o desde la CLI de AWS).
* El tamaño deseado del _nodegroup_ aún no coincide con el de su _Auto Scaling group_. Ocurre durante unos minutos después de cada cambio de _cluster-autoscaler_.
* Algún _nodegroup_ se queda con un mínimo por encima de su número de nodos o con un máximo por debajo de él. Ese número de nodos es el que fija la nueva `quantity` si la cambias; si no, el actual.
* El _cluster_ no puede consultar AWS con sus credenciales.

En los dos primeros casos, repite el cambio pasados unos minutos.

NOTE: Puede que _cluster-autoscaler_ no escale un grupo desde cero después de cambiar sus etiquetas o sus _taints_. Consulta el xref:ROOT:known-issues.adoc#cluster-autoscaler-grupo-sin-nodos-etiquetas-taints[problema conocido y su solución].

==== Prueba

Para probar el autoescalado, crea un _Deployment_ con más réplicas de las que se pueden ejecutar en los nodos actuales:

[source,bash]
----
kubectl create deploy test --replicas 1500 --image nginx:alpine
----

Al terminar la prueba, elimina el _Deployment_:

[source,bash]
----
kubectl delete deploy test
----

==== _Logs_

Los _logs_ de _cluster-autoscaler_ se pueden consultar desde su _Deployment_. En Azure no gestionado:

[source,bash]
----
kubectl -n kube-system logs -f -l app.kubernetes.io/name=clusterapi-cluster-autoscaler
----

En EKS, _cluster-autoscaler_ usa el proveedor `aws`:

[source,bash]
----
kubectl -n kube-system logs -f -l app.kubernetes.io/name=aws-cluster-autoscaler
----

En los _clusters_ de EKS actualizados a partir de la versión 0.7.x, la instancia `cluster-autoscaler-aws` está instalada con 0 réplicas y no tiene _logs_. La instancia anterior sigue escalando los _MachineDeployment_: consulta sus _logs_ con el comando de Azure no gestionado.

[[eks-activar-cluster-autoscaler-aws]]

==== Activación de `cluster-autoscaler-aws` en EKS

En los _clusters_ de EKS actualizados desde la 0.7.x, activa la instancia `cluster-autoscaler-aws` cuando vayas a usar grupos _MachinePool_, porque es la instancia que escala esos grupos.

Actívala desde sus valores de Helm. No uses `kubectl scale`, porque cualquier actualización de la _release_ devuelve el _Deployment_ a las réplicas definidas en sus valores.

. Guarda los valores propios de la instancia en un fichero:
+
[source,bash]
----
kubectl -n kube-system get configmap 02-cluster-autoscaler-aws-helm-chart-override-values -o jsonpath='{.data.values\.yaml}' > cluster-autoscaler-aws-values.yaml
----
+
Si el fichero ya tiene una línea `replicaCount`, cámbiala por `replicaCount: 2` y pasa al paso 3.

. Añade `replicaCount: 2` al fichero:
+
[source,bash]
----
printf '\nreplicaCount: 2\n' >> cluster-autoscaler-aws-values.yaml
----

. Sustituye el _ConfigMap_ por el contenido del fichero:
+
[source,bash]
----
kubectl -n kube-system create configmap 02-cluster-autoscaler-aws-helm-chart-override-values --from-file=values.yaml=cluster-autoscaler-aws-values.yaml --dry-run=client -o yaml | kubectl replace -f -
----

. Comprueba que Flux aplica el cambio:
+
[source,bash]
----
kubectl -n kube-system get deployment cluster-autoscaler-aws-cluster-autoscaler
----
+
*Salida esperada:* `READY` en `2/2` al cabo de unos minutos.

=== Actualización de Kubernetes

La actualización del _cluster_ a una versión superior de Kubernetes se realizará en dos partes dentro del mismo proceso atómico: primero, el _control-plane_, y una vez que esté en la nueva versión, los nodos _worker_, iterando por cada grupo y actualizándolos uno a uno.

CAUTION: La actualización de la versión de Kubernetes de los nodos en los _clusters_ en los que no se haya especificado la imagen puede implicar una actualización del sistema operativo.

image::upgrade-w.png[]

[CAUTION]
====
Un _Pod Disruption Budget_ (PDB) mal configurado puede impedir la eliminación de un _pod_. Esto ocurre si el PDB exige al menos una réplica disponible, pero el recurso solo tiene una réplica desplegada. En ese caso, la réplica no puede eliminarse y el nodo no se puede drenar, lo que puede afectar a las actualizaciones.

Para evitar este problema:

. Asegúrate de que los despliegues tengan más de una réplica si el PDB requiere al menos una réplica disponible.
. Antes de actualizar el _cluster_, revisa los PDB para evitar bloqueos.
. Si un recurso tiene solo una réplica, puedes eliminar temporalmente el PDB para permitir la actualización del _cluster_.

En EKS, por ejemplo, es recomendable comprobar si existe el PDB `coredns` en el _namespace_ `kube-system` y eliminarlo antes de actualizar el _cluster_:

[source,bash]
----
kubectl -n kube-system get poddisruptionbudget coredns
kubectl -n kube-system delete poddisruptionbudget coredns
----

====

==== Prerrequisitos

La actualización de la versión de un _cluster_ en entornos productivos, y especialmente en _flavours_ no gestionados, deberá realizarse extremando todas las precauciones. En particular, antes de actualizar se recomienda hacer un _backup_ de los objetos que gestionan la infraestructura con el siguiente comando:

[source,bash]
----
clusterctl --kubeconfig ./kubeconfig/path move -n cluster-<cluster_name> --to-directory ./backup/path/
----

En el caso de un _control-plane_ gestionado, se deberá verificar que la versión deseada de Kubernetes está admitida por el proveedor.

===== EKS

Antes de actualizar EKS, asegúrate de que la versión deseada está admitida. Para ello puedes utilizar el siguiente comando:

[source,bash]
----
aws eks describe-addon-versions | jq -r ".addons[] | .addonVersions[] | .compatibilities[] | .clusterVersion" | sort -nr | uniq | head -4
----

===== Azure no gestionado

La _GlobalNetworkPolicy_ creada para el _control-plane_ en la fase de instalación de _Stratio KEOS_ deberá modificarse para que *permita el tráfico de red entre todos los nodos temporalmente* durante la actualización de la versión.

Una vez finalizada, se deberán actualizar las IP internas de los nodos y las de túnel asignadas a dichos nodos:

[source,bash]
----
kubectl get nodes -l node-role.kubernetes.io/control-plane= -ojson | jq -r '.items[].status.addresses[] | select(.type=="InternalIP").address + "\/32"'
----

[source,bash]
----
IPAMHANDLERS=$(kw get ipamhandles -oname | grep control-plane)
for handler in $IPAMHANDLERS; do kw get $handler -o json | jq -r '.spec.block | keys[]' | sed 's/\/.*/\/32/'; done
----

==== Iniciar la actualización

Para iniciar la actualización, una vez satisfechos los prerrequisitos, se ejecutará un _patch_ de _spec.k8s++_++version_ en el recurso _KeosCluster_:

[source,bash]
----
kubectl -n cluster-<cluster_name> patch KeosCluster <cluster_name> --type merge -p '{"spec": {"k8s_version": "v1.35.x"}}'
----

NOTE: El _controller_ aprovisiona un nuevo nodo del grupo de _workers_ con la versión actualizada y, una vez que esté _Ready_ en Kubernetes, elimina un nodo con la versión anterior. De esta forma, se garantiza el número de nodos configurado.

[[verificacion-etcd]]
==== Verificación de etcd

Una forma de asegurar que el etcd está correcto después de actualizar un _control-plane_ no gestionado es abrir una terminal en cualquier _pod_ de etcd, verificar el estado del _cluster_ y comparar las direcciones IP de los miembros registrados con las de los nodos del _control-plane_.

[source,bash]
----
k -n kube-system exec -ti etcd-<control-plane-node> sh

alias e="etcdctl --cert=/etc/kubernetes/pki/etcd/server.crt --key=/etc/kubernetes/pki/etcd/server.key --cacert=/etc/kubernetes/pki/etcd/ca.crt "
e endpoint status
e endpoint status -w table --cluster
e member list
e member remove <member-id>
----

=== Eliminación del _cluster_

[NOTE]
.Consideraciones previas
====
Antes de eliminar los recursos del proveedor _cloud_ generados por _Stratio Cloud Provisioner_, se deberán eliminar aquellos creados por _keos-installer_ o por cualquier automatismo externo (por ejemplo, los _Services_ de tipo _LoadBalancer_).

Además, deberás tener en cuenta que el proceso requiere el binario `clusterctl` en la máquina bastión (cualquier ordenador con acceso al _API Server_) en la que se ejecutará.
====

Ejecuta los siguientes pasos para llevar a cabo la eliminación del _cluster_:

. Crea un _cluster_ local, indicando que no se cree ningún recurso en el proveedor _cloud_.
+
[source,bash]
----
[bastion]$ sudo ./bin/cloud-provisioner create cluster --name <cluster_name> --descriptor cluster.yaml --vault-password <my-passphrase> --avoid-creation
----

. Pausa el _controller_ del _Stratio Cluster Operator_:
+
[source,bash]
----
[bastion]$ kubectl --kubeconfig $KUBECONFIG -n kube-system scale deployment keoscluster-controller-manager --replicas 0
----

. Mueve la gestión del _cluster_ _worker_ al _cluster_ local utilizando el _kubeconfig_ correspondiente (para los _control-planes_ gestionados, se necesitará el _kubeconfig_ del proveedor). Para asegurar este paso, se buscará el siguiente texto en la salida del comando: "Moving Cluster API objects Clusters=1".
+
[source,bash]
----
[bastion]$ sudo clusterctl --kubeconfig $KUBECONFIG move -n cluster-<cluster_name> --to-kubeconfig /root/.kube/config
----

. Accede al _cluster_ local y elimina el _cluster_ _worker_.
+
[source,bash]
----
[bastion]$ sudo docker exec -ti <cluster_name>-control-plane bash
root@<cluster_name>-control-plane:/# kubectl -n cluster-<cluster_name> delete cl --all
cluster.cluster.x-k8s.io "<cluster_name>" deleted
root@<cluster_name>-control-plane:/#
----

. Finalmente, elimina el _cluster_ local.
+
[source,bash]
----
[bastion]$ sudo ./bin/cloud-provisioner delete cluster --name <cluster_name>
----

== Resolución de problemas

=== Bucle de reconciliación en GKE por etiquetas automáticas

En los _clusters_ gestionados con el Cluster API Provider GCP (CAPG), el controlador de CAPG responsable del recurso `GCPManagedMachinePool` puede entrar en un bucle de reconciliación infinito si detecta discrepancias entre las etiquetas (`additional_labels`) definidas en la especificación del objeto (o no definidas) y las etiquetas efectivamente presentes en el _node pool_ de GKE. Este comportamiento se refleja en los registros, con mensajes repetidos como `Node pool config update required` y `Node pool config updating in progress`. Se trata de un problema conocido en CAPG, relacionado con la reconciliación de etiquetas en los _node pools_ gestionados por el objeto `GCPManagedMachinePool`.

La causa principal es que Google Cloud GKE añade automáticamente etiquetas a los _node pools_ (por ejemplo, `goog-gke-node-pool-provisioning-model: on-demand`) que no están presentes por defecto en el recurso `GCPManagedMachinePool` generado por Cluster API. Este valor es solo un ejemplo: puede tratarse de cualquier etiqueta añadida por Google.

Para resolver este problema y detener el bucle, hay que añadir manualmente la etiqueta en la configuración del `KeosCluster` para que coincida con la que aplica el proveedor. Puedes seguir estos pasos:

. Edita el recurso `KeosCluster`:
+
[source,bash]
----
kubectl edit keoscluster <cluster_name> -n <namespace>
----

. Añade la etiqueta en el campo _additional++_++labels_ de la definición de los `worker_nodes`:
+
[source,yaml]
----
spec:
  ...
  worker_nodes:
    - name: <node_pool_name>
      ...
      additional_labels:
        "goog-gke-node-pool-provisioning-model": "on-demand"
----

CAUTION: Modificar el campo _additional++_++labels_ en los `worker_nodes` de un `KeosCluster` gestionado por CAPG provocará la recreación de los nodos asociados al _node pool_. Esto implica que los nodos actuales se eliminarán y serán reemplazados por nuevos con la configuración actualizada. Se recomienda planificar esta operación para evitar interrupciones o afectaciones al servicio.

==== _Clusters_ creados con _Stratio Cloud Provisioner_ 0.7.x

En los _clusters_ creados con _Stratio Cloud Provisioner_ 0.7.x, el objeto `KeosCluster` no admite el campo _additional++_++labels_, que se incorporó en la versión 0.8.0, y mientras el _cluster_ no esté _ready_, tampoco se puede modificar su especificación. En ese caso, añade la etiqueta directamente en los `GCPManagedMachinePool` del _cluster_, con el mismo valor que muestra GKE para el _node pool_:

[source,bash]
----
gcloud container node-pools describe <node_pool_name> --cluster <cluster_name> --region <región> \
  --format='value(config.resourceLabels)'

for mp in $(kubectl -n cluster-<cluster_name> get gcpmanagedmachinepool -o name); do
  kubectl -n cluster-<cluster_name> patch $mp --type=merge \
    -p '{"spec":{"additionalLabels":{"goog-gke-node-pool-provisioning-model":"on-demand"}}}'
done
----

Cuando el `KeosCluster` vuelva a `READY = true` y el _cluster_ esté en una versión que admita el campo, declara también la etiqueta en _additional++_++labels_ de cada grupo del `KeosCluster`, como se indica más arriba, para que se mantenga si _cluster-operator_ vuelve a generar el `GCPManagedMachinePool`.
