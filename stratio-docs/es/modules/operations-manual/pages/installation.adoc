= Instalación

== Prerrequisitos

=== EKS

* Roles y políticas
+
Para el aprovisionamiento automatizado en EKS, hay que ejecutar acciones en varios servicios, como EC2, ECR, EKS y Elastic Load Balancing (ELB), entre otros. Aunque el uso de estas acciones puede variar según el tipo de instalación, el proveedor comprueba que el usuario indicado dispone de los permisos necesarios para garantizar su correcto funcionamiento. Mantén los permisos de ambos ficheros de forma permanente.
+
** xref:attachment$stratio-eks-policy.json[Descargar permisos para EKS]
** xref:attachment$stratio-aws-temp-policy.json[Descargar permisos de IAM y CloudFormation para EKS]
+
Para el despliegue de EKS, crea manualmente el rol `AWSServiceRoleForAmazonEKS` y asígnale la política `AmazonEKSServiceRolePolicy` (que AWS crea por defecto).
+
[[eks_nodegroup_permissions]]
+
NOTE: Si el _cluster_ incluye grupos de tipo _MachinePool_ (_nodegroups_ gestionados por EKS), el usuario de despliegue necesita permisos adicionales: `eks:CreateNodegroup`, `eks:DescribeNodegroup`, `eks:DeleteNodegroup`, `autoscaling:DescribeAutoScalingGroups` e `iam:CreateServiceLinkedRole`. Estos permisos ya están incluidos en el fichero `stratio-eks-policy.json`.

* Sistemas operativos certificados
+
En EKS, los nodos _worker_ usan las AMI que gestiona EKS para el tipo indicado en _ami++_++type_: `BOTTLEROCKET_x86_64` (por defecto) o `BOTTLEROCKET_x86_64_NVIDIA`. No necesitas construir imágenes propias.

* AWS CloudFormation
+
WARNING: Si no has creado el _stack_ de AWS CloudFormation o no has creado previamente los requisitos de IAM en la cuenta, establece el parámetro `spec.security.aws.create_iam` en `true` (por defecto, es `false`).

=== GKE

* Permisos
+
En GKE, la cuenta de servicio con la que se aprovisionan los _clusters_ tiene que tener los siguientes conjuntos de permisos:
+
** xref:attachment$stratio-gcp-permissions.list[Descargar permisos para GCP].
** xref:attachment$stratio-gke-permissions.list[Descargar permisos para GKE].

* Sistemas operativos certificados
+
En GKE, el sistema operativo predeterminado es Container-Optimized OS (COS) y no es necesario especificar ninguna imagen.

* API de Google Kubernetes Engine (GKE) habilitada

* _Bastion_
+
Para desplegar _Stratio KEOS_ en GKE, necesitas un _bastion_ que facilite la comunicación con el _cluster_. Créalo en la misma red que el _cluster_.
+
Desde Kubernetes 1.35, la VM del _bastion_ debe tener habilitado cgroup v2. Si el _preflight check_ del kubelet (`system-validators v1.12.1`) detecta cgroup v1 en el _host_, devuelve un error, no un aviso. Esto ocurre al ejecutar el kubelet en la versión 1.35 o posterior. Para habilitar cgroup v2 en el _bastion_, ejecuta:
+
[source,bash]
----
sudo sed -i 's/GRUB_CMDLINE_LINUX=""/GRUB_CMDLINE_LINUX="systemd.unified_cgroup_hierarchy=1 cgroup_no_v1=all"/' /etc/default/grub
sudo update-grub
sudo reboot
----
+
Tras el reinicio, comprueba el cambio con `stat -fc %T /sys/fs/cgroup/`, que debe devolver `cgroup2fs`.
+
Referencia: https://github.com/kubernetes/kubernetes/blob/master/CHANGELOG/CHANGELOG-1.35.md[Kubernetes v1.35 CHANGELOG].

=== Azure no gestionado

* Permisos
+
Para aprovisionar en Azure no gestionado, necesitas una cuenta con todos los permisos necesarios, al igual que en los demás proveedores admitidos. Además, tienes que definir:
+
** Un rol para los _workers_ del _cluster_ en `spec.security.nodes_identity`.
** Un rol para el _control-plane_ en `spec.security.control_plane_identity`.
+
Si los permisos se asignan a nivel de suscripción, se recomiendan estos ficheros:
+
** xref:attachment$stratio-azure-role.json[Descargar permisos para el usuario de despliegue de Azure].
** xref:attachment$stratio-azure-nodes-role.json[Descargar permisos para _workers_ de Azure].
** xref:attachment$stratio-azure-cp-role.json[Descargar permisos para el _control-plane_ de Azure].
+
Si los permisos se asignan a nivel de grupo de recursos, se recomiendan estos ficheros:
+
** xref:attachment$stratio-azure-role-rg.json[Descargar permisos para el usuario de despliegue de Azure].
** xref:attachment$stratio-azure-nodes-role-rg.json[Descargar permisos para _workers_ de Azure].
** xref:attachment$stratio-azure-cp-role-rg.json[Descargar permisos para el _control-plane_ de Azure].
** xref:attachment$stratio-azure-acr.json[Descargar permisos para el usuario de despliegue, los _workers_ y el _control-plane_ de Azure].
** Además, asigna estos permisos a nivel de grupo de recursos:
*** Usuario de despliegue: `AcrPull` en `/subscriptions/<subscription_id>/resourceGroups/<resource_group>/providers/Microsoft.ContainerRegistry/registries/<acr_name>`
*** _Control-plane_: `AcrPull` en `/subscriptions/<subscription_id>/resourceGroups/<resource_group>/providers/Microsoft.ContainerRegistry/registries/<acr_name>`
*** _Workers_: `AcrPull` en `/subscriptions/<subscription_id>/resourceGroups/<resource_group>/providers/Microsoft.ContainerRegistry/registries/<acr_name>`
+
Si el usuario de despliegue también prepara el prerrequisito de _external-dns_ de _Stratio KEOS_ (las zonas DNS, su _Service Principal_ y sus asignaciones de rol), además necesita:
+
** Los permisos del rol para el prerrequisito de _external-dns_, que puedes descargar en el fichero xref:attachment$stratio-azure-keos-dns-role.json[`stratio-azure-keos-dns-role.json`]. Complementan los permisos del usuario de despliegue, no los sustituyen.
** El permiso de aplicación `Application.ReadWrite.OwnedBy` de Microsoft Graph, que debe ser concedido por un administrador de Microsoft Entra ID.

* Sistemas operativos certificados
+
Para garantizar la compatibilidad entre el _control-plane_ y los nodos _worker_ en entornos no gestionados de Azure, hay que usar imágenes correctamente configuradas. Se recomienda generarlas con el https://github.com/kubernetes-sigs/image-builder[_Image Builder_ de Kubernetes], una herramienta oficial del proyecto Kubernetes que permite crear imágenes adaptadas a distintos proveedores de _cloud_. Para aprender a construir imágenes personalizadas, consulta la https://image-builder.sigs.k8s.io/[documentación oficial de _Image Builder_].

El sistema operativo recomendado es Ubuntu 22.04, que es el que se configura por defecto en el _controller_ de Azure.

=== Consideraciones para las imágenes

En EKS y GKE no se puede especificar una imagen para el _control-plane_, pero en Azure no gestionado sí se puede.

Para los nodos _worker_, en Azure no gestionado, indicar la imagen es opcional (si no se indica, el _controller_ asigna una imagen disponible del proveedor de _cloud_).

Al crear la imagen para el _cluster_, ten en cuenta los requisitos del sistema operativo de las aplicaciones que los requieran (_systemd units_, _DaemonSets_, etc.) y la versión de Kubernetes que se va a utilizar.

==== Elasticsearch

Para admitir los despliegues de Elasticsearch, el sistema operativo debe tener el parámetro `vm.max_map_count = 262144` configurado en _sysctl_, como indica su https://www.elastic.co/guide/en/elasticsearch/reference/current/vm-max-map-count.html[documentación oficial].

Las imágenes de Amazon Linux 2 *que utiliza EKS* ya incluyen este parámetro y su valor.

==== Imagen de _cluster-autoscaler_

Con `deploy_autoscaler: true`, _Stratio Cloud Provisioner_ instala _cluster-autoscaler_ en EKS y en Azure no gestionado. En EKS, _cluster-autoscaler_ usa el proveedor `aws`. Con `spec.security.aws.create_iam: true`, _Stratio Cloud Provisioner_ asocia la política de IAM de _cluster-autoscaler_ a los roles de los nodos. Con `create_iam: false`, el rol `eks-nodegroup.cluster-api-provider-aws.sigs.k8s.io` ya debe tener asociadas las políticas `cluster-autoscaler.cluster-api-provider-aws.sigs.k8s.io` y `AmazonEBSCSIDriverPolicy`. Si falta alguna, la validación del descriptor falla e indica cuáles faltan.

NOTE: Puede que _cluster-autoscaler_ no escale un grupo desde cero después de cambiar sus etiquetas o sus _taints_. Consulta el xref:ROOT:known-issues.adoc#cluster-autoscaler-grupo-sin-nodos-etiquetas-taints[problema conocido y su solución].

La imagen depende de la versión de Kubernetes del _cluster_ y del registro:

[cols="1,3,3", options="header"]
|===
^|Kubernetes ^|Sin registro privado ^|Con registro privado

| 1.32
| `registry.k8s.io/autoscaling/cluster-autoscaler:v1.32.7`
| `<registro>/autoscaling/cluster-autoscaler:v1.32.7`

| 1.34
| `registry.k8s.io/autoscaling/cluster-autoscaler:v1.34.5`
| `<registro>/autoscaling/cluster-autoscaler:v1.34.5`

| 1.35
| `registry.k8s.io/autoscaling/cluster-autoscaler:v1.35.3`
| `<registro>/autoscaling/cluster-autoscaler:v1.35.3`
|===

`<registro>` es el repositorio marcado con _keos++_++registry_. Las imágenes de esa ruta deben estar en él antes de crear el _cluster_. Con la _pull-through cache_ de ECR, la ruta es `<registro>/k8s/autoscaling/cluster-autoscaler`.

==== Prerrequisitos para `ecr_pull_through_cache_enabled`

Antes de crear un _cluster_ con `ecr_pull_through_cache_enabled: true`, comprueba que la cuenta de AWS cumple los siguientes requisitos:

* Reglas de _pull-through cache_ configuradas en Amazon ECR para los cinco _upstreams_ que utiliza _Stratio KEOS_: `registry.k8s.io`, `docker.io`, `ghcr.io`, `quay.io` y `public.ecr.aws`.
* Permisos de IAM para el rol de los nodos: `ecr:BatchImportUpstreamImage` y `ecr:CreateRepository`.

Si tienes `spec.security.aws.create_iam: true` en el descriptor, _Stratio Cloud Provisioner_ añade estos permisos automáticamente al crear el _cluster_. Si gestionas los recursos de IAM de forma manual (`create_iam: false`) o necesitas habilitarlos en una cuenta existente, actualiza el _stack_ de AWS CloudFormation con `clusterawsadm`:

NOTE: El usuario de AWS con el que ejecutas `clusterawsadm` debe tener los permisos definidos en el fichero xref:attachment$stratio-aws-temp-policy.json[`stratio-aws-temp-policy.json`].

[source,bash]
----
cat > /tmp/eks.config << 'EOF'
apiVersion: bootstrap.aws.infrastructure.cluster.x-k8s.io/v1beta1
kind: AWSIAMConfiguration
spec:
  bootstrapUser:
    enable: false
  eks:
    enable: true
    iamRoleCreation: false
    defaultControlPlaneRole:
        disable: false
    managedMachinePool:
        disable: false
        extraPolicyAttachments:
        - arn:aws:iam::aws:policy/service-role/AmazonEBSCSIDriverPolicy
  controlPlane:
    enableCSIPolicy: true
  nodes:
    extraPolicyAttachments:
    - arn:aws:iam::aws:policy/service-role/AmazonEBSCSIDriverPolicy
    extraStatements:
    - Action:
        - "ecr:BatchImportUpstreamImage"
        - "ecr:CreateRepository"
      Effect: Allow
      Resource:
        - "*"
EOF

clusterawsadm bootstrap iam create-cloudformation-stack \
  --config /tmp/eks.config \
  --region <region>
----

Si el _stack_ ya estaba actualizado, el comando termina con este error, muestra su ayuda (`Usage:`) y devuelve el código de salida 1. No cambia nada y puedes ignorarlo:

[source,text]
----
Error: failed to update AWS CloudFormation stack: operation error CloudFormation: UpdateStack, https response error StatusCode: 400, RequestID: <id>, api error ValidationError: No updates are to be performed.
----

NOTE: La política de _cluster-autoscaler_ (`cluster-autoscaler.cluster-api-provider-aws.sigs.k8s.io`) no forma parte del _stack_. La asocian a los roles `eks-nodegroup` y `nodes` _Stratio Cloud Provisioner_, al crear el _cluster_, y `upgrade-provisioner.py`, al actualizarlo. Las actualizaciones del _stack_ no la eliminan. No la añadas a esta configuración: si el _stack_ la incluye, la siguiente actualización del _stack_ sin ella la quita de los roles.

=== Uso de `role_arn` en el descriptor de credenciales

También puedes definir el `role_arn` directamente en el descriptor de credenciales para usar _assume role_ automáticamente:

[source,yaml]
----
credentials:
    aws:
        role_arn: arn:aws:iam::<accountID>:role/my-aws-role
----

NOTE: Este parámetro es opcional. Solo se utiliza _assume role_ si `role_arn` está definido en el descriptor.

NOTE: Los prerrequisitos son los mismos que los de la sección xref:operations-manual:operations-manual.adoc#_prerrequisitos[Activar la autorización mediante _assume role_ en AWS para un _cluster_ EKS] del manual de operaciones.

=== Redes

Como se mencionó anteriormente, el instalador permite utilizar elementos de red del proveedor de _cloud_ creados previamente (por ejemplo, por un equipo de seguridad de redes), lo que permite implementar las arquitecturas que mejor se adapten a cada necesidad.

Tanto la VPC como las _subnets_ deben estar creadas en el proveedor de _cloud_. Las _subnets_ pueden ser privadas o públicas, pero, en este último caso, tienen que tener un _NAT gateway_ y un _Internet Gateway_ en la misma VPC. Si indicas _subnets_ de ambos tipos, los nodos _worker_ se despliegan en las _subnets_ privadas.

_Stratio KEOS_ no gestiona el ciclo de vida de los objetos creados previamente.

NOTE: Puedes establecer _min++_++size_ en 0, de modo que el autoescalado aumente o reduzca el número de nodos hasta llegar a cero, según sea necesario. Así, puedes definir un grupo de _workers_ sin instanciar recursos innecesarios en el proveedor de _cloud_, con el consiguiente ahorro de costes.

NOTE: En EKS, _Stratio Cloud Provisioner_ crea todos los grupos de nodos como _MachinePool_ (grupos gestionados por EKS) y rechaza los grupos con _node++_++image_. Los _clusters_ actualizados desde la versión 0.7.x conservan sus grupos _MachineDeployment_. Para escalar un _MachinePool_ a cero réplicas, _max++_++size_ debe ser mayor o igual que el número de zonas de disponibilidad del _cluster_.

==== EKS

En este ejemplo, se pueden ver estas particularidades:

* _Cluster_ en AWS con _control-plane_ gestionado (EKS).
* Versión 1.35.x de Kubernetes (EKS no considera la versión _patch_).
* Uso de ECR como registro de Docker (no requiere credenciales).
* Uso de una VPC y de unas _subnets_ personalizadas (creadas previamente). Este apartado es opcional.
* Definición de una _StorageClass_ por defecto. Este apartado es opcional.

[%header,cols="2,3"]

| Limitación
| Nota

| AMI personalizada (`ami_id`) no admitida en _MachinePool_

== Creación del _cluster_

_Stratio Cloud Provisioner_ es una herramienta que automatiza el aprovisionamiento de los recursos necesarios en el proveedor de _cloud_ indicado para crear un _cluster_ de Kubernetes a partir del <<descriptor_del_cluster, descriptor>>.

Actualmente, el binario ofrece las siguientes opciones:

- `--avoid-creation`: no crea el _cluster_ _worker_, solo el _cluster_ local.
- `--build-stratio-image`: en lugar de descargar la imagen de _Stratio Cloud Provisioner_, la construye localmente y la utiliza. Esta opción está pensada solo para el desarrollo.
- `--delete-previous`: elimina el contenedor del _cluster_ local si ya existe.
- `-d, --descriptor <string>`: permite indicar el nombre del descriptor, en el directorio actual o en otro. Por defecto, `cluster.yaml`.
- `-h, --help`: muestra la ayuda del comando.
- `--keep-mgmt`: mantiene la gestión del _cluster_ en kind (solo en entornos *no productivos*).
- `--local-stratio-image-version <string>`: sobrescribe la versión local de la imagen de _Stratio Cloud Provisioner_ cuando se utiliza `--use-local-stratio-image`.
- `-n, --name <string>`: nombre del _cluster_; sobrescribe la variable `KIND_CLUSTER_NAME`. Por defecto, `kind`.
- `--retain`: conserva los nodos para depurarlos si falla la creación del _cluster_.
- `--use-local-stratio-image`: utiliza la imagen local de _Stratio Cloud Provisioner_, sin construirla ni descargarla.
- `--validate-only`: valida el descriptor sin crear el _cluster_.
- `-p, --vault-password <string>`: establece la contraseña de Vault con la que se cifran los secretos.

=== Balanceador de carga

Por un error de los distintos _controllers_ (corregido en la rama principal, pero todavía sin una versión publicada), el balanceador de carga que se crea en GCP y en Azure para el _API Server_ de los _clusters_ con _control-plane_ no gestionado se configura con un _health check_ basado en TCP.

Esto puede causar problemas en las peticiones si falla alguno de los nodos del _control-plane_, porque el balanceador de carga envía peticiones a los nodos del _control-plane_ cuyo puerto responde, aunque no puedan atenderlas.

Para evitarlo, modifica el _health check_ del balanceador de carga creado para que utilice el protocolo HTTPS y la ruta `/readyz`. Mantén el puerto 443 en GCP y el 6443 en Azure.

=== Etiquetas automáticas en GKE

GKE aplica automáticamente varias etiquetas a los recursos del _cluster_, como las instancias de máquinas virtuales de Compute Engine, los discos persistentes y los aceleradores (TPU). Por ejemplo:

- `goog-gke-node-pool-provisioning-model`: `on-demand`. Indica el modelo de aprovisionamiento del grupo de nodos (_node pool_).

NOTE: Según el caso, puede que tengas que añadir manualmente la etiqueta `goog-gke-node-pool-provisioning-model` al descriptor al desplegar el _cluster_, para evitar bucles de reconciliación. También puedes añadirla después, modificando el objeto `KeosCluster`. Los nodos pueden ser _on-demand_, reservados o _spot_.

WARNING: Estas etiquetas automáticas pueden causar un bucle de reconciliación en los _node pools_ en el controlador de `cluster-api-provider-gcp` (CAPG). Para más detalles, consulta la sección xref:operations-manual:operations-manual.adoc#_bucle_de_reconciliación_en_gke_por_etiquetas_automáticas[Resolución de problemas] del manual de operaciones.

No edites ni elimines estas etiquetas automáticas, porque GKE las vuelve a aplicar al recrear los nodos de los _node pools_ correspondientes.

TIP: Para más información, consulta la documentación oficial de Google sobre las https://docs.cloud.google.com/kubernetes-engine/docs/how-to/creating-managing-labels[etiquetas automáticas que aplica GKE].

== Despliegue de _aws-load-balancer-controller_ (solo EKS)

En los _clusters_ de EKS, se puede desplegar un controlador (_aws-load-balancer-controller_) que crea los _Elastic Load Balancers_ para objetos como los _Ingress_ y los _Service_ de tipo _LoadBalancer_.

Como este despliegue no está habilitado por defecto, tienes que indicarlo en el recurso _ClusterConfig_ del descriptor del _cluster_, con `spec.eks_lb_controller: true`.

Para autorizar el controlador, se utilizan https://docs.aws.amazon.com/es_es/eks/latest/userguide/iam-roles-for-service-accounts.html[roles de IAM para cuentas de servicio], así que hay que crear los objetos de IAM correspondientes:

* Define las siguientes variables de entorno:
+
[source,shell]
----
export AWS_ACCOUNT_ID=<account_id>
export AWS_REGION=<aws_region>
export AWS_VPC_ID=<vpc_id>
export AWS_EKS_CLUSTER_NAME=<aws_eks_cluster_name>
export AWS_EKS_OIDC_ID=$(aws eks describe-cluster --region ${AWS_REGION} --name ${AWS_EKS_CLUSTER_NAME} --query 'cluster.identity.oidc.issuer' --output text | awk -F'/' '{print $NF}')
export AWS_IAM_POLICY_NAME="${AWS_EKS_CLUSTER_NAME}-lb-controller-manager"
export AWS_IAM_ROLE_NAME="${AWS_EKS_CLUSTER_NAME}-lb-controller-manager"
----

* https://docs.aws.amazon.com/es_es/IAM/latest/UserGuide/id_roles_create.html[Crea el rol de IAM] que va a utilizar la cuenta de servicio del despliegue de _aws-load-balancer-controller_, con la siguiente política de confianza:
+
[source,console]
----
$ cat << EOF > trustpolicy.json
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Effect": "Allow",
            "Principal": {
                "Federated": "arn:aws:iam::${AWS_ACCOUNT_ID}:oidc-provider/oidc.eks.${AWS_REGION}.amazonaws.com/id/${AWS_EKS_OIDC_ID}"
            },
            "Action": "sts:AssumeRoleWithWebIdentity",
            "Condition": {
                "StringEquals": {
                    "oidc.eks.${AWS_REGION}.amazonaws.com/id/${AWS_EKS_OIDC_ID}:sub": "system:serviceaccount:kube-system:aws-load-balancer-controller",
                    "oidc.eks.${AWS_REGION}.amazonaws.com/id/${AWS_EKS_OIDC_ID}:aud": "sts.amazonaws.com"
                }
            }
        }
    ]
}
EOF
$ aws iam create-role --role-name ${AWS_IAM_ROLE_NAME} --assume-role-policy-document file://trustpolicy.json
----

* https://docs.aws.amazon.com/es_es/IAM/latest/UserGuide/access_policies_create.html[Crea la política de IAM] con los permisos estrictamente necesarios:
+
[source,console]
----
$ cat << EOF > policy.json
{
	"Statement": [
		{
			"Action": [
        			"ec2:DescribeAvailabilityZones",
				"ec2:DescribeInstances",
				"ec2:DescribeSecurityGroups",

				"elasticloadbalancing:DescribeListeners",
				"elasticloadbalancing:DescribeListenerAttributes",
				"elasticloadbalancing:DescribeLoadBalancers",

				"elasticloadbalancing:DescribeRules",
				"elasticloadbalancing:DescribeTags",
				"elasticloadbalancing:DescribeTargetGroups",
				"elasticloadbalancing:DescribeTargetGroupAttributes",
				"elasticloadbalancing:DescribeTargetHealth",
        "shield:GetSubscriptionState"
			],
			"Effect": "Allow",
			"Resource": "*"
		},
		{
			"Action": [
				"ec2:AuthorizeSecurityGroupIngress",
				"ec2:CreateSecurityGroup",
        			"ec2:CreateTags",

			"Effect": "Allow",

* https://docs.aws.amazon.com/es_es/IAM/latest/UserGuide/access_policies_manage-attach-detach.html[Asocia la política de IAM] al rol que has creado:
+
[source,console]
----

----

* Reinicia el controlador (_aws-load-balancer-controller_):
+
[source,console]
----
$ kubectl -n kube-system rollout restart deployment aws-load-balancer-controller
----
