= Installation

== Prerequisites

=== EKS

* Roles and policies
+
For automated provisioning in EKS, actions must be run across several services, such as EC2, ECR, EKS, and Elastic Load Balancing (ELB). Although the required actions may vary depending on the installation type, the provider checks that the specified user has the necessary permissions to ensure correct operation. Keep the permissions of both files permanent.
+
** xref:attachment$stratio-eks-policy.json[Download the permissions for EKS]
** xref:attachment$stratio-aws-temp-policy.json[Download the IAM and CloudFormation permissions for EKS]
+
For the EKS deployment, manually create the `AWSServiceRoleForAmazonEKS` role and assign the `AmazonEKSServiceRolePolicy` policy to it (which AWS creates by default).
+
[[eks_nodegroup_permissions]]
+
NOTE: When the cluster includes _MachinePool_-type groups (nodegroups managed by EKS), the deployment user needs additional permissions: `eks:CreateNodegroup`, `eks:DescribeNodegroup`, `eks:DeleteNodegroup`, `autoscaling:DescribeAutoScalingGroups`, and `iam:CreateServiceLinkedRole`. These permissions are already included in `stratio-eks-policy.json`.

* Certified operating systems
+
In EKS, the worker nodes use the AMIs that EKS manages for the type indicated in _ami++_++type_: `BOTTLEROCKET_x86_64` (by default) or `BOTTLEROCKET_x86_64_NVIDIA`. No need to build custom images.

* AWS CloudFormation
+
WARNING: When the AWS CloudFormation stack has not been created, or the IAM requirements have not been previously created in the account, set the `spec.security.aws.create_iam` parameter to `true` (by default, it is `false`).

=== GKE

* Permissions
+
In GKE, the service account with which the clusters are provisioned must have the following sets of permissions:
+
** xref:attachment$stratio-gcp-permissions.list[Download the permissions for GCP].
** xref:attachment$stratio-gke-permissions.list[Download the permissions for GKE].

* Certified operating systems
+
In GKE, the default operating system is Container-Optimized OS (COS), and you don't need to specify an image.

* Google Kubernetes Engine (GKE) API enabled

* Bastion
+
To deploy _Stratio KEOS_ in GKE, you need a bastion that facilitates communication with the cluster. Create it in the same network as the cluster.
+
From Kubernetes 1.35, the bastion VM must have cgroup v2 enabled. When the kubelet preflight check (`system-validators v1.12.1`) detects cgroup v1 on the host, it returns an error, not a warning. This happens when running kubelet 1.35 or later. To enable cgroup v2 on the bastion, run:
+
[source,bash]
----
sudo sed -i 's/GRUB_CMDLINE_LINUX=""/GRUB_CMDLINE_LINUX="systemd.unified_cgroup_hierarchy=1 cgroup_no_v1=all"/' /etc/default/grub
sudo update-grub
sudo reboot
----
+
After the restart, check the change with `stat -fc %T /sys/fs/cgroup/`, which should return `cgroup2fs`.
+
Reference: https://github.com/kubernetes/kubernetes/blob/master/CHANGELOG/CHANGELOG-1.35.md[Kubernetes v1.35 CHANGELOG].

=== Unmanaged Azure

* Permissions
+
To provision in unmanaged Azure, you need an account with all the necessary permissions, as with the other supported providers. In addition, the following must be defined:
+
** A role for the cluster workers in `spec.security.nodes_identity`.
** A role for the _control-plane_ in `spec.security.control_plane_identity`.
+
When the permissions are assigned at the subscription level, these files are recommended:
+
** xref:attachment$stratio-azure-role.json[Download the permissions for the Azure deployment user].
** xref:attachment$stratio-azure-nodes-role.json[Download the permissions for Azure workers].
** xref:attachment$stratio-azure-cp-role.json[Download the permissions for the Azure _control-plane_].
+
When the permissions are assigned at the resource-group level, these files are recommended:
+
** xref:attachment$stratio-azure-role-rg.json[Download the permissions for the Azure deployment user].
** xref:attachment$stratio-azure-nodes-role-rg.json[Download the permissions for Azure workers].
** xref:attachment$stratio-azure-cp-role-rg.json[Download the permissions for the Azure _control-plane_].
** xref:attachment$stratio-azure-acr.json[Download the permissions for the deployment user, the workers, and the Azure _control-plane_].
** In addition, assign these permissions at the resource-group level:
*** Deployment user: `AcrPull` on `/subscriptions/<subscription_id>/resourceGroups/<resource_group>/providers/Microsoft.ContainerRegistry/registries/<acr_name>`
*** _Control-plane_: `AcrPull` on `/subscriptions/<subscription_id>/resourceGroups/<resource_group>/providers/Microsoft.ContainerRegistry/registries/<acr_name>`
*** Workers: `AcrPull` on `/subscriptions/<subscription_id>/resourceGroups/<resource_group>/providers/Microsoft.ContainerRegistry/registries/<acr_name>`
+
When the deployment user also prepares the _Stratio KEOS_ _external-dns_ prerequisite (the DNS zones, its service principal, and its role assignments), in addition it needs:
+
** The permissions of the role for the _external-dns_ prerequisite, which can be downloaded in the xref:attachment$stratio-azure-keos-dns-role.json[`stratio-azure-keos-dns-role.json`] file. They complement the permissions of the deployment user; they do not replace them.
** The `Application.ReadWrite.OwnedBy` application permission of Microsoft Graph, which must be granted by a Microsoft Entra ID administrator.

* Certified operating systems
+
To ensure compatibility between the _control-plane_ and the worker nodes in unmanaged Azure environments, use correctly configured images. It is recommended to generate them with the https://github.com/kubernetes-sigs/image-builder[Kubernetes _Image Builder_], an official Kubernetes project tool that allows you to create images adapted to different cloud providers. To learn how to build custom images, see https://image-builder.sigs.k8s.io/[official _Image Builder_ documentation].

The recommended operating system is Ubuntu 22.04, which is the one configured by default in the Azure controller.

=== Considerations for the images

In EKS and GKE, an image for the _control-plane_ cannot be specified, but in unmanaged Azure it can.

For the worker nodes, in unmanaged Azure, specifying the image is optional (if not specified, the controller assigns an available image from the cloud provider).

When creating the image for the cluster, take into account the operating system requirements of the applications (systemd units, _DaemonSets_, and so on) and the Kubernetes version to be used.

==== Elasticsearch

To support Elasticsearch deployments, the operating system must have the `vm.max_map_count = 262144` parameter configured in sysctl, as indicated in its https://www.elastic.co/guide/en/elasticsearch/reference/current/vm-max-map-count.html[official documentation].

The Amazon Linux 2 images *that EKS uses* already include this parameter and its value.

==== cluster-autoscaler image

With `deploy_autoscaler: true`, _Stratio Cloud Provisioner_ installs cluster-autoscaler in EKS and in unmanaged Azure. In EKS, cluster-autoscaler uses the `aws` provider. With `spec.security.aws.create_iam: true`, _Stratio Cloud Provisioner_ associates the cluster-autoscaler IAM policy with the nodes' roles. With `create_iam: false`, the `eks-nodegroup.cluster-api-provider-aws.sigs.k8s.io` role must already have the `cluster-autoscaler.cluster-api-provider-aws.sigs.k8s.io` and `AmazonEBSCSIDriverPolicy` policies associated with it. If any are missing, descriptor validation fails and indicates which ones are missing.

NOTE: cluster-autoscaler may not scale a group from zero after changing its labels or its taints. See the xref:ROOT:known-issues.adoc#cluster-autoscaler-grupo-sin-nodos-etiquetas-taints[known issue and its solution].

The image depends on the Kubernetes version of the cluster and on the registry:

[cols="1,3,3", options="header"]
|===
^|Kubernetes ^|Without a private registry ^|With a private registry

| 1.32
| `registry.k8s.io/autoscaling/cluster-autoscaler:v1.32.7`
| `<registry>/autoscaling/cluster-autoscaler:v1.32.7`

| 1.34
| `registry.k8s.io/autoscaling/cluster-autoscaler:v1.34.5`
| `<registry>/autoscaling/cluster-autoscaler:v1.34.5`

| 1.35
| `registry.k8s.io/autoscaling/cluster-autoscaler:v1.35.3`
| `<registry>/autoscaling/cluster-autoscaler:v1.35.3`
|===

`<registry>` is the repository marked with _keos++_++registry_. The images in that path must be in it before creating the cluster. With the ECR pull-through cache, the path is `<registry>/k8s/autoscaling/cluster-autoscaler`.

==== Prerequisites for `ecr_pull_through_cache_enabled`

Before creating a cluster with `ecr_pull_through_cache_enabled: true`, check that the AWS account meets the following requirements:

* Pull-through cache rules configured in Amazon ECR for the five upstreams that _Stratio KEOS_ uses: `registry.k8s.io`, `docker.io`, `ghcr.io`, `quay.io`, and `public.ecr.aws`.
* IAM permissions for the `nodes` role: `ecr:BatchImportUpstreamImage` and `ecr:CreateRepository`. Con `create_iam: true`, los añade _Stratio Cloud Provisioner_.
* Los mismos permisos para el rol `eks-nodegroup`, que usan los nodos _MachinePool_. En el _stack_ de `clusterawsadm`, este rol solo admite políticas gestionadas, así que necesitas una política de IAM propia con esos permisos.

_Stratio Cloud Provisioner_ no crea esta política. Créala antes de instalar con un usuario que tenga el permiso `iam:CreatePolicy`, incluido en xref:attachment$stratio-aws-temp-policy.json[`stratio-aws-temp-policy.json`]:

[source,bash]
----
cat > ecr-pull-through-mp-policy.json << 'EOF'
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Action": ["ecr:BatchImportUpstreamImage", "ecr:CreateRepository"],
      "Effect": "Allow",
      "Resource": ["*"]
    }
  ]
}
EOF

aws iam create-policy --policy-name ecr-pull-through-cache-machinepool \
  --policy-document file://ecr-pull-through-mp-policy.json \
  --query Policy.Arn --output text
----

Guarda el ARN que devuelve. Si la política ya existe (`EntityAlreadyExists`), su ARN es `arn:aws:iam::<id-de-cuenta>:policy/ecr-pull-through-cache-machinepool`.

Con `spec.security.aws.create_iam: true`, indica ese ARN en el descriptor. Al crear el _cluster_, _Stratio Cloud Provisioner_ añade los permisos al rol `nodes` y asocia la política al rol `eks-nodegroup`:

[source,yaml]
----
spec:
  security:
    aws:
      create_iam: true
      nodegroup_extra_policy_arn: arn:aws:iam::<id-de-cuenta>:policy/ecr-pull-through-cache-machinepool
----

NOTE: El _stack_ de IAM es común a todos los _clusters_ de la cuenta, y cada creación con `create_iam: true` lo actualiza. Indica `nodegroup_extra_policy_arn` en todos ellos: si un _cluster_ se crea sin él, la política deja de estar asociada al rol `eks-nodegroup`.

When the IAM resources are managed manually (`create_iam: false`) or they need to be enabled on an existing account, update the AWS CloudFormation stack with `clusterawsadm`. Put the policy ARN in `managedMachinePool.extraPolicyAttachments`, as in the example. No indiques `nodegroup_extra_policy_arn` en el descriptor: con `create_iam: false`, la validación lo rechaza.

NOTE: The AWS user with which `clusterawsadm` is run must have the permissions defined in the xref:attachment$stratio-aws-temp-policy.json[`stratio-aws-temp-policy.json`] file.

[source,bash]
----
cat > /tmp/eks.config << 'EOF'
apiVersion: bootstrap.aws.infrastructure.cluster.x-k8s.io/v1beta1
kind: AWSIAMConfiguration
spec:
  bootstrapUser:
    enable: false
  eks:
    enable: true
    iamRoleCreation: false
    defaultControlPlaneRole:
        disable: false
    managedMachinePool:
        disable: false
        extraPolicyAttachments:
        - arn:aws:iam::aws:policy/service-role/AmazonEBSCSIDriverPolicy
        - arn:aws:iam::<id-de-cuenta>:policy/ecr-pull-through-cache-machinepool
  controlPlane:
    enableCSIPolicy: true
  nodes:
    extraPolicyAttachments:
    - arn:aws:iam::aws:policy/service-role/AmazonEBSCSIDriverPolicy
    extraStatements:
    - Action:
        - "ecr:BatchImportUpstreamImage"
        - "ecr:CreateRepository"
      Effect: Allow
      Resource:
        - "*"
EOF

clusterawsadm bootstrap iam create-cloudformation-stack \
  --config /tmp/eks.config \
  --region <region>
----

When the stack was already updated, the command ends with this error, shows its help (`Usage:`), and returns exit code 1. It does not change anything and can be ignored:

[source,text]
----
Error: failed to update AWS CloudFormation stack: operation error CloudFormation: UpdateStack, https response error StatusCode: 400, RequestID: <id>, api error ValidationError: No updates are to be performed.
----

NOTE: The cluster-autoscaler policy (`cluster-autoscaler.cluster-api-provider-aws.sigs.k8s.io`) is not part of the stack. It is associated with the `eks-nodegroup` and `nodes` roles by _Stratio Cloud Provisioner_, on creating the cluster, and by `upgrade-provisioner.py`, on upgrading it. Stack updates do not remove it. Do not add it to this configuration: when the stack includes it, the next stack update without it removes it from the roles.

=== Use of `role_arn` in the credentials descriptor

credentials:

== Cluster creation

_Stratio Cloud Provisioner_ automates provisioning the necessary resources on the specified cloud provider to create a Kubernetes cluster from the <<descriptor_del_cluster, descriptor>>.

Currently, the binary offers the following options:

- `--avoid-creation`: does not create the worker cluster, only the local cluster.
- `--build-stratio-image`: instead of downloading the _Stratio Cloud Provisioner_ image, builds it locally and uses it. This option is intended for development only.
- `--delete-previous`: removes the local cluster container when it already exists.
- `-d, --descriptor <string>`: allows indicating the name of the descriptor, in the current directory or in another. By default, `cluster.yaml`.
- `-h, --help`: shows the help for the command.
- `--keep-mgmt`: keeps the cluster management in kind (only in *non-production* environments).
- `--local-stratio-image-version <string>`: overrides the local version of the _Stratio Cloud Provisioner_ image when `--use-local-stratio-image` is used.
- `-n, --name <string>`: cluster name; overrides the `KIND_CLUSTER_NAME` variable. By default, `kind`.
- `--retain`: keeps the nodes to debug them when the creation of the cluster fails.
- `--use-local-stratio-image`: uses the local _Stratio Cloud Provisioner_ image, without building or downloading it.
- `--validate-only`: validates the descriptor without creating the cluster.
- `-p, --vault-password <string>`: sets the Vault password with which the secrets are encrypted.

=== Load balancer

Due to an error in different controllers (fixed in the main branch, but still without a published release), the load balancer created in GCP and Azure for the _API Server_ of clusters with an unmanaged _control-plane_ is configured with a TCP-based health check.

This may cause problems when any _control-plane_ node fails, because the load balancer sends requests to _control-plane_ nodes whose port responds, even when they cannot serve them.

To avoid it, modify the health check of the load balancer created so that it uses the HTTPS protocol and the `/readyz` path. Keep port 443 in GCP and 6443 in Azure.

=== Automatic labels in GKE

GKE automatically applies several labels to the cluster resources, such as Compute Engine virtual machine instances, persistent disks, and accelerators (TPU). For example:

- `goog-gke-node-pool-provisioning-model`: `on-demand`. Indicates the provisioning model of the node group (node pool).

NOTE: Depending on the case, the `goog-gke-node-pool-provisioning-model` label may need to be added manually to the descriptor when deploying the cluster to avoid reconciliation loops. You can also add it afterward by modifying the `KeosCluster` object. The nodes can be on-demand, reserved, or spot.

WARNING: These automatic labels may cause a reconciliation loop in the node pools in the `cluster-api-provider-gcp` controller (CAPG). For more details, see the xref:operations-manual:operations-manual.adoc#_reconciliation_loop_in_gke_due_to_automatic_labels[Troubleshooting] section of the operations manual.

Do not edit or remove these automatic labels, because GKE applies them again when recreating the nodes of the corresponding node pools.

TIP: For more information, see Google's official documentation at https://docs.cloud.google.com/kubernetes-engine/docs/how-to/creating-managing-labels[automatic labels that GKE applies].
