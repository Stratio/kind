= Version upgrade

== Description

The `upgrade-provisioner.py` script upgrades a cluster created with _Stratio Cloud Provisioner_ 0.7.x and Kubernetes 1.32 to version 0.9.x with Kubernetes 1.35. Each environment has its own step-by-step procedure:

* xref:operations-manual:upgrade/aws-eks.adoc[EKS] on AWS (managed).

This page brings together what is common to the three environments:

* The components that are updated and their versions.
* The common requirements.
* The script options.

To run the upgrade, follow the environment's procedure.

IMPORTANT: Before starting, read this page and the environment's procedure page completely. Some steps cannot be undone, and you make several decisions before launching the script. If there is any doubt, open a ticket with the Platform team before continuing.

IMPORTANT: Only version 1.32 clusters are supported. If the cluster is on an earlier version, first run the upgrade procedure until you reach the supported version.

The script and all its dependencies come in the `cloud-provisioner-upgrade:0.9.X` Docker image, so they do not need to be installed on the machine:

== Common requirements

These requirements are the same in the three environments. Each procedure adds its own in its requirements section.

* Technical:
** Have Docker installed on the system.
** Have a kubeconfig file with access to the cluster (located at `.kube/config`).
** Have the `secrets.yml` file (Ansible Vault) used to create the cluster, along with its Vault password. Pass the password as a mandatory argument (`-p`/`--vault-password`) when running the script inside the container; it has no default value.
** Have a local directory called `backup` for backups (mounted in the container at `/upgrade/backup`), created in the working directory from which the container is launched. Always use this same name across all clusters and clients so the location is predictable when providing support. The script manages its own subfolder structure within this directory: one per execution, with a timestamp and nested within an additional `upgrade/` level, so that the actual path of each copy is `/upgrade/backup/upgrade/<timestamp>/`. The directory does not need to be empty or recreated between executions; it only needs to exist as a mount point.
** Check that the container registry and the destination Helm repository contain the images and charts of Universe 15.1 (see <<_what_is_updated, what is updated>>). To see where the script downloads from, see <<_origin_of_charts_and_images, origin of charts and images>>.
+
IMPORTANT: The repository to be verified *is not necessarily the one that the cluster has configured today*. The script asks interactively whether to indicate a new one (see <<_interactive_prompts, interactive prompts>>); if you answer differently, that becomes the repository used for the entire upgrade, including the _cluster-operator_ chart. Verify the chart in the repository used for this execution.
+
When it is the turn of the _cluster-operator_ chart, the script downloads it (`helm pull`) from that repository to apply its CRDs (if the chart includes them). If the chart does not include CRDs, the script continues without issue; the upgrade stops at this step only if the download fails (chart or version not found in the repository, or invalid repository credentials).

* Functional:
+
Before running the upgrade, verify that the cluster meets the following conditions. If any is not met, *do not launch the upgrade* until it is resolved:
+
** `KeosCluster` ready:
+
[source,bash]
----
kubectl get keosclusters.installer.stratio.com -A
----
+
*Expected output:*
+
*** `READY = true`
*** `PHASE = Provisioned`

** Healthy nodes:
+
[source,bash]
----
kubectl get nodes
----
+
*Expected output:* all nodes with `STATUS = Ready`.

** Cluster API and _cluster-operator_ pods:
+
[source,bash]
----
kubectl get pods -n capi-system
kubectl get pods -n kube-system -l app.kubernetes.io/name=keoscluster-controller-manager
----
+
*Expected output:* all pods in `Running` state.

** Cluster API and _cluster-operator_ logs:
+
[source,bash]
----
kubectl logs -n capi-system -l cluster.x-k8s.io/provider=cluster-api --tail=-1 --since=1h | grep '^E'
kubectl logs -n kube-system -l app.kubernetes.io/name=keoscluster-controller-manager --tail=-1 --since=1h | grep -P '\tERROR\t'
----
+
*Expected output:* no errors. If any appear, review them before continuing.

** _HelmReleases_:
+
[source,bash]
----
kubectl get helmrelease -A
----
+
*Expected output:* all with `READY = True`.

** [[automatic_check]]Automatic check: on startup, before asking for confirmation, the script runs its own health check, independent of the previous ones:
+
--
* Verifies `KeosCluster.status.ready`.
* Verifies that no pod in the cluster is in `CrashLoopBackOff`, `ImagePullBackOff`, `ErrImagePull`, or `CreateContainerConfigError`, or in a phase other than `Running`, `Succeeded`, or `Pending`.
* Verifies that the Cluster API and provider controllers have 2 available replicas.
* Verifies that no `Machine` is outside the `Running`, `Provisioning`, `Pending`, or `ScalingUp` phases.
* *It does not directly check the state of the `HelmReleases`; only that of the pods, as an indirect indicator.* For this reason, the manual check above (`kubectl get helmrelease -A`) is still necessary; it is not redundant.
* If it finds any problem, *it aborts the upgrade before starting*, unless `--skip-preflight-checks` (assuming the risk) or `--dry-run` (which only reports that it would abort) is specified.
--

== Important notes

=== Use of the `--private` option

The `--private` option *forces* the use of private repositories for:

* Container images (`private_registry`).
* Helm charts (`private_helm_repo`).

Both are fields of `ClusterConfig.spec`. The script uses the private mode if the field is already `true` or if `--private` is passed; the option can only enable it, never disable it.

This implies that:

* If `ClusterConfig.spec.private_registry=true`, the script continues using the private registry even if `--private` *is not passed*.
* If `ClusterConfig.spec.private_helm_repo=true`, the script continues using the private Helm repository even if `--private` *is not passed*.
* *If `--private` is passed*, both values are forced to `true` during the upgrade and the `ClusterConfig` is updated with those values.

==== Common cases

[%header,cols="2,2,3"]
|===
| Current state in `ClusterConfig`
| Execution
| Result

| `private_registry=true` +
`private_helm_repo=true`
| Without `--private`
| The private registry and the private Helm repository continue to be used.

| `private_registry=false` +
`private_helm_repo=false`
| Without `--private`
| Public repositories are used.

| `private_registry=false` +
`private_helm_repo=false`
| With `--private`
| The private registry and private Helm repository are used, and `ClusterConfig` is updated to `true`.
|===

==== Origin of charts and images

* _cluster-operator_ chart: always from `KeosCluster.spec.helm_repository.url`.
* The rest of the charts: also from `KeosCluster.spec.helm_repository.url` if `ClusterConfig.spec.private_helm_repo` is `true` or if `--private` is passed. If not, from their public repository.
* Images: from the registry with `keos_registry: true` in `KeosCluster.spec.docker_registries` if `ClusterConfig.spec.private_registry` is `true` or if `--private` is passed. If not, it uses public registries.

TIP: Use `--private` only if private repositories are to be used and one of the two fields of `ClusterConfig` is `false`. If both are already `true`, the option changes nothing.

== Use of the upgrade script

[#upgrade_provisioner_sintaxis]

=== Syntax

Inside the container, run:

[source,bash]
----
python3 upgrade-provisioner.py -p <vault-password>
----

To see all the available options:

[source,bash]
----
python3 upgrade-provisioner.py --help
----

Main options:

[%header,cols="1,2,1,1"]
|===
| Option | Description | Default value | Mandatory

| `-p`, `--vault-password`
| Specifies the Vault password needed to decrypt the secrets.
|
| Yes

| `-k`, `--kubeconfig`
| Specifies the kubeconfig file that will be used. If the script is run inside the upgrade container, this option is ignored: the container sets the `KUBECONFIG=/upgrade/.kube/config` variable, and the script uses it instead of the value of `-k`. For this reason, the kubeconfig is mounted at that path.
| `~/.kube/config`
| No

| `-s`, `--secrets`
| Specifies the encrypted secrets file.
| `secrets.yml`
| No

| `-y`, `--yes`

| No

| `--cluster-operator`
| Target version of _cluster-operator_.
| The one included in this version of _Stratio Cloud Provisioner_.
| No

| `--disable-backup`
| Disables the pre-upgrade backup (enabled by default). It does not affect the copy of the `KeosCluster` webhooks, which the script needs to restore them.
| `False`
| No

| `--disable-prepare-capsule`
| Disables the temporary exclusion of the system namespaces (`kube-system`, `tigera-operator`, `calico-system`, `cert-manager`, `capi-system`, and so on) in the Capsule admission webhooks, so that they do not interfere with the chart upgrade. The exclusion is removed after that phase completes.
| `False`
| No

| `--private`
| Indicates that the Docker registry and the Helm repository are private. It is saved in the `ClusterConfig` (`private_registry`, `private_helm_repo`), so it persists after the execution (see the <<_use_of_the_private_option, use of the `--private` option>>).
| `False`
| No

| `--ecr-pull-through`
| Only for EKS. Moves the images of the charts to the ECR pull-through cache paths in this execution, even if the cache is not enabled in the `KeosCluster`. It only changes images already downloaded from the `KeosCluster` registry. The new paths are kept in the chart values. The `KeosCluster.spec.docker_registries[].ecr_pull_through_cache_enabled` field does not change: to enable it, use `ecr_pull_through.py`.
| `False`
| No

| `--skip-preflight-checks`
| Skips the pre-upgrade cluster health checks (see the <<automatic_check, automatic check>>). *Not recommended*: an unhealthy cluster can get worse after the upgrade (for example, a half-drained node or a CAPI controller stuck on 1 replica).
| `False`
| No

| `--k8s-version`
| Target Kubernetes minor version for the bump (for example, `1.35`). On AWS, it applies as a single patch to `KeosCluster.spec.k8s_version`; the script temporarily disables the `KeosCluster` webhooks, so the +1 minor-per-patch limit doesn't apply. On Azure VMs and on GKE, the script issues one patch per intermediate minor. This option still specifies the final minor, so its use does not change.
| `1.35`
| No

| `--node-image-map`
| *Mandatory on Azure VMs* for a `k8s_version` bump; it does not apply on AWS or on GCP. JSON with the VM image of each intermediate minor, for example, `{"1.33":"<id>","1.34":"<id>","1.35":"<id>"}`. Each value must be the ID of a managed image (`/subscriptions/.../providers/Microsoft.Compute/images/<name>`) or of a Community Gallery version (`/CommunityGalleries/.../images/.../versions/...`). Neither a Compute Gallery ID (`/subscriptions/.../galleries/...`) nor a loose name is accepted. The script validates the format, verifies that all minors are present, and aborts if they are not, even with `--dry-run`.
|
| Only Azure

| `--start-from-k8s-version`
| Skips the Y/N confirmation prior to the `k8s_version` bump (see the <<_interactive_prompts, interactive prompts>>). On AWS, the bump remains a single patch to `--k8s-version`; on Azure and GKE, it remains a sequence of minor-by-minor patches, not a resume mechanism from an intermediate step.
| `False`
| No

| `--control-plane-timeout`
| Minutes that the script waits, at most, for the _control-plane_ to reach each target minor: the EKS or GKE _control-plane_, or the `KubeadmControlPlane` on Azure VMs. It is an absolute limit per wait. Raise it if the cloud provider takes longer than usual to upgrade the _control-plane_. It must be a positive integer.
| `90`
| No

| `--node-convergence-timeout`
| Only applies on Azure VMs and GKE; on EKS the script does not wait for the worker nodes. Minutes that the worker-node upgrade can go *without progress* before the script stops. It is not a total limit: the deadline is reset each time an additional node (or, on GKE, an additional node pool) reaches the target version. This way, a cluster with many nodes or many groups doesn't use up the limit while the replacement continues; only a stopped replacement uses it up, for example, when a _Pod Disruption Budget_ prevents a node from being drained. Raise it only if replacing a single node can take longer than this value. It must be a positive integer.
| `90`
| No

| `--dry-run`
| Simulates the upgrade without applying real changes.
| `False`
| No

TIP: Always run with `--dry-run` first to detect obvious problems without risk, such as an invalid Vault password or cloud credentials, the version of `clusterctl`, and health-check problems, without aborting. It doesn't download any chart or check the registry, so it won't detect a missing chart or image. However, a clean `--dry-run` *does not guarantee* that the real upgrade will complete without issues: the mode simulates without running any command that modifies the cluster (`apply`, `patch`, `delete`, `scale`, `create`, `annotate`, `label`, `clusterctl upgrade apply`), so any failure that only manifests on applying those changes for real (a webhook that rejects a specific patch, a `HelmRelease` reconciliation that fails, a real `clusterctl upgrade apply`) remains untested.

=== Interactive prompts

The script may ask for up to three keyboard confirmations, in this order. In `--dry-run` it only asks the second one:

. *Continue with the upgrade*: at the start, after the pre-checks of the cluster. Press Enter to continue; to abort, enter any other text and press Enter. It is skipped with `-y`/`--yes`.
. *Helm repository*: right after. It shows the repository configured in `KeosCluster.spec.helm_repository.url` and lets you specify a new one. Press Enter to keep the current one. *It cannot be skipped*: it is always asked, even with `-y`.
. *`k8s_version` bump* (only if `KeosCluster.spec.k8s_version` is going to change): it appears when reaching the Kubernetes upgrade, when the charts and Cluster API are already updated. It asks for explicit `[y/N]` confirmation before applying the patch. The uppercase `N` indicates the default answer: if you press Enter without entering anything, the answer is "no". The answers do not distinguish between upper and lower case (`y`, `yes`, `n`, `no`). Answering `n` or leaving it blank cancels only this step (the rest of the upgrade continues). It is skipped with `--start-from-k8s-version`. On Azure VMs, the image map is validated before this question: if it is incorrect, the script aborts, even if `n` is answered.
+
To stop the upgrade at this point, answer `n`: the script restores the `KeosCluster` webhooks, starts its controller, resumes the `HelmRelease`, waits for the `KeosCluster` to be ready, returns _cluster-autoscaler_ to the replicas it had at the start, and ends, without changing the Kubernetes version. You can change the version later in another execution. *Do not use `Ctrl+C` on this question*: the script is inside the critical section, and its recovery is not run, so the `KeosCluster` webhooks would be left disabled and the `HelmRelease` would be left suspended.

WARNING: If a different Helm repository is indicated, the script saves it in `KeosCluster.spec.helm_repository.url` and in the `keos` `HelmRepository`, and uses it for the _cluster-operator_ chart and, if it is a private repository, for the rest of the charts. Change this value only if the new repository publishes the same Universe of versions (`kubernetes-universe`) that corresponds to this version of _Stratio Cloud Provisioner_; a repository from a different Universe may resolve versions of charts that are incompatible with each other.

== Overview of the upgrade process

This section summarizes, in order, the phases the script goes through when run. You don't need to run any of these steps; you only need to respond to the prompts (see the <<_interactive_prompts, interactive prompts>>).

. *Validation*
** Checks the version of `clusterctl` and that the secrets and the kubeconfig exist, and decrypts the secrets.
** Configures the cloud provider credentials and checks access to the cluster. On EKS and GKE, it regenerates the kubeconfig if it does not grant access.
** Runs the automatic health check (see the <<automatic_check, automatic check>>).
** Asks for the initial confirmation and the Helm repository (see the <<_interactive_prompts, interactive prompts>>).

. *Pre-upgrade*
** Scales _cluster-autoscaler_ to 0 to prevent automatic scaling during the upgrade, if it is deployed. On GKE, it is not.
** On EKS, applies the permissions of `aws-node` and _cluster-autoscaler_ that may be missing in clusters created with earlier versions.
+
NOTE: On updating its chart, _cluster-autoscaler_ returns to 2 replicas until the other charts finish. After that, the script scales it back to 0 and keeps it that way until the end.

. *Backup* (except with `--disable-backup`)
** CAPX components (through `clusterctl move`).
** Capsule webhook configurations.
** Secrets of the CAPX namespaces.

. *Capsule preparation*
** Temporarily excludes the system namespaces from the Capsule admission webhooks, so that they do not block the chart upgrade in the following step.

. *Chart upgrade*
** Updates the common charts (cert-manager, cluster-autoscaler, cluster-operator, flux2, and tigera-operator) and those of the provider: aws-load-balancer-controller on EKS, if it is installed, and azuredisk-csi-driver, azurefile-csi-driver, and cloud-provider-azure on Azure VMs (see <<_what_is_updated, what is updated>>). If any of these charts is not in the cluster, the script skips it; for example, aws-load-balancer-controller, which is optional on EKS, or _cluster-autoscaler_ if the cluster was created without it.
** On EKS, sets in _cluster-autoscaler_ the proprietary Stratio image `v1.35.2`, from `<registry>/autoscaling/cluster-autoscaler`.
** Keeps the override values (`ConfigMap` `02-<release>-helm-chart-override-values`) of each chart.
** After the charts complete, undoes the exclusion of the Capsule webhooks.
** Scales _cluster-autoscaler_ back to 0, if it is deployed.

. *_cluster-operator_ preparation*
** If the _cluster-operator_ `HelmRelease` was left suspended in a previous execution, it resumes it. After that, it waits up to 5 minutes for it to be ready.
** Suspends the _cluster-operator_ `HelmRelease`.
** Verifies that the `KeosCluster` is ready (`ready`) and in the `Provisioned` phase before entering the critical section.
** Stops the `keoscluster-controller-manager` deployment.
** Makes a backup of the configurations of the `KeosCluster` webhooks.
** Disables the validation and mutation webhooks of `KeosCluster`.
** Updates `ClusterConfig` with the new versions of the components.

. *CAPI upgrade*
+
[source,bash]
----
clusterctl upgrade apply \
  --core cluster-api:v1.10.10 \
  --infrastructure <provider>:<version> \
  --wait-providers
----
+
It is skipped if all the providers are already on their destination version. If cert-manager manages it with Helm, it removes the `clusterctl` label beforehand so it doesn't replace it. Afterward, it returns the CAPI and provider controllers to 2 replicas with `priorityClassName: system-node-critical`.
+
NOTE: On Azure VMs, the command additionally includes the `--bootstrap kubeadm:<version>` and `--control-plane kubeadm:<version>` parameters. EKS and GKE manage their own _control-plane_ and do not need to update these providers, but Azure VMs use `KubeadmControlPlane`, the kubeadm _control-plane_ provider of CAPI, which must be updated separately.

. *Kubernetes version upgrade*: each environment does it in a different way. See the "Before starting" section of the environment's procedure.

. *Post-upgrade*
** Restores the `KeosCluster` webhooks, starts `keoscluster-controller-manager` again, and resumes the _cluster-operator_ `HelmRelease`.
** Checks that the _control-plane_ is on the new Kubernetes version and that _cluster-operator_ is ready. On EKS, worker nodes don't change: the _MachineDeployment_ groups stay on version 1.32.
** Returns _cluster-autoscaler_ to the replicas it had at the start, or to 2 if it was on 0, if it is deployed.
** On EKS, if `spec.control_plane.aws.mp_role_name` is empty and the `eks-nodegroup.cluster-api-provider-aws.sigs.k8s.io` role exists, it waits for the `KeosCluster` to be ready and sets that role in the field. If it cannot, it shows a `[WARN]` with the command to fix it manually and ends anyway.

== Final verification

* Verify the images of the cluster pods:
+
[source,bash]
----
kubectl get pods -A -o json \
| jq -r '
  .items[]
  | (
      [.spec.containers[]?.image] +
      [.spec.initContainers[]?.image]
    )
  | .[]
' \
| sort -u
----
+
*Expected versions:* the images of the CAPI and provider controllers (`capi-controller-manager`, `capa-controller-manager`, `capz-controller-manager`, or `capg-controller-manager` and, on Azure VMs, the two kubeadm controllers) include the versions of the table of <<_what_is_updated, what is updated>>. A chart's version is not its image version; the chart is checked in the next step.

* Verify the chart versions:
+
[source,bash]
----
kubectl get hr -A -o json \
| jq -r '
  .items[]
  | "\(.metadata.namespace)/\(.metadata.name) -> \(.spec.chart.spec.chart)@\(.spec.chart.spec.version)"
' \
| sort -u
----
+
*Expected versions:* those of the table of <<_what_is_updated, what is updated>>. The script does not modify the cluster's other charts.

* Verify the final state:
+
[source,bash]
----
kubectl get keoscluster -A -o custom-columns=NAME:.metadata.name,K8S_VERSION:.spec.k8s_version,READY:.status.ready
kubectl get nodes -o custom-columns=NAME:.metadata.name,VERSION:.status.nodeInfo.kubeletVersion
kubectl logs -n capi-system -l cluster.x-k8s.io/provider=cluster-api --tail=-1 --since=1h | grep '^E'
kubectl logs -n kube-system -l app.kubernetes.io/name=keoscluster-controller-manager --tail=-1 --since=1h | grep -P '\tERROR\t'
----
+
*Expected output:* `K8S_VERSION` is the target version and `READY` is `true`. Review the logs for errors before considering the upgrade finished. Cluster API logs may show "Unauthorized" or "connection to the workload cluster is down" errors while the control plane changes version; they are only a problem if they keep appearing after the upgrade finishes. The "Post-upgrade checks" section of each environment's procedure lists the changes.
