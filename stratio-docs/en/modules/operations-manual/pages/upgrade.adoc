= Version upgrade

== Description

El _script_ `upgrade-provisioner.py` actualiza un _cluster_ creado con _Stratio Cloud Provisioner_ 0.7.x, con Kubernetes 1.32, a la versión 0.9.x, con Kubernetes 1.35. Cada entorno tiene su propio procedimiento paso a paso:

* xref:operations-manual:upgrade/aws-eks.adoc[EKS] en AWS (gestionado).

Esta página reúne lo que es común a los tres entornos:

* Los componentes que se actualizan y sus versiones.
* Los requisitos comunes.
* Las opciones del _script_.

Para ejecutar la actualización, sigue el procedimiento de tu entorno.

IMPORTANT: Antes de empezar, lee completas esta página y la del procedimiento de tu entorno. Algunos pasos no tienen vuelta atrás, y varias decisiones se toman antes de lanzar el _script_. Si tienes cualquier duda, abre un ticket al departamento de Platform antes de continuar.

IMPORTANT: Solo se admiten _clusters_ en la versión `1.32`. Si tu _cluster_ está en una versión anterior, debes realizar primero el procedimiento de actualización hasta alcanzar la versión admitida.

El _script_ y todas sus dependencias vienen en la imagen Docker `cloud-provisioner-upgrade:0.9.X`, así que no necesitas instalarlas en tu máquina:

[%header,cols="2,4,1"]
|===
| Herramienta | Descripción | Entorno

| Python 3 | Intérprete que ejecuta los _scripts_ de actualización. | Todos
| `kubectl` | Cliente de línea de comandos para consultar y modificar el _cluster_. | Todos
| `helm` | Cliente de Helm para consultar y descargar _charts_. | Todos
| `clusterctl` | Cliente de Cluster API para actualizar sus proveedores y copiar sus objetos. | Todos
| `jq` y `yq` | Procesadores de JSON y YAML de línea de comandos. | Todos
| AWS CLI v2 | Cliente de línea de comandos para consultar los servicios de AWS. | EKS
| `clusterawsadm` | Cliente de CAPA para gestionar el _stack_ de IAM en AWS. | EKS
| Azure CLI | Cliente de línea de comandos para consultar los servicios de Azure. | Azure VMs
| Google Cloud SDK y `gke-gcloud-auth-plugin` | Cliente de línea de comandos de Google Cloud y _plugin_ de autenticación de GKE para `kubectl`. | GKE
|===

== Requisitos comunes

Estos requisitos son los mismos en los tres entornos. Cada procedimiento añade los suyos en su apartado de requisitos.

* Technical:
** Have Docker installed on the system.
** Have a kubeconfig file with access to the cluster (located at `.kube/config`).
** Have the _secrets.yml_ file (Ansible Vault) used to create the cluster, along with its Vault password. The password is a mandatory argument (`-p`/`--vault-password`) when running the script inside the container; it has no default value.
** Tener un directorio local llamado `backup` para copias de seguridad (se montará en el contenedor en `/upgrade/backup`), creado en el directorio de trabajo desde el que lanzas el contenedor. Usa siempre este mismo nombre en todos los _clusters_/clientes, para que la ubicación sea predecible al dar soporte. El _script_ gestiona su propia estructura de subcarpetas dentro de este directorio: una por ejecución, con marca de tiempo y anidada dentro de un nivel `upgrade/` adicional, de modo que la ruta real de cada copia es `/upgrade/backup/upgrade/<marca_de_tiempo>/`. No es necesario que el directorio esté vacío ni recrearlo entre ejecuciones; basta con que exista como punto de montaje.
** Comprobar que el registro de contenedores y el repositorio de Helm de destino contienen las imágenes y los _charts_ del Universo 15.1 (ver <<_qué_se_actualiza, qué se actualiza>>). Para saber de dónde los descarga el _script_, consulta <<_origin_of_charts_and_images, origen de _charts_ e imágenes>>.
+
IMPORTANT: El repositorio a verificar *no es necesariamente el que el _cluster_ tiene configurado hoy*. El _script_ pregunta interactivamente si quieres indicar uno nuevo (ver <<_interactive_prompts, _prompts_ interactivos>>); si respondes con uno distinto, ese pasa a ser el repositorio real utilizado durante toda la actualización, incluido el _chart_ de _cluster-operator_. Verifica el _chart_ en el repositorio que realmente vayas a usar en esta ejecución.
+
Cuando llega el turno del _chart_ de _cluster-operator_, el _script_ lo descarga (`helm pull`) desde ese repositorio para aplicar sus CRD (si el _chart_ las incluye). Si el _chart_ no incluye CRD, el _script_ continúa sin problema; lo que detiene la actualización en este paso es que la descarga falle (_chart_ o versión no encontrados en el repositorio, o credenciales del repositorio no válidas).

* Functional:
+
Antes de ejecutar la actualización, verifica que el _cluster_ cumpla las siguientes condiciones. Si alguna no se cumple, *no lances la actualización* hasta resolverla:
+
** _KeosCluster_ ready:
+
[source,bash]
----
kubectl get keosclusters.installer.stratio.com -A
----
+
*Expected output:*
+
*** `READY = true`
*** `PHASE = Provisioned`

** Healthy nodes:
+
[source,bash]
----
kubectl get nodes
----
+
*Expected output:* all nodes with `STATUS = Ready`.

** _Pods_ de _Cluster API_ y de _cluster-operator_:
+
[source,bash]
----
kubectl get pods -n capi-system
kubectl get pods -n kube-system -l app.kubernetes.io/name=keoscluster-controller-manager
----
+
*Salida esperada:* todos los _pods_ en estado `Running`.

** _Logs_ de _Cluster API_ y de _cluster-operator_:
+
[source,bash]
----
kubectl logs -n capi-system -l cluster.x-k8s.io/provider=cluster-api --tail=-1 --since=1h | grep '^E'
kubectl logs -n kube-system -l app.kubernetes.io/name=keoscluster-controller-manager --tail=-1 --since=1h | grep -P '\tERROR\t'
----
+
*Salida esperada:* ningún error. Si aparece alguno, revísalo antes de continuar.

** _HelmReleases_:
+
[source,bash]
----
kubectl get helmrelease -A
----
+
*Expected output:* all with `READY = True`.

** [[comprobación_automática]]Comprobación automática: al arrancar, antes de pedir confirmación, el _script_ ejecuta su propio chequeo de salud, independiente de los anteriores:
+
--
* Verifica `KeosCluster.status.ready`.
* Verifica que ningún _pod_ del _cluster_ esté en `CrashLoopBackOff`, `ImagePullBackOff`, `ErrImagePull` o `CreateContainerConfigError`, ni en una fase distinta de `Running`, `Succeeded` o `Pending`.
* Verifica que los _controllers_ de Cluster API y del proveedor tengan 2 réplicas disponibles.
* Verifica que ninguna `Machine` esté fuera de las fases `Running`, `Provisioning`, `Pending` o `ScalingUp`.
* *It does not check the state of the `HelmRelease` directly; only that of the pods as an indirect indicator.* That is why the manual check above (`kubectl get helmrelease -A`) is still necessary; it is not redundant.
* If it finds any problem, it *aborts the upgrade before starting*, unless `--skip-preflight-checks` is indicated (assuming the risk) or `--dry-run` (which only reports that it would abort).
--

== Important notes

=== Use of the `--private` flag

The `--private` flag *forces* the use of private repositories for:

* Container images (`private_registry`).
* Helm charts (`private_helm_repo`).

Ambos son campos de `ClusterConfig.spec`. El _script_ usa el modo privado si el campo ya es `true` o si pasas `--private`: el _flag_ solo puede activarlo, nunca lo desactiva.

This implies that:

* If `ClusterConfig.spec.private_registry=true`, the script will continue to use the private registry even if `--private` is *not passed*.
* If `ClusterConfig.spec.private_helm_repo=true`, the script will continue to use the private Helm repository even if `--private` is *not passed*.
* *If* `--private` *is passed*, both values are forced to `true` during the upgrade and the `ClusterConfig` is updated with those values.

==== Common cases

[%header,cols="2,2,3"]
|===
| Current state in `ClusterConfig`
| Execution
| Result

| `private_registry=true` +
`private_helm_repo=true`
| without `--private`
| Se siguen usando el registro privado y el repositorio privado de Helm.

| `private_registry=false` +
`private_helm_repo=false`
| without `--private`
| Public repositories will be used.

| `private_registry=false` +
`private_helm_repo=false`
| with `--private`
| The private registry and private Helm repository are forced, and `ClusterConfig` is left updated to `true`.
|===

==== Origin of charts and images

* _Chart_ de _cluster-operator_: siempre de `KeosCluster.spec.helm_repository.url`.
* El resto de _charts_: también de `KeosCluster.spec.helm_repository.url` si `ClusterConfig.spec.private_helm_repo` es `true` o si pasas `--private`. Si no, de su repositorio público.
* Imágenes: del registro con `keos_registry: true` en `KeosCluster.spec.docker_registries` si `ClusterConfig.spec.private_registry` es `true` o si pasas `--private`. Si no, de sus registros públicos.

TIP: Pasa `--private` solo si quieres usar repositorios privados y alguno de los dos campos de `ClusterConfig` está en `false`. Si los dos ya están en `true`, el _flag_ no cambia nada.

TIP: Ejecuta siempre primero con `--dry-run` antes de la actualización real, para detectar problemas obvios sin riesgo: contraseña de Vault o credenciales _cloud_ inválidas, versión de `clusterctl` y los problemas del chequeo de salud, que se listan sin abortar. No descarga ningún _chart_ ni comprueba el registro, así que no detecta un _chart_ o una imagen que falten. Sin embargo, un `--dry-run` limpio *no es garantía* de que la actualización real vaya a completarse sin problemas: el modo simula sin ejecutar ningún comando que modifique el _cluster_ (`apply`, `patch`, `delete`, `scale`, `create`, `annotate`, `label`, `clusterctl upgrade apply`), así que cualquier fallo que solo se manifieste al aplicar esos cambios de verdad (un _webhook_ rechazando un _patch_ concreto, una reconciliación de `HelmRelease` que falla, un `clusterctl upgrade apply` real) queda sin probar.

=== Interactive prompts

El _script_ puede pedir hasta tres confirmaciones por teclado, en este orden. En `--dry-run` solo pide la segunda:

. *Continuar con la actualización*: al inicio, tras las comprobaciones previas del _cluster_. Pulsa ENTER para continuar; para abortar, escribe cualquier otro texto y pulsa ENTER. Se omite con `-y`/`--yes`.
. *Repositorio de Helm*: justo después. Muestra el repositorio configurado en `KeosCluster.spec.helm_repository.url` y permite indicar uno nuevo. Pulsa ENTER para mantener el actual. *No se puede omitir*: se pregunta siempre, incluso con `-y`.
. *Bump de `k8s_version`* (solo si `KeosCluster.spec.k8s_version` va a cambiar): aparece al llegar a la actualización de Kubernetes, cuando los _charts_ y Cluster API ya están actualizados. Pide confirmación explícita `[y/N]` antes de aplicar el _patch_. La `N` en mayúscula indica la respuesta por defecto: si pulsas ENTER sin escribir nada, la respuesta es "no". Las respuestas no distinguen entre mayúsculas y minúsculas (`y`, `yes`, `n`, `no`). Responder "n" o dejarlo en blanco cancela solo este paso (el resto de la actualización continúa). Se omite con `--start-from-k8s-version`. En Azure VMs, el mapa de imágenes se valida antes de esta pregunta: si es incorrecto, el _script_ aborta aunque vayas a responder "n".
+
Para detener la actualización en este punto, responde "n": el _script_ restaura los _webhooks_ de `KeosCluster`, arranca su _controller_, reanuda el `HelmRelease`, espera a que el `KeosCluster` esté listo, devuelve _cluster-autoscaler_ a las réplicas que tenía al empezar y termina, sin cambiar la versión de Kubernetes. Puedes hacer el cambio de versión más tarde con otra ejecución. *No uses Ctrl+C en esta pregunta*: el _script_ está dentro de la sección crítica y su recuperación no se ejecuta, así que los _webhooks_ de `KeosCluster` quedarían desactivados y el `HelmRelease` suspendido.

WARNING: Si indicas un repositorio de Helm distinto, el _script_ lo guarda en `KeosCluster.spec.helm_repository.url` y en el `HelmRepository` `keos`, y lo usa para el _chart_ de _cluster-operator_ y, con repositorio privado, para el resto de _charts_. Cambia este valor únicamente si el nuevo repositorio publica el mismo universo de versiones (`kubernetes-universe`) que corresponde a esta versión de _Stratio Cloud Provisioner_; un repositorio de un universo distinto puede resolver versiones de _charts_ incompatibles entre sí.

== General description of the upgrade process

Esta sección resume, en orden, las fases por las que pasa el _script_ una vez que lo lanzas. No tienes que ejecutar ninguno de estos pasos: solo responder a los _prompts_ (ver <<_interactive_prompts, _prompts_ interactivos>>).

. *Validation*
** Comprueba la versión de `clusterctl`, que existan los secretos y el _kubeconfig_, y descifra los secretos.
** Configura las credenciales del proveedor _cloud_ y comprueba el acceso al _cluster_. En EKS y GKE regenera el _kubeconfig_ si no da acceso.
** Ejecuta la comprobación automática de salud (ver <<comprobación_automática, comprobación automática>>).
** Pide la confirmación inicial y el repositorio de Helm (ver <<_interactive_prompts, _prompts_ interactivos>>).

. *Pre-upgrade*
** Escala _cluster-autoscaler_ a 0 para evitar el escalado automático durante la actualización, si está desplegado. En GKE no lo está.
** En EKS, aplica los permisos de `aws-node` y de _cluster-autoscaler_ que pueden faltar en los _clusters_ creados con versiones anteriores.
+
NOTE: Al actualizar su _chart_, _cluster-autoscaler_ vuelve a 2 réplicas hasta que terminan los demás _charts_. Después, el _script_ lo escala otra vez a 0 y lo mantiene así hasta el final.

. *Copia de seguridad* (salvo con `--disable-backup`)
** CAPX components (via `clusterctl move`).
** Capsule webhook configurations.
** Secrets of the CAPX namespaces.

. *Capsule preparation*
** Excluye temporalmente los _namespaces_ de sistema de los _webhooks_ de admisión de Capsule, para que no bloqueen la actualización de los _charts_ del paso siguiente.

. *Chart upgrade*
** Actualiza los _charts_ comunes (cert-manager, cluster-autoscaler, cluster-operator, flux2 y tigera-operator) y los del proveedor: aws-load-balancer-controller en EKS, si está instalado, y azuredisk-csi-driver, azurefile-csi-driver y cloud-provider-azure en Azure VMs (ver <<_qué_se_actualiza, qué se actualiza>>). Si alguno de estos _charts_ no está en el _cluster_, el _script_ lo omite; por ejemplo, aws-load-balancer-controller, que es opcional en EKS, o _cluster-autoscaler_ si el _cluster_ se creó sin él.
** En EKS, fija en _cluster-autoscaler_ la imagen propia de Stratio `v1.35.2`, desde `<registro>/autoscaling/cluster-autoscaler`.
** Conserva los valores de _override_ (`ConfigMap` `02-<release>-helm-chart-override-values`) de cada _chart_.
** Al terminar los _charts_, deshace la exclusión de los _webhooks_ de Capsule.
** Vuelve a escalar _cluster-autoscaler_ a 0, si está desplegado.

. *Preparación de _cluster-operator_*
** Si el `HelmRelease` de _cluster-operator_ quedó suspendido en una ejecución anterior, lo reanuda. Después espera hasta 5 minutos a que esté listo.
** Suspende el `HelmRelease` de _cluster-operator_.
** Verifies that `KeosCluster` is _ready_/`Provisioned` before entering the critical section.
** Detiene el _deployment_ `keoscluster-controller-manager`.
** Backs up the configuration of the `KeosCluster` webhooks.
** Desactiva los _webhooks_ de validación y mutación de `KeosCluster`.
** Updates _ClusterConfig_ with the new versions of the components.

. *CAPI upgrade*
+
[source,bash]
----
clusterctl upgrade apply \
  --core cluster-api:v1.10.10 \
  --infrastructure <provider>:<version> \
  --wait-providers
----
+
Se omite si todos los _providers_ ya están en su versión de destino. Antes, si cert-manager lo gestiona Helm, le quita la etiqueta de `clusterctl` para que este no lo sustituya. Después, devuelve los _controllers_ de CAPI y del _provider_ a 2 réplicas con `priorityClassName: system-node-critical`.
+
NOTE: En las VMs de Azure, el comando incluye además los parámetros `--bootstrap kubeadm:<versión>` y `--control-plane kubeadm:<versión>`. EKS y GKE gestionan su propio _control-plane_ y no necesitan actualizar estos _providers_, pero Azure VMs usa `KubeadmControlPlane`, del _provider_ de _control-plane_ kubeadm de CAPI, que hay que actualizar aparte.

. *Actualización de la versión de Kubernetes*: cada entorno la hace de forma distinta. Consulta el apartado «Antes de empezar» del procedimiento de tu entorno.

. *Post-upgrade*
** Restaura los _webhooks_ de `KeosCluster`, vuelve a arrancar `keoscluster-controller-manager` y reanuda el `HelmRelease` de _cluster-operator_.
** Comprueba que el _control-plane_ está en la nueva versión de Kubernetes y que _cluster-operator_ está listo. En EKS, los nodos de trabajo no cambian: los grupos _MachineDeployment_ se quedan en 1.32.
** Devuelve _cluster-autoscaler_ a las réplicas que tenía al empezar, o a 2 si estaba en 0, si está desplegado.
** En EKS, si `spec.control_plane.aws.mp_role_name` está vacío y existe el _role_ `eks-nodegroup.cluster-api-provider-aws.sigs.k8s.io`, espera a que el `KeosCluster` esté listo y fija ese _role_ en el campo. Si no puede, muestra un `[WARN]` con el comando para fijarlo a mano y termina igualmente.

== Final verification

* Verificar las imágenes de los _pods_ del _cluster_.
+
[source,bash]
----
kubectl get pods -A -o json \
| jq -r '
  .items[]
  | (
      [.spec.containers[]?.image] +
      [.spec.initContainers[]?.image]
    )
  | .[]
' \
| sort -u
----
+
*Versiones esperadas:* las imágenes de los _controllers_ de CAPI y del proveedor (`capi-controller-manager`, `capa-controller-manager`, `capz-controller-manager` o `capg-controller-manager` y, en Azure VMs, los dos _controllers_ de kubeadm) llevan las versiones de la tabla de <<_qué_se_actualiza, qué se actualiza>>. La versión de un _chart_ no es la de sus imágenes: los _charts_ se comprueban en el paso siguiente.

* Verify chart versions.
+
[source,bash]
----
kubectl get hr -A -o json \
| jq -r '
  .items[]
  | "\(.metadata.namespace)/\(.metadata.name) -> \(.spec.chart.spec.chart)@\(.spec.chart.spec.version)"
' \
| sort -u
----
+
*Versiones esperadas:* las de la tabla de <<_qué_se_actualiza, qué se actualiza>>. El _script_ no cambia los demás _charts_ del _cluster_.

* Verification of the final state.
+
[source,bash]
----
kubectl get keoscluster -A -o custom-columns=NAME:.metadata.name,K8S_VERSION:.spec.k8s_version,READY:.status.ready
kubectl get nodes -o custom-columns=NAME:.metadata.name,VERSION:.status.nodeInfo.kubeletVersion
kubectl logs -n capi-system -l cluster.x-k8s.io/provider=cluster-api --tail=-1 --since=1h | grep '^E'
kubectl logs -n kube-system -l app.kubernetes.io/name=keoscluster-controller-manager --tail=-1 --since=1h | grep -P '\tERROR\t'
