= Version upgrade

== Description

The `upgrade-provisioner.py` script automates the upgrade of Kubernetes clusters in the following environments:

* *EKS* on AWS (managed)
* *Azure VMs* (unmanaged)
* *GKE* on GCP (managed)

It upgrades the Kubernetes version of the cluster from the one installed with `cloud-provisioner 0.9.X` to the one provided by `cloud-provisioner 0.10.X`: 1.37 on EKS and Azure VMs, and 1.36 on GKE.

IMPORTANT: Only clusters on version `1.35` whose Cluster API providers are already migrated to `v1beta2` with <<upgrade_providers, `upgrade-providers.py`>> are supported. The _script_ checks it when it starts, before changing anything. It requires the Cluster API core on v1.13.0 or later and each provider exactly on its target version. If not, it stops.

NOTE: On GKE, the target is 1.36 because Google only offers 1.37 in the `RAPID` _release channel_, which _Stratio Cloud Provisioner_ doesn't support. Check it with:

[source,bash]
----
gcloud container get-server-config --zone=<zone> --format=json | jq -c '[.channels[]|{c:.channel, v137:[.validVersions[]|select(startswith("1.37"))]}]'
----

To guarantee a reproducible execution environment, the `cloud-provisioner-upgrade:0.10.X` Docker image has been created. It includes the upgrade _script_ and all the required dependencies (Python 3, AWS CLI v2, Azure CLI, Google Cloud SDK, `kubectl`, `helm`, and `clusterctl`, among others). The full download path depends on where it's published: in the ECR/ACR/GAR private registry or in the Stratio Nexus for internal work. See <<_execution_of_the_upgrade_container, execution of the upgrade container>>.

=== What is upgraded

* *Common components* for all platforms:
** _cluster-operator_: `0.8.0`
** _cert-manager_: `v1.21.2`
** _flux2_: `2.18.4`
** _tigera-operator_: `v3.33.0`
** _cluster-autoscaler_: `9.59.0`

* Platform-specific *_charts_*:
** EKS (if installed):
*** _aws-load-balancer-controller_: `3.4.3`
** Azure VMs:
*** _azuredisk-csi-driver_: `1.36.0`
*** _azurefile-csi-driver_: `1.35.7`
*** _cloud-provider-azure_: `1.36.0`

* *Kubernetes version*: 1.37 on EKS and Azure VMs, and 1.36 on GKE.

This _script_ doesn't upgrade Cluster API or its providers: `upgrade-providers.py` does it beforehand and leaves them on the versions in the xref:operations-manual:upgrade-overview/from-0-9-x-to-0-10-x.adoc#components[route sheet].

NOTE: In `cloud-provider-azure`, the _script_ also pins the image _tag_ of `cloudControllerManager`/`cloudNodeManager` to a known, published version, because the _chart_ itself can reference a _tag_ that isn't published yet for some _minors_. When it upgrades the _chart_, it uses the one for the cluster's current _minor_. When the `k8s_version` _bump_ ends, it switches it to the one for the target _minor_: `v1.37.0` for 1.37. If a _minor_ isn't in the _script_'s internal table, it warns and leaves the _chart_ default values as they are.

== Requirements

* Technical:
** Have Docker installed on the system.
** Have a kubeconfig file with access to the cluster (located at `.kube/config`).
** Have the _secrets.yml_ file (Ansible Vault) used to create the cluster, along with its Vault password. The password is a mandatory argument (`-p`/`--vault-password`) when running the script inside the container; it has no default value.
** Have valid AWS credentials for the cluster (`~/.aws/config` and `~/.aws/credentials`). The container sets the variables `AWS_CONFIG_FILE=/upgrade/.aws/config` and `AWS_SHARED_CREDENTIALS_FILE=/upgrade/.aws/credentials`, so the `.aws` directory must be mounted in the container; otherwise, any call from the script to the AWS API will fail.
+
NOTE: At startup, the script validates connectivity (`kubectl get ns`) and, if it fails, automatically regenerates the kubeconfig for EKS/GKE (not for Azure). This corrects an outdated kubeconfig, but not an expired AWS credential.

** Have a local directory called `backup` for backups (it will be mounted in the container at `/upgrade/backup`), created inside the same working directory as the rest of the structure (see <<_required_structure, required structure>>). Always use the same name across all clusters/customers so the location is predictable when providing support. The script manages its own subfolder structure inside this directory: one per execution, with a timestamp and nested inside an additional `upgrade/` level, so that the actual path of each backup is `/upgrade/backup/upgrade/<timestamp>/`. The directory does not need to be empty or recreated between executions; it just needs to exist as a mount point.
** Check that the *target* Helm repository already publishes the _cluster-operator_ chart in the target version. _Cluster-operator_ always resolves its chart from `KeosCluster.spec.helm_repository.url` (unlike the rest of the components, whose origin does depend on `ClusterConfig.spec.private_helm_repo`; see <<_use_of_the_private_flag, use of the `--private` flag>>).
+
IMPORTANT: The repository to verify *is not necessarily the one the cluster has configured today*. The script interactively asks whether you want to indicate a new one (see <<_interactive_prompts, interactive prompts>>); if you respond with a different one, that becomes the actual repository used throughout the entire upgrade, including the _cluster-operator_ chart. Verify the chart in the repository that you are actually going to use in this execution, not just in the one that appears with the following command:
+
[source,bash]
----
kubectl get keoscluster -n cluster-<cluster-name> <cluster-name> -o jsonpath='{.spec.helm_repository.url}'
----
+
The script downloads (`helm pull`) the _cluster-operator_ chart from that URL to apply its CRDs (if the chart includes them) before upgrading the rest of the components. If the chart does not include CRDs, the script continues without issue; the only thing that stops the upgrade at this step is `helm pull` failing (chart or version not found in the repository).

* Functional:
+
Before executing the upgrade, verify that the cluster meets the following conditions depending on each platform:
+
** _KeosCluster_ ready:
+
[source,bash]
----
kubectl get keosclusters.installer.stratio.com -A
----
+
*Expected output:*
+
*** `READY = true`
*** `PHASE = Provisioned`
+
NOTE: On GKE, if `READY` is not `true` and some `MachinePool` remains in `ScalingUp`, check whether CAPG is in a reconciliation loop due to the GKE automatic labels: the `capg-controller-manager` logs repeat the "Node pool config update required" message. See xref:operations-manual:operations-manual.adoc#_reconciliation_loop_in_gke_due_to_automatic_labels[Reconciliation loop on GKE due to automatic labels].

** Healthy nodes:
+
[source,bash]
----
kubectl get nodes
----
+
*Expected output:* all nodes with `STATUS = Ready`.

** Running machines:
+
[source,bash]
----
kubectl get machines -A
----
+
*Expected output:* all with `PHASE = Running`.

** _MachineDeployments_:
+
[source,bash]
----
kubectl get machinedeployments -A
----
+
*Expected output:*
+
*** `READY = REPLICAS`
*** `UNAVAILABLE = 0`
*** On GKE, the list always comes out empty: all worker groups are _MachinePool_.

** _MachinePools_:
+
[source,bash]
----
kubectl get machinepools -A
----
+
*Expected output:* all with `PHASE = Running`.

** _Cluster API_ and provider pods:
+
[source,bash]
----
kubectl get pods -n capi-system
kubectl get pods -n capa-system
kubectl get pods -n capg-system
kubectl get pods -n capz-system
----
+
*Expected output:* all pods in `Running` state and without errors in the logs.

** _HelmReleases_:
+
[source,bash]
----
kubectl get helmrelease -A
----
+
*Expected output:* all with `READY = True`.

** [[comprobación_automática]] The script executes its own health check at startup (before touching anything), independent of the previous ones:
+
--
* Verifies `KeosCluster.status.ready`, the health of the pods of the entire cluster (`CrashLoopBackOff`/`ImagePullBackOff`/`ErrImagePull`/`CreateContainerConfigError`), the HA replicas of `capi`/`capa`/`capg`/`capz` (must be 2), and `Machine` stuck outside their normal phases.
* On Azure VMs, it also checks that the `ClusterRoleBinding kubeadm:apiserver-kubelet-client` exists. If missing, it creates it automatically, without manual intervention; its absence can leave a `k8s_version` bump hanging indefinitely if the etcd health check in CAPI fails.
* *It does not check the state of the `HelmRelease` directly; only that of the pods as an indirect indicator.* That is why the manual check above (`kubectl get helmrelease -A`) is still necessary; it is not redundant.
* If it finds any problem, it *aborts the upgrade before starting*, unless `--skip-preflight-checks` is indicated (assuming the risk) or `--dry-run` (which only reports that it would abort).
* On GKE, the pod check includes the addons managed by Google, such as `event-exporter-gke` or `konnectivity-agent`. If any of them fail, the script aborts even though it is not part of _Stratio KEOS_. Before using `--skip-preflight-checks`, which omits all the checks, identify whose pod it is: if its image comes from `gke-release`, it is a Google component.
--

== Preparation

Go to the working directory from which you will run the container. Normally, this is the same workspace where you installed the cluster and `keos-installer`, since it likely already contains several necessary files (see <<_required_structure, required structure>>); if not, use a specific directory.

Create a local directory for backups:

[source,bash]
----
mkdir -p $PWD/backup
----

NOTE: This directory must be mounted inside the container at `/upgrade/backup`.

== Required structure

Make sure that the working directory includes the following elements. Only what is mounted from the host is needed here; the main script, the Jinja2 templates, and the dependencies are already in the image, so you do not need them here.

* `secrets.yml`: cluster credentials.
* `.kube/config`: kubeconfig file of the cluster.
* `backup/`: directory for backups (can be empty at the start).
* `.aws/` (AWS only): directory containing `config` and `credentials`. Without it, any call from the script to the AWS API fails (see <<_execution_of_the_upgrade_container, execution of the upgrade container>>).

== Important notes

=== Use of the `--private` flag

The `--private` flag *forces* the use of private repositories for:

* Container images (`private_registry`).
* Helm charts (`private_helm_repo`).

Both are fields of `ClusterConfig.spec`, which can be consulted with:

[source,bash]
----
kubectl get clusterconfig -n cluster-<cluster-name> <cluster-name> -o jsonpath='{.spec.private_registry}{"\n"}{.spec.private_helm_repo}{"\n"}'
----

The final behavior of the script does not depend only on the flag, but also on the values already defined in `ClusterConfig`.

This implies that:

* If `ClusterConfig.spec.private_registry=true`, the script will continue to use the private registry even if `--private` is *not passed*.
* If `ClusterConfig.spec.private_helm_repo=true`, the script will continue to use the private Helm repository even if `--private` is *not passed*.
* *If* `--private` *is passed*, both values are forced to `true` during the upgrade and the `ClusterConfig` is updated with those values.

==== Common cases

[%header,cols="2,2,3"]
|===
| Current state in `ClusterConfig`
| Execution
| Result

| `private_registry=true` +
`private_helm_repo=true`
| without `--private`
| The private Helm registry in private repositories will continue to be used.

| `private_registry=false` +
`private_helm_repo=false`
| without `--private`
| Public repositories will be used.

| `private_registry=false` +
`private_helm_repo=false`
| with `--private`
| The private registry and private Helm repository are forced, and `ClusterConfig` is left updated to `true`.
|===

==== Origin of charts and images

* When `private_helm_repo=true`, the charts are resolved from `KeosCluster.spec.helm_repository.url`.
* When `private_registry=true`, the Cluster API images are resolved from the registry marked with `keos_registry=true` in `KeosCluster.spec.docker_registries`.

WARNING: The `--private` flag is only necessary if you want to *force the use of private repositories* and the current `ClusterConfig` does not have it enabled anymore.

== Execution of the upgrade container

This step is common to `ecr_pull_through.py` and `upgrade-provisioner.py` (see <<_migration_to_ecr_pull_through_cache, migration to ECR pull-through cache>> and <<upgrade_provisioner_sintaxis, syntax of `upgrade-provisioner.py`>> respectively). `upgrade-providers.py` uses the same image with different mounts (see <<upgrade_providers, migration of the providers to Cluster API v1beta2>>).

Download the image:

[source,bash]
----
docker pull <registry>/cloud-provisioner-upgrade:0.10.X
----

Start the container:

[source,bash]
----
docker run \
  --name cloud-provisioner-upgrade-0.10.X \
  --net host \
  -it \
  -v $PWD/secrets.yml:/upgrade/secrets.yml \
  -v $PWD/.kube/config:/upgrade/.kube/config \
  -v ~/.aws:/upgrade/.aws \
  -v $PWD/backup:/upgrade/backup \
  <registry>/cloud-provisioner-upgrade:0.10.X
----

Inside the container, execute the corresponding script with the appropriate flags. See <<_migration_to_ecr_pull_through_cache, migration to ECR pull-through cache>> or <<upgrade_provisioner_sintaxis, syntax of `upgrade-provisioner.py`>>, as appropriate.

NOTE: The mount `-v ~/.aws:/upgrade/.aws` is *not necessary on Azure or on GCP*: both scripts obtain the credentials from `secrets.yml` itself and configure them themselves (`az login --service-principal` for Azure, `configure_gcp_credentials()` for GCP) before the first call to the provider's CLI, without ever reading that directory. Omit it for those two providers.

NOTE: On GKE, the script rewrites the mounted kubeconfig at startup: it replaces the static credential with one that uses `gke-gcloud-auth-plugin` and obtains a new token on each call. Therefore, don't mount the file read-only (`:ro`), since the script needs to write to it. After execution, to use that kubeconfig from the host machine, you need to have `gcloud` and `gke-gcloud-auth-plugin` installed and authenticated. If you want to keep the original, copy it before launching the container.

NOTE: The container uses the host machine's network (`--net host`). On a GKE cluster with a private endpoint, launch it from a machine that can access that endpoint, for example, from within the cluster's VPC. That machine also needs access to the Google APIs because the script calls `gcloud`.

NOTE: Neither script generates its own timestamped log file; all output goes to the container console. To keep a complete log of the execution, redirect the output to a file, for example, by adding `2>&1 | tee upgrade-$(date +%Y%m%d-%H%M%S).log` to the previous command.

== Migration to ECR pull-through cache

WARNING: This procedure applies only to EKS clusters (managed by AWS). It is not available for Azure VMs or for GKE.

The `ecr_pull_through.py` script upgrades `cluster-operator` to the indicated version and activates `docker_registries[].ecr_pull_through_cache_enabled` in the `KeosCluster`, so that the components start resolving their images through the Amazon ECR pull-through cache rules instead of their direct paths.

NOTE: This action is independent of the rest of the upgrade. It is usually executed before `upgrade-provisioner.py`, within the same upgrade cycle, when you want to activate the pull-through cache when moving up in version.

Before applying any change, the script automatically saves a copy of the previous state (the CRDs `keosclusters.installer.stratio.com`/`clusterconfigs.installer.stratio.com`, the `ConfigMap` of _cluster-operator_ values, and a `state.json` with the previous version and URLs) in `backup/ecr_pull_through/<timestamp>/`. This copy is the one used by the `--restore` flag (see <<_recovery_from_failures, recovery from failures of `ecr_pull_through.py`>>) to undo the operation.

IMPORTANT: This backup mechanism and the `--restore` flag are exclusive to `ecr_pull_through.py`. `upgrade-provisioner.py` makes different backups: manifests of `clusterctl move`, `capsule` webhooks, and secrets of the CAPX namespaces. They are activated by default and deactivated with `--disable-backup` (see <<upgrade_provisioner_sintaxis, syntax of `upgrade-provisioner.py`>>). The script automatically recovers from failures internally, without any flag equivalent to `--restore` that the operator can run manually. Do not assume that the behavior of one applies to the other.

WARNING: Activating `ecr_pull_through_cache_enabled` on an existing cluster does not by itself rewrite the image paths of the already deployed components that do not change version in the same execution. See the xref:operations-manual:installation.adoc#_docker_repositories[note on day-0 configuration].

=== Prerequisites

* The pull-through cache rules must already exist in the cloud account for the upstreams that _Stratio KEOS_ uses (`registry.k8s.io`, `docker.io`, `ghcr.io`, `quay.io`, `public.ecr.aws`). The script does not create them; it assumes they already exist.
* The node role of the EC2 nodes needs the IAM permissions `ecr:BatchImportUpstreamImage` and `ecr:CreateRepository` (it is the xref:operations-manual:installation.adoc#_docker_repositories[same requirement as in the day-0 configuration]). Without them, nodes can't pull images through the cache, even if the rules already exist. If the cluster was created without `ecr_pull_through_cache_enabled` from the beginning, add these permissions to the IAM stack with `clusterawsadm` before executing this script.
* The target Helm repository must already publish the `cluster-operator` chart in the version indicated by `--cluster-operator`, along with its corresponding image in the container registry.

=== Syntax

[source,bash]
----
python3 ecr_pull_through.py -p <vault-password> --cluster-operator <version>
----

[%header,cols="1,2,1,1"]
|===
| Flag | Description | Default value | Mandatory

| `-p`, `--vault-password`
| Vault password to decrypt the secrets.
|
| Yes

| `-s`, `--secrets`
| Encrypted secrets file.
| secrets.yml
| No

| `-k`, `--kubeconfig`
| Kubeconfig file to use.
| ~/.kube/config
| No

| `--cluster-operator`
| Target version of _cluster-operator_.
|
| Yes

| `--helm-registry`
| Forces the Helm repository to use, without asking interactively.
| _(current repository of the `KeosCluster`)_
| No

| `--restore`
| Restores a previous backup instead of upgrading (see <<_recovery_from_failures, recovery from failures of `ecr_pull_through.py`>>). Without a path, it restores the most recent one from `backup/ecr_pull_through/`. With `--restore` present, `--cluster-operator` is no longer mandatory.
| _(none: upgrade mode)_
| No
|===

At startup, if `--helm-registry` is not specified, the script displays the Helm repository currently configured in `KeosCluster.spec.helm_repository.url` and allows specifying a new one. Press ENTER to keep the current one.

=== Recovery from failures

If the failure is because the image or chart of the indicated version hasn't been published in the target repository yet, the simplest solution is to publish the missing artifact and run the script again; it is idempotent against a previous incomplete attempt, so you don't need to restore anything.

To undo an already applied (or partially applied) upgrade, use `--restore` with the same credential options as before (`-p`, `-s`, `-k`):

[source,bash]
----
python3 ecr_pull_through.py -p <vault-password> --restore
----

Without a path after `--restore`, it automatically restores the most recent copy in `backup/ecr_pull_through/`, which is the normal behavior for undoing the last attempt. To restore a different copy (for example, if there were several consecutive failed attempts and you do not want to undo the last one), indicate its explicit path:

[source,bash]
----
python3 ecr_pull_through.py -p <vault-password> --restore backup/ecr_pull_through/<timestamp>
----

IMPORTANT: The path is relative to the working directory *inside the container* (`/upgrade`, where `-v $PWD/backup:/upgrade/backup` is mounted), never the *host* path. To list the available copies and copy the exact name, run `ls backup/ecr_pull_through/` inside the container itself before executing `--restore`.

The flag reverts, in this order, the CRDs, the `ConfigMap` of _cluster-operator_ values, `KeosCluster.spec.helm_repository.url`, `HelmRepository.spec.url`, the chart version in the `HelmRelease`, and finally `ecr_pull_through_cache_enabled` to its previous value. During the process, it waits for the `HelmRelease` to be in `Ready` state and the `KeosCluster` in `Provisioned` state, just like in a normal upgrade.

=== Verification

[source,bash]
----
kubectl get helmrelease cluster-operator -n kube-system
kubectl get keoscluster <cluster-name> -n cluster-<cluster-name> -o jsonpath='{.spec.docker_registries[0].ecr_pull_through_cache_enabled}'
----

*Expected output:* `HelmRelease` in `Ready = True` with the chart in the indicated version, and `ecr_pull_through_cache_enabled` set to `true`.

[[upgrade_providers]]
== Migration of the providers to Cluster API v1beta2

The `upgrade-providers.py` _script_ migrates a `cloud-provisioner 0.9.X` cluster to Cluster API v1.13.6, which uses the `v1beta2` API. It doesn't change the Kubernetes version or replace nodes. It runs only once per cluster, before upgrading to `cloud-provisioner 0.10.X`.

It upgrades, in this order:

. The Cluster API core and its _bootstrap_ and _control-plane_ providers, from v1.10.10 to v1.13.6.
. The infrastructure provider: CAPA to v2.13.0 on EKS, CAPZ to v1.26.1 on Azure VMs, and CAPG to `1.13.1-0.1.0` on GKE.
. The storage of the Cluster API objects, which moves to `v1beta2`.
. _cluster-operator_, to version 0.8.0, the first one that reads and writes those objects in `v1beta2`.

To plan the window, see the xref:operations-manual:upgrade-overview/from-0-9-x-to-0-10-x.adoc[sheet of the upgrade from 0.9.x to 0.10.x].

=== Prerequisites

* The cluster is EKS, GKE, or Azure VMs. The _script_ rejects any other combination.
* The cluster is on `cloud-provisioner 0.9.X`, with the Cluster API core on v1.10 or later and _cluster-operator_ on the 0.7 line. If it comes from 0.7.X, run the 0.9.X `upgrade-provisioner.py` first.
* The registry configured in the cluster (`keos_registry` in the `KeosCluster`) has the target provider images published. Also the _cluster-operator_ 0.8.0 _chart_ and image. The _script_ doesn't check that they exist.
* On EKS, a _kubeconfig_ that gets the _token_ with `exec`. See <<upgrade_providers_kubeconfig_eks, _kubeconfig_ on EKS>>.

The _script_ runs a pre-check and stops, without changing anything, if it finds any of these problems:

* The `KeosCluster` isn't in `ready: true` with the `Provisioned` phase.
* The Cluster API or infrastructure provider _controllers_ don't have any ready replica.
* Some `MachinePool` or `MachineDeployment` isn't in the `Running` phase.
* Some node isn't `Ready` or is marked as unschedulable.
* `cert-manager` has the `clusterctl` label, so `clusterctl` would try to upgrade it.
* The _secret_ with the infrastructure provider credentials is missing or empty.
* The _kubeconfig_ identity can't create, delete, or modify the objects that `clusterctl` applies again.

[[upgrade_providers_kubeconfig_eks]]
=== _Kubeconfig_ on EKS

A static EKS _token_ expires after 15 minutes and can do so in the middle of the run. That's why the pre-check rejects a _kubeconfig_ whose user has a _token_ without `exec`. Generate one with `exec` on the host machine, in the directory from which you're going to launch the container:

[source,bash]
----
aws eks update-kubeconfig --name <cluster-name> --region <region> --profile <profile> --kubeconfig $PWD/.kube/config
----

The container reads the AWS credentials from `/upgrade/.aws`, so mount your `~/.aws` directory as shown in the next section.

On GKE, unlike `upgrade-provisioner.py`, this _script_ doesn't rewrite the _kubeconfig_ to use `gke-gcloud-auth-plugin`. Use a _kubeconfig_ whose user only has an access _token_, without `exec`, and generate it right before you launch the container:

[source,bash]
----
kubectl --kubeconfig $PWD/.kube/config config set-credentials upgrade-providers --token=$(gcloud auth print-access-token)
kubectl --kubeconfig $PWD/.kube/config config set-context --current --user=upgrade-providers
----

The `gcloud` identity must be able to create, delete, and modify the objects that `clusterctl` applies again. The pre-check verifies it.

=== Execution of the container

Pull the 0.10.X image:

[source,bash]
----
docker pull <registry>/cloud-provisioner-upgrade:0.10.X
----

Start the container:

[source,bash]
----
docker run \
  --name cloud-provisioner-upgrade-providers \
  --net host \
  -it \
  -v $PWD/.kube/config:/upgrade/.kube/config \
  -v ~/.aws:/upgrade/.aws \
  -v $PWD/backup:/upgrade/backup \
  <registry>/cloud-provisioner-upgrade:0.10.X
----

NOTE: This _script_ doesn't need `secrets.yml` or the _vault_ password: it reads the provider credentials from the _secret_ that already exists in the cluster. The `~/.aws` mount is only needed on EKS.

=== Syntax

Always run a _dry-run_ first. It really runs the checks, the backup, and `clusterctl upgrade plan`, but it only shows the steps that would modify the cluster:

[source,bash]
----
python3 upgrade-providers.py --dry-run 2>&1 | tee /upgrade/backup/upgrade-providers-dryrun-$(date +%Y%m%d-%H%M%S).log
----

If the _dry-run_ ends without errors, launch the migration:

[source,bash]
----
python3 upgrade-providers.py 2>&1 | tee /upgrade/backup/upgrade-providers-$(date +%Y%m%d-%H%M%S).log
----

Before the first step that modifies the cluster, the _script_ asks for confirmation with ENTER. With `-y`, it doesn't ask.

[cols="2,1,3", options="header"]
|===
| _Flag_ | Default value | Use

| `--dry-run`
| disabled
| Runs the checks, the backup, and `clusterctl upgrade plan`. It doesn't apply any change.

| `-y`, `--yes`
| disabled
| Doesn't ask for confirmation before the first step that modifies the cluster.

| `-k`, `--kubeconfig`
| `$KUBECONFIG` (`/upgrade/.kube/config` in the container)
| _Kubeconfig_ of the cluster.

| `--cluster-operator`
| `0.8.0`
| Target version of _cluster-operator_ (_chart_ and image). It must be a version that works with `v1beta2`.

| `--backup-dir`
| `./backup/upgrade-providers`
| Base directory of the backups. Each run creates a subdirectory in it with its timestamp.

| `--backup-owner`
| `$BACKUP_OWNER`
| User and group (`uid:gid`) that the backup is assigned to when it ends. The container writes as `root`.

| `--storage-migration-timeout`
| `3`
| Minutes without progress in the storage migration before the _script_ migrates the pending objects itself.

| `--resume-from`
| —
| Backup of a previous run that failed halfway. See <<upgrade_providers_recuperacion, recovery from failures>>.

| `--clusterctl`, `--clusterctl-v1beta1`
| `clusterctl-v1.13.6`, `clusterctl`
| `clusterctl` v1.13.6 and v1.10.10 binaries. The ones in the image are the right ones; you don't need to change them.
|===

IMPORTANT: The backup contains the provider credentials. The _script_ creates it with `700` permissions, and it's left in `backup/upgrade-providers/<timestamp>/` of the directory from which you launch the container.

=== What the _script_ does

. Checks the `clusterctl` binaries, the provider manifests, and the prerequisites.
. Backs up the Cluster API objects with `clusterctl move --to-directory`. It also copies the provider _namespaces_, the CRDs, and the _webhooks_. It saves the state of `KeosCluster`, `ClusterConfig`, _cluster-operator_, and _cluster-autoscaler_, and a snapshot of the content of the objects and of the nodes.
. Validates the plan with `clusterctl upgrade plan`, without changing anything.
. Stops _cluster-autoscaler_ and _cluster-operator_. Suspends the _cluster-operator_ `HelmRelease`.
. If the cluster has Capsule, temporarily excludes the provider _namespaces_ from its _namespace_ _webhooks_. Then it checks, with a server-side _dry-run_, that no _webhook_ rejects what `clusterctl` is going to apply.
. On EKS and GKE, temporarily creates the `allow-all-egress` `NetworkPolicy` in the kubeadm _namespaces_, if it doesn't exist.
. If the kubeadm providers are below v1.10, first upgrades them to v1.10.10 with `clusterctl` v1.10.10.
. On Azure VMs, labels the Azure Service Operator CRDs as part of the infrastructure provider, as CAPZ requires before upgrading.
. Upgrades the core, kubeadm, and the infrastructure provider with `clusterctl` v1.13.6 and waits for the providers to be ready.
. Restores Capsule, the `NetworkPolicy`, and the provider replicas: 2 for the core and the infrastructure, and kubeadm to 0 on EKS and GKE or as it was on Azure VMs.
. Waits for the _controllers_ to migrate the storage of the Cluster API CRDs to `v1beta2`. If there's no progress within `--storage-migration-timeout`, it migrates the pending objects itself.
. Briefly disables the `KeosCluster` _webhooks_, updates the `ClusterConfig` versions, and restores them.
. Upgrades _cluster-operator_ to the target version, reactivates its `HelmRelease`, and waits for it to be ready.
. Starts _cluster-autoscaler_ again and checks in its _logs_ that it uses `v1beta2`.
. Waits for the `KeosCluster` to be in `ready: true` with the `Provisioned` phase.
. Checks the result and compares the content of the objects with the initial snapshot.

The _feature gates_ of the _controllers_ are shown before and after, only as a report: the _script_ doesn't modify them.

[[upgrade_providers_recuperacion]]
=== Recovery from failures

If the _script_ fails before stopping _cluster-autoscaler_ (checks, backup, or `clusterctl upgrade plan`), nothing has changed in the cluster. Fix the cause and launch it again.

If it fails afterward, the _script_ restores the `KeosCluster` _webhooks_, Capsule, and the `NetworkPolicy`, and reactivates _cluster-operator_ and _cluster-autoscaler_. It ends with `Migration did NOT complete. Backup: <path>`. It doesn't try to go back to the previous versions. Fix the cause and launch it again with `--resume-from` and the backup path of that run:

[source,bash]
----
python3 upgrade-providers.py --dry-run --resume-from /upgrade/backup/upgrade-providers/<timestamp>
python3 upgrade-providers.py --resume-from /upgrade/backup/upgrade-providers/<timestamp>
----

With `--resume-from`, the _script_:

* Doesn't require the Cluster API and provider _controllers_ to have ready replicas, because the previous run may have left them halfway.
* If `clusterctl move` fails in the backup, it only warns: the backup of the previous run is still the reference one.
* Compares the final content with the snapshot of the previous run (`snapshot-before.json`), that is, with the state before the migration.

What was already done isn't repeated: if the providers are already on the target version, the _script_ doesn't upgrade them again with `clusterctl` and completes the missing steps.

IMPORTANT: Always give the backup of the *first* run that failed. Each run saves its own snapshot when it starts; the one of a retry that fails again already reflects a half-migrated state.

=== Verification

When it ends, the _script_ checks the following and fails if something isn't met:

* The providers are on the target version.
* Every Cluster API CRD only stores `v1beta2`.
* The `Cluster`, `MachineDeployment`, `MachinePool`, `MachineSet`, and `Machine` objects are the same ones, with the same names: no node has been replaced.
* The provider replicas are the expected ones, and the _Pod Disruption Budgets_ of the core and of the infrastructure provider allow at least one disruption.
* The `KeosCluster` is in `ready: true` with the `Provisioned` phase.

The content difference is saved in `content-diff.txt`, inside the backup. You can check the result by hand:

[source,bash]
----
kubectl get providers -A
kubectl get crd clusters.cluster.x-k8s.io -o jsonpath='{.status.storedVersions}'
kubectl get keoscluster <cluster-name> -n cluster-<cluster-name>
----

*Expected output:* the providers on the target version, `["v1beta2"]`, and the `KeosCluster` in `READY = true`.

=== Interactive prompts

At startup, the script may request up to three keyboard confirmations, in this order:

. *Continue with the upgrade*: after the pre-upgrade cluster checks, press ENTER to continue or any other key to abort. It is omitted with `-y`/`--yes`.
. *Helm repository*: it displays the Helm repository currently configured in `KeosCluster.spec.helm_repository.url` and allows specifying a new one. Press ENTER to keep the current one. *It cannot be omitted*: it is always asked, even with `-y`.
. *`k8s_version` bump* (only if `KeosCluster.spec.k8s_version` is going to change): it requests explicit confirmation `[y/N]` before applying the patch. Responding "n" or leaving it blank cancels only this step (the rest of the upgrade continues). It is omitted with `--start-from-k8s-version`.

WARNING: If you indicate a Helm repository different from the one already configured, all chart versions that the script uses will be resolved against that new repository. Change this value only if the new repository publishes the same universe of versions (`kubernetes-universe`) that corresponds to this version of _Stratio Cloud Provisioner_; a repository from a different universe can resolve chart versions that are incompatible with each other.

To automate the execution without manual intervention (for example, in a pipeline), combine `-y`/`--start-from-k8s-version` with the necessary responses via stdin for the Helm repository prompt (which cannot be deactivated) before launching the container.

[[upgrade_provisioner_recuperacion]]

=== Recovery from failures

As already indicated in <<_migration_to_ecr_pull_through_cache, migration to ECR pull-through cache>>, `upgrade-provisioner.py` does not have a flag equivalent to `--restore` in `ecr_pull_through.py`. Its recovery is automatic and internal: it is activated by the script itself when it detects a failure within what this document calls the "critical section", the stretch of the upgrade in which `cluster-operator` is suspended, `keoscluster-controller-manager` is stopped, and the `KeosCluster` webhooks are disabled. To know whether a specific failure occurred in that stretch, look in the console output for the "[INFO] Suspending cluster-operator helmrelease:" message. If that message already appeared and the failure occurred before you saw "[INFO] Resuming cluster-operator helmrelease: OK", the failure occurred within the critical section.

The automatic recovery restores the _webhooks_ and restarts the controller, but *it doesn't cover every possible failure*. The most common case is described below.

==== Failure of the health check of a chart (`unhealthy pod(s)`)

`upgrade-provisioner.py` checks, right after upgrading each chart, that its pods are really healthy (not just that Flux marks the `HelmRelease` as `Ready`). That check is a point-in-time snapshot taken immediately after executing `helm upgrade`. If at that instant the rollout still has a pod of the previous version in the process of terminating, the script can interpret it as a real failure and abort with a message like "[ERROR] Error updating chart: N unhealthy pod(s) for release <chart>".

*Before assuming that the cluster was left in a bad state*, check the real state of the affected chart:

[source,bash]
----
kubectl get helmrelease <chart> -n <namespace>
kubectl get pods -n <namespace>
----

If the `HelmRelease` already reflects the target version and the pods are `Running`, the chart was applied correctly: the failure was only in the script's check, not in the cluster. In that case, *relaunch `upgrade-provisioner.py` with the same command*: the script's design is idempotent at the chart level (it compares the current version with the target version before touching anything), so the already upgraded charts are skipped automatically and the execution continues from where it left off.

== General description of the upgrade process

The script executes the following workflow:

. *Validation*
** Validates the _kubeconfig_ and the secrets.
** Configures the _cloud_ provider credentials.
** Checks that the Cluster API core is on v1.13.0 or later and that each provider is exactly on its target version. If not, it stops without changing anything and asks you to run `upgrade-providers.py` first.

. *Pre-upgrade*
** Scales _cluster-autoscaler_ to 0 to prevent automatic scaling during the upgrade. (Does not apply on GKE).

. *Backup*
** CAPX components (via `clusterctl move`).
** Capsule webhook configurations.
** Secrets of the CAPX namespaces.

. *Capsule preparation*
** Modifies the webhooks to exclude critical namespaces from validation and mutation.
** Guarantees that tenant isolation does not block the upgrade.

. *Chart upgrade*
** Upgrades base charts (cert-manager, flux2, tigera-operator, and so on).
** Upgrades the provider-specific charts (aws-load-balancer-controller, Azure CSI controllers).
** Restores the Capsule webhooks to their original configuration.

. *_Cluster-Operator_ preparation*
** Suspends the _cluster-operator_ _HelmRelease_.
** Verifies that `KeosCluster` is _ready_/`Provisioned` before entering the critical section.
** Stops the _keoscluster-controller_ deployment.
** Backs up the configuration of the `KeosCluster` webhooks.
** Deactivates the _keoscluster_ validation/mutation webhooks.
** Updates _ClusterConfig_ with the new versions of the components.

. *Cluster API providers*
** It doesn't upgrade them: since they're already on their target version, the _script_ skips `clusterctl upgrade apply` and says so with the message `Upgrading Cluster API providers: already at target versions: SKIP`.

. *Kubernetes version upgrade* (if `KeosCluster.spec.k8s_version` changes with respect to the current version)
** On AWS: patches `KeosCluster.spec.k8s_version` directly with the final version. Restores the _keoscluster_ webhooks and restarts the _keoscluster-controller_ deployment. Verifies that _cluster-operator_ has propagated the change to the provider-managed _control-plane_ resource (`AWSManagedControlPlane` on EKS) before continuing.
** On Azure VMs: sequence of patches, one for each intermediate minor, with the _keoscluster-controller_ deployment active throughout the entire process (see <<_bump_de_k8s_version_en_azure_vms, `k8s_version` bump on Azure VMs>>).
** On GKE: sequence of patches, one for each intermediate minor, also with the _keoscluster-controller_ deployment active (see <<_bump_de_k8s_version_en_gke, `k8s_version` bump on GKE>>).

IMPORTANT: On EKS, the cluster cannot have _MachineDeployment_ worker groups: migrate each one to _MachinePool_ before running the script (see <<_migration_from_machinedeployments_to_machinepools, migration from _MachineDeployments_ to _MachinePools_>>). On AWS, _cluster-operator_ does not bump the version of _MachineDeployment_ groups and the script waits for every node to reach the target version, so with one of those groups the wait times out. On Azure VMs, each step of the bump upgrades all worker groups with a fixed `node_image`, along with the control plane. On GKE, all worker groups are _MachinePool_ and the script waits for them to converge in each step.

[[_bump_de_k8s_version_en_azure_vms]]

=== `k8s_version` bump on Azure VMs

Unlike AWS, on Azure VMs the _script_ can't apply a single _patch_ to the final _minor_. The reason isn't a design choice, it's an external block: the Azure VMs _control-plane_ is a `KubeadmControlPlane` (CAPI _kubeadm_-based), and its _webhook_, which belongs to CAPI _core_ and not to `KeosCluster`, rejects any jump of ≥2 _minors_ without exception. `upgrade-provisioner.py` can only disable the `KeosCluster` _webhook_, not this one. That's why the _script_ itself has to issue one _patch_ per intermediate _minor_ (`1.35`→`1.36`→`1.37`), waiting for each step to really converge before launching the next one. On EKS, CAPA does that same work internally after a single _patch_. It's not that Azure "is slower": here the _script_ explicitly does what stays invisible on EKS.

This has direct practical implications:

* *`--node-image-map` is mandatory* for any `k8s_version` bump on Azure. It is a JSON map with the VM image of each intermediate minor (see the flags table above). Without it, the script aborts before touching anything. Each step needs the image of *its* minor, not the final destination: CAPI requires that a new machine exactly matches the _control-plane_ version at the time of creation.

* The complete process takes longer than on EKS, because it is N sequential upgrades of the _control-plane_ (with its convergence wait and a settling margin between steps), not just one.
* Throughout the entire bump, the script automatically applies and reverts two temporary changes, without manual intervention:
** It extends the Calico `GlobalNetworkPolicy` to allow traffic from the control plane, so connectivity isn't interrupted while _control-plane_ nodes have mixed versions during the transition.
** It temporarily removes the `nodes.capsule.clastix.io` entry from the `capsule` validation webhook. If left active, it blocks the `kubeadm join` command for the new _control-plane_ replicas.
+
If the script is interrupted mid-bump (for example, if the container is stopped), both changes may remain applied. Check `kubectl get globalnetworkpolicy allow-all-traffic-from-control-plane -o yaml` and `kubectl get validatingwebhookconfigurations capsule-validating-webhook-configuration` before relaunching.

. *Post-upgrade*
** Resumes the _cluster-operator_ _HelmRelease_.
** Waits for the _cluster-operator_ to be _ready_.
** Waits for the real cloud provider infrastructure to reach the new Kubernetes version (up to `--control-plane-timeout`, 90 minutes by default; on EKS, CAPA applies the minors one at a time automatically, so a jump of several minors can be observed as several successive `UPDATING` → `ACTIVE` transitions before reaching the final version; on GKE, the script queries the GKE API directly).
** If there was no `k8s_version` bump (the wait for that case is already covered by the previous step), waits for `KeosCluster.status.ready` to be `true`.
** Waits for the `keoscluster-controller-manager` deployment to be in `Available` state.
** On EKS, waits for every _nodegroup_ and every node to reach the target _minor_. It gets the _nodegroups_ from the cluster's `AWSManagedMachinePool` objects, so it doesn't need the `eks:ListNodegroups` permission.
** On Azure VMs, switches the `cloudControllerManager`/`cloudNodeManager` image to the one for the target _minor_.
** Restores the _cluster-autoscaler_ replicas to 2.

[[_bump_de_k8s_version_en_gke]]

=== `k8s_version` bump on GKE

As on Azure VMs, on GKE the _script_ doesn't apply a single _patch_ to the final _minor_, but for a different reason: GKE refuses to upgrade the _control-plane_ by more than one _minor_ at a time. That's why the _script_ issues one _patch_ per intermediate _minor_, with the _keoscluster-controller_ _deployment_ active throughout the process. In this version, the target on GKE is 1.36, so there's a single step (`1.35`→`1.36`).

In each step, the script:

. Resolves the target version. GKE does not accept a generic `X.Y.0`, so the script uses the highest valid patch of the cluster's release channel for that minor.
. Waits for the _control-plane_ to reach that version, querying the GKE API (`gcloud container clusters describe`) instead of the state of the `KeosCluster`.
. Waits for all node pools to be in `RUNNING` with the new version and for each node's `kubeletVersion` to match that version.
. Waits for the `KeosCluster` to return to `ready: true` and `phase: Provisioned` before moving to the next minor.

This has practical implications:

* You do not need `--node-image-map`: GKE manages the node images based on the version of each node pool.
* The available versions change over time because GKE retires old patches from each release channel. The script resolves the version at execution time.
* The nodes must converge in each step, not only at the end: GKE only admits nodes up to two minors behind the control plane.
* The node wait verifies the real `kubeletVersion`. GKE sets the `version` field of the node pool to the target value as soon as it accepts the request, before replacing any node.
* The node wait is controlled with `--node-convergence-timeout`: it only aborts if no node or node pool progresses during that time.

Before starting, check that the target minor is available in the cluster's release channel:

[source,bash]
----
gcloud container clusters describe <cluster-name> --region <region> --format='value(releaseChannel.channel)'
gcloud container get-server-config --zone=<zone> --format=json | jq -c '[.channels[]|{c:.channel, v137:[.validVersions[]|select(startswith("1.37"))]}]'
----

== Monitoring during the upgrade

* Monitor unhealthy pods. It is a generic command, valid for any provider, that does not depend on a component name list that may become outdated.
+
[source,bash]
----
watch -n5 'kubectl get pods -A | grep -Ev "Running|Completed"'
----
+
NOTE: During a healthy upgrade, this command should not show anything.

* Follow _HelmReleases_.
+
[source,bash]
----
watch -n2 kubectl get helmreleases -A
----

* During the Kubernetes version upgrade, the script does not show progress while it waits for the real cloud provider infrastructure to complete the change.
+
** On EKS, follow the real state of the _control-plane_ directly on AWS:
+
[source,bash]
----
watch -n30 aws eks describe-cluster --name <cluster-name> --query 'cluster.{status:status,version:version}' --output table
----
+
** On Azure VMs, follow the real convergence of the `KubeadmControlPlane` (the same object that the script internally watches; see <<_bump_de_k8s_version_en_azure_vms, `k8s_version` bump on Azure VMs>>):
+
[source,bash]
----
watch -n30 "kubectl get kubeadmcontrolplanes.v1beta2.controlplane.cluster.x-k8s.io <nombre-cluster>-control-plane -n cluster-<nombre-cluster> -o jsonpath='{.status.version} upToDate={.status.upToDateReplicas}/{.status.replicas} available={.status.conditions[?(@.type==\"Available\")].status}'"
----
+
** On GKE, follow the _control-plane_ and the node pools separately: the _control-plane_ reaches the destination well before the nodes (see <<_bump_de_k8s_version_en_gke, `k8s_version` bump on GKE>>):
+
[source,bash]
----
watch -n30 'gcloud container clusters describe <cluster-name> --region <region> --format="value(status,currentMasterVersion)"; gcloud container node-pools list --cluster <cluster-name> --region <region> --format="table(name,version,status)"'
----
+
The reliable signal that the nodes have finished is the `kubeletVersion` of each node, not the `version` field of the node pool:
+
[source,bash]
----
kubectl get nodes -o custom-columns=NAME:.metadata.name,VERSION:.status.nodeInfo.kubeletVersion
----
+
NOTE: In the GKE operations list (`gcloud container operations list`), you will see `UPGRADE_NODES` operations that last seconds. They are metadata changes CAPG applies during reconciliation, not node replacements; a real replacement takes minutes per node. If they keep appearing every few seconds for the same node pools and the `capg-controller-manager` logs repeat `Node pool config update required`, CAPG is in a reconciliation loop: see xref:operations-manual:operations-manual.adoc#_reconciliation_loop_in_gke_due_to_automatic_labels[Reconciliation loop on GKE due to automatic labels].

| jq -r '
  .items[]
  | "\(.metadata.namespace)/\(.metadata.name) -> \(.spec.chart.spec.chart)@\(.spec.chart.spec.version)"
' \
| sort -u
----

* Verification of the final state.
+
[source,bash]
----
kubectl get keoscluster -A
kubectl get machines -A
kubectl get machinedeployments -A
kubectl get machinepools -A
kubectl get nodes -o custom-columns=NAME:.metadata.name,VERSION:.status.nodeInfo.kubeletVersion
kubectl logs -n capi-system deploy/capi-controller-manager --since=30m | grep -i error
kubectl logs -n capa-system deploy/capa-controller-manager --since=30m | grep -i error
kubectl logs -n capz-system deploy/capz-controller-manager --since=30m | grep -i error
kubectl logs -n capg-system deploy/capg-controller-manager --since=30m | grep -i error
----
+
NOTE: In a jump of several `k8s_version` minors, it is expected to see two transient errors in the `capa-controller-manager` logs: `InvalidParameterException: Addon version specified is not supported` when upgrading the EKS addons (e.g., `kube-proxy`) while the real AWS _control-plane_ has not yet reached the necessary intermediate minor, and `connection to the workload cluster is down` during the upgrade window of the control plane itself. Both self-resolve in the following minutes, without intervention, once `AWSManagedControlPlane.status.conditions[EKSAddonsConfigured]` transitions to `True`. Treat them as a real problem only if they persist beyond the upgrade window.
+
*Expected output:* `KeosCluster.spec.k8s_version` matches the target version. The _MachinePool_ groups report the same version in `kubeletVersion`. On GKE, `k8s_version` keeps the _patch_ that the _script_ resolved (for example, `v1.36.4`), not `v1.36.0`. On EKS, every worker group is a _MachinePool_ (it's a prerequisite, see <<_general_description_of_the_upgrade_process, general description of the process>>), so every node reports the target version. On Azure VMs, every worker group with a fixed `node_image` is upgraded along with the _control-plane_ (see <<_bump_de_k8s_version_en_azure_vms, `k8s_version` _bump_ on Azure VMs>>).

== Upgrade of _cluster-autoscaler_ after the upgrade

IMPORTANT: On EKS and Azure VMs, the _script_ leaves _cluster-autoscaler_ on the Stratio image, `v1.36.1`, which includes the fix for the scale-down of _MachinePool_ nodes (https://github.com/kubernetes/autoscaler/pull/9693[kubernetes/autoscaler#9693]). It pulls it from `<registry>/autoscaling/cluster-autoscaler`, also with ECR _pull-through cache_, so replicate it in the cluster's registry *before* you run the _script_, as described in xref:operations-manual:installation.adoc#_actualización_de_cluster_autoscaler[Upgrade of _cluster-autoscaler_ after installation]. The _script_ recreates the `02-cluster-autoscaler-helm-chart-override-values` _ConfigMap_ empty: if you had other _overrides_ in it, apply them again when it finishes.

== EKS clusters with _MachinePools_

NOTE: _MachinePools_ are available on clusters created with _Stratio Cloud Provisioner_ 0.9.x or later. There is no automatic migration from _MachineDeployments_ to _MachinePools_ on existing clusters. To migrate an existing cluster, see the <<_migration_from_machinedeployments_to_machinepools, migration from _MachineDeployments_ to _MachinePools_>>.

=== Migration from _MachineDeployments_ to _MachinePools_

WARNING: This procedure applies only to EKS clusters (managed by AWS). It is not available for Azure VMs or for GKE.

Migrating an existing worker group from _MachineDeployment_ to _MachinePool_ has three parts: confirming the cluster meets the prerequisites, configuring the mandatory fixed IAM role for the _MachinePool_, and manually migrating each node group.

==== Prerequisites

Any 0.9.x cluster already has the _cluster-operator_ and CAPA versions and the CAPA feature gates (`MachinePool=true`, `EKSAllowAddRoles=true`) that _MachinePools_ need. The cluster also needs:

* `KeosCluster.status.ready = true`.
* The EKS policy of the deployment user, with the xref:operations-manual:installation.adoc#eks_nodegroup_permissions[nodegroup permissions] (`eks:CreateNodegroup`, `eks:DescribeNodegroup`, `eks:DeleteNodegroup`, `autoscaling:DescribeAutoScalingGroups`, `iam:CreateServiceLinkedRole`), which are included in _stratio-eks-policy.json_. If the cluster was created without them, update the IAM stack with `clusterawsadm` (the same procedure as in the installation).

The service role `AWSServiceRoleForAmazonEKSNodegroup` (the one used by the EKS service itself to manage the Auto Scaling Group/launch template behind each managed nodegroup) is not created by any _Stratio Cloud Provisioner_ script: AWS creates it automatically in the first managed nodegroup that is created in the account/region, provided the deployment user has the `iam:CreateServiceLinkedRole` permission (already listed above). No manual action is required for this role.

==== Configure the fixed IAM role for the _MachinePools_

IMPORTANT: This step is mandatory when migrating to _MachinePool_: you cannot leave nodegroups with the dynamic IAM role that CAPA creates by default (`capa_<hash>`, different on each recreation of the nodegroup). Fixing `mp_role_name` is the only supported way to manage consistent IAM permissions on the _MachinePool_ nodes (for example, for `ecr_pull_through_cache_enabled`; see <<_migration_to_ecr_pull_through_cache, migration to ECR pull-through cache>>). With a dynamic role, you would have to grant those permissions manually every time the nodegroup is recreated, with a different role each time.

Set `spec.control_plane.aws.mp_role_name` to a single, reusable IAM role for all _MachinePools_ in the cluster. With `security.aws.create_iam: true`, _Stratio Cloud Provisioner_ already automatically creates the role `eks-nodegroup.cluster-api-provider-aws.sigs.k8s.io` as part of the CloudFormation stack, but does not use it anywhere until it is explicitly indicated here. Set it with a `patch` (never `apply`; see project convention):

[source,bash]
----
kubectl patch keoscluster <cluster-name> -n cluster-<cluster-name> --type=merge \
  -p '{"spec":{"control_plane":{"aws":{"mp_role_name":"eks-nodegroup.cluster-api-provider-aws.sigs.k8s.io"}}}}'
----

IMPORTANT: On a cluster created with a version earlier than 0.9.x, this role may not yet exist even if it has `security.aws.create_iam: true` (see <<_if_the_role_does_not_exist_yet_on_a_cluster_with_create_iam_true, if the role does not exist yet on a cluster with `create_iam: true`>>, below). With `security.aws.create_iam: false` (IAM managed by the customer), the role is not created automatically in any case: it must be created manually with a name of the customer's choice and with the equivalent permissions (see the xref:operations-manual:installation.adoc#mp_role_name_ownership[reference of the `mp_role_name` field]).

This change does not affect _MachinePools_ that already exist, only those created after the `patch`. To migrate one already created with a dynamic role to a fixed role, you must recreate it (it is not an in-place updatable field on an existing EKS nodegroup).

===== If the role does not exist yet on a cluster with `create_iam: true`

WARNING: This section applies only to *already existing* clusters, whose CloudFormation stack was created before _Stratio Cloud Provisioner_ supported `security.aws.nodegroup_extra_policy_arn`. For *new* installations, indicate that field directly in the descriptor (see xref:operations-manual:installation.adoc#nodegroup_extra_policy_arn[nodegroup_extra_policy_arn]); the rest of this section does not apply in that case.

The CloudFormation stack of a cluster with `security.aws.create_iam: true` includes the role `eks-nodegroup.cluster-api-provider-aws.sigs.k8s.io` since _Stratio Cloud Provisioner_ started generating that configuration by default (`AWSIAMConfiguration`, `spec.eks.managedMachinePool` block). A cluster whose stack was created before that may not yet have it. Check it:

[source,bash]
----
aws iam get-role --role-name eks-nodegroup.cluster-api-provider-aws.sigs.k8s.io
----

If it does not exist, update the existing stack with `clusterawsadm`. It is an idempotent operation (`create-cloudformation-stack` and `update-cloudformation-stack` are aliases of the same command) that adds what is missing without affecting the rest of the resources already created by the stack. Add the `eks.managedMachinePool` block to the configuration (same pattern as the rest of this guide; see xref:operations-manual:installation.adoc[the documentation for the base IAM configuration]):

[source,bash]
----
cat > /tmp/eks-mp.config << 'EOF'
apiVersion: bootstrap.aws.infrastructure.cluster.x-k8s.io/v1beta1
kind: AWSIAMConfiguration
spec:
  bootstrapUser:
    enable: false
  eks:
    enable: true
    iamRoleCreation: false
    defaultControlPlaneRole:
        disable: false
    managedMachinePool:
        disable: false
        extraPolicyAttachments:
        - arn:aws:iam::aws:policy/service-role/AmazonEBSCSIDriverPolicy
  controlPlane:
    enableCSIPolicy: true
  nodes:
    extraPolicyAttachments:
    - arn:aws:iam::aws:policy/service-role/AmazonEBSCSIDriverPolicy
EOF

clusterawsadm bootstrap iam create-cloudformation-stack \
  --config /tmp/eks-mp.config \
  --region <region>
----

If the cluster also has `ecr_pull_through_cache_enabled: true`, the _MachinePool_ nodes need the same ECR permissions (`ecr:BatchImportUpstreamImage`, `ecr:CreateRepository`) that the `nodes` role already has (see <<_migration_to_ecr_pull_through_cache, migration to ECR pull-through cache>>). Unlike `nodes`, the `eks-nodegroup` role *does not support inline policies* (`extraStatements`), only policies managed by ARN. First, create an independent IAM policy with those permissions:

[source,bash]
----
cat > /tmp/ecr-pull-through-mp-policy.json << 'EOF'
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Action": ["ecr:BatchImportUpstreamImage", "ecr:CreateRepository"],
      "Effect": "Allow",
      "Resource": ["*"]
    }
  ]
}
EOF

aws iam create-policy \
  --policy-name ecr-pull-through-cache-machinepool \
  --policy-document file:///tmp/ecr-pull-through-mp-policy.json
----

Add the returned ARN to the `managedMachinePool.extraPolicyAttachments` block *alongside* `AmazonEBSCSIDriverPolicy` (see the example above), not in its place. `ManagedPolicyArns` in CloudFormation is a full replacement list: if you only list the new ARN, `AmazonEBSCSIDriverPolicy` is detached from the role in the next `update-cloudformation-stack`.

==== Migrate a node group

Repeat these steps for each group you want to migrate:

. Add the new _MachinePool_ group to the `KeosCluster` object. Omit `node_image` and indicate `ami_type` optionally (by default, "BOTTLEROCKET_x86_64"):
+
[source,bash]
----
kubectl -n cluster-<cluster-name> patch keoscluster <cluster-name> \
  --type=json \
  -p '[{"op":"add","path":"/spec/worker_nodes/-","value":{"name":"<name>","size":"<size>","quantity":<n>,"az":"<az>","min_size":<min>,"max_size":<max>}}]'
----
+
NOTE: Use `--type=json` with the `add` operation and the path `/spec/worker_nodes/-` to add the group without replacing the existing ones. Never use `kubectl apply` on the `KeosCluster`: _cluster-operator_ detects the `kubectl.kubernetes.io/last-applied-configuration` annotation that `apply` generates and skips the real reconciliation cycle, so the changes in `spec.worker_nodes` are never processed.
+
WARNING: `spec.worker_nodes[].name` (`<name>` above) admits between 3 and 25 characters (`KeosCluster` webhook) and must be unique. *Do not add the `-mp`/`-md` suffix yourself*: _cluster-operator_ already automatically adds `-mp-<index>` (or `-md-<index>` on _MachineDeployment_) to the name you give (`controllers/templates/aws/aws.eks.tmpl`).

. Wait for the new group to be healthy:
+
[source,bash]
----
kubectl -n cluster-<cluster-name> get machinepool -l cluster.x-k8s.io/deployment-name=<name>-mp-<index> \
  -o jsonpath='{.items[0].status.readyReplicas}/{.items[0].status.replicas}'
----

. Identify the real nodes of the _MachineDeployment_ to replace and drain them one by one, verifying the state of the cluster between each one:
+
IMPORTANT: The label `cluster.x-k8s.io/deployment-name` lives on the `Machine` object (CAPI), not on the Kubernetes `Node`, so `kubectl get nodes -l cluster.x-k8s.io/deployment-name=...` always returns 0 results. Resolve the real name of the `Node` through the `Machine`:
+
[source,bash]
----
kubectl -n cluster-<cluster-name> get machine -l cluster.x-k8s.io/deployment-name=<real-md-name> \
  -o jsonpath='{.items[*].status.nodeRef.name}'
kubectl drain <node> --ignore-daemonsets --delete-emptydir-data --timeout=10m
----

. Delete the entry of the migrated _MachineDeployment_ from `spec.worker_nodes` in the `KeosCluster` (same `--type=json` mechanism, `remove` operation) and verify that there are no _MachineDeployment_ objects of that group left:
+
[source,bash]
----
kubectl get machinedeployment -A | grep <real-md-name>
----

NOTE: Do not delete the _MachineDeployment_ group until all its nodes are drained and the _MachinePool_ group has enough capacity to absorb the workload.
