= Version upgrade

== Description

The `upgrade-provisioner.py` script upgrades a cluster created with _Stratio Cloud Provisioner_ 0.7.x and Kubernetes 1.32 to version 0.9.9, with Kubernetes 1.35. Each environment has its own step-by-step procedure:

* xref:operations-manual:upgrade/aws-eks.adoc[EKS] in AWS (managed).
* xref:operations-manual:upgrade/azure-vms.adoc[Azure VMs] (unmanaged).
* xref:operations-manual:upgrade/gcp-gke.adoc[GKE] in GCP (managed).

This page gathers what is common to the three environments:

* The upgraded components and their versions.
* The common requirements.
* The use of the `--private` option.
* The script's options and prompts.
* The phases of the upgrade process.
* The final verification.

To run the upgrade, follow the procedure for your environment.

IMPORTANT: Before starting, read this page and the procedure for your environment in full. Some steps cannot be undone, and several decisions are made before launching the script. If you have any questions, open a ticket with the Platform team before continuing.

IMPORTANT: Only clusters with Kubernetes version 1.32 are supported. If the cluster is on an earlier version, follow the corresponding upgrade procedure first until you reach the supported version.

The script and all its dependencies are in the `cloud-provisioner-upgrade:0.9.9` Docker image, so there is no need to install them on your machine:

== Common requirements

These requirements are the same across the three environments. Each procedure adds its own in its requirements section.

* Technical:
** Have Docker installed on the system.
** Have a _kubeconfig_ file with access to the cluster (at `.kube/config`).
** Have the `secrets.yml` file (encrypted with Ansible Vault) that was used to create the cluster, and its Ansible Vault password. The password is passed as a mandatory argument (`-p`/`--vault-password`) when running the script inside the container, and has no default value.
** Have a local directory called `backup` for the backups (mounted in the container at `/upgrade/backup`), in the working directory from which the container is launched. Always use the same name on all clusters and clients so the location is predictable when support is provided. The script manages its own subfolder structure within that directory: one per execution, with a timestamp, inside an additional `upgrade/` level, so the actual path of each backup is `/upgrade/backup/upgrade/<timestamp>/`. There is no need for the directory to be empty or to recreate it between executions; it is enough for it to exist as a mount point.
** Check that the container registry and the target Helm repository contain the images and the charts of Universe 15.1 (see <<_what_is_upgraded, what is upgraded>>). To see where the script downloads each item from, see <<_origen_de_charts_e_imágenes, origin of the charts and the images>>.
+
IMPORTANT: The repository that must be checked *is not necessarily the one the cluster currently has configured*. The script asks interactively whether to specify a new one (see the <<_prompts_interactivos, interactive prompts>>); when a different one is specified, it becomes the repository used for the entire upgrade, including the _cluster-operator_ chart. Check the chart of the repository that will actually be used in this execution.
+
When it's the turn of the _cluster-operator_ chart, the script downloads it (`helm pull`) from that repository to apply its CRDs (when the chart includes them). It downloads it before changing its values and its `HelmRelease`; when the download fails, _cluster-operator_ is left as it was. The dry-run does not perform this download, so it does not check it. When the chart does not include CRDs, the script continues without problems; the upgrade stops at this step only if the download fails (because the chart or version is not in the repository, or because the repository credentials are invalid). The script downloads the flux2 chart in the same way: from that repository, in private mode, and, when not, from its public repository.

* Functional:
+
Before running the upgrade, check that the cluster meets the following conditions. When any is not met, *do not launch the upgrade* until it is resolved:
+
** `KeosCluster` ready:
+
[source,bash]
----
kubectl get keosclusters.installer.stratio.com -A
----
+
*Expected output:*
+
*** `READY = true`
*** `PHASE = Provisioned`

** Nodes in good state:
+
[source,bash]
----
kubectl get nodes
----
+
*Expected output:* all the nodes with `STATUS = Ready`.

** Cluster API and _cluster-operator_ pods:
+
[source,bash]
----
kubectl get pods -n capi-system
kubectl get pods -n kube-system -l app.kubernetes.io/name=keoscluster-controller-manager
----
+
*Expected output:* all the pods in `Running` state.

** Cluster API and _cluster-operator_ logs:
+
[source,bash]
----
kubectl logs -n capi-system -l cluster.x-k8s.io/provider=cluster-api --tail=-1 --since=1h | grep '^E'
kubectl logs -n kube-system -l app.kubernetes.io/name=keoscluster-controller-manager --tail=-1 --since=1h | grep -P '\tERROR\t'
----
+
NOTE: When any error appears, review it before continuing.

** _HelmReleases_:
+
[source,bash]
----
kubectl get helmrelease -A
----
+
*Expected output:* all with `READY = True`.

** [[automatic_check]]Automatic check: on startup, before asking for confirmation, the script performs its own health check, independent of the previous ones:
+
--
* Checks `KeosCluster.status.ready`.
* Checks that no pod in the cluster is in `CrashLoopBackOff`, `ImagePullBackOff`, `ErrImagePull`, or `CreateContainerConfigError`, or in a phase other than `Running`, `Succeeded`, or `Pending`.
* Checks that the Cluster API and provider controllers have 2 replicas available.
* Checks that no `Machine` is outside the `Running`, `Provisioning`, `Pending`, or `ScalingUp` phases.
* *It does not directly check the state of the `HelmRelease` objects, but only that of the pods, as an indirect indicator.* For this reason, the previous manual check (`kubectl get helmrelease -A`) remains necessary: it is not redundant.
* When it finds any problem, *it aborts the upgrade before starting*, unless `--skip-preflight-checks` is indicated (assuming the risk) or `--dry-run` (which only reports that it would abort).
--

== Important notes

=== Use of the `--private` option

The `--private` option *forces* the use of private repositories for:

* Container images (`private_registry`).
* Helm charts (`private_helm_repo`).

Both are fields of `ClusterConfig.spec`. The script uses private mode when the field is already `true` or when `--private` is passed: the option can only enable it, never disable it.

This implies that:

* When `ClusterConfig.spec.private_registry=true`, the script continues to use the private registry even when `--private` *is not passed*.
* When `ClusterConfig.spec.private_helm_repo=true`, the script continues to use the private Helm repository even when `--private` *is not passed*.
* When `--private` *is passed*, both values are forced to `true` during the upgrade, and the `ClusterConfig` is updated with those values.

==== Common cases

[%header,cols="2,2,3"]
|===
| Current state in `ClusterConfig`
| Execution
| Result

| `private_registry=true` +
`private_helm_repo=true`
| Without `--private`
| The private registry and the private Helm repository continue to be used.

| `private_registry=false` +
`private_helm_repo=false`
| Without `--private`
| The public repositories are used.

| `private_registry=false` +
`private_helm_repo=false`
| With `--private`
| The use of the private registry and the private Helm repository is enforced, and `ClusterConfig` is updated to `true`.

| `private_registry=false` +
`private_helm_repo=false`, with the cluster already upgraded without `--private`
| Relaunching with `--private`
| The chart images and the Cluster API provider images move to the private registry, even when they are already on their target version, and `ClusterConfig` is updated to `true`.
|===

[#_origen_de_charts_e_imágenes]

==== Origin of charts and images

* _cluster-operator_ chart: always from `KeosCluster.spec.helm_repository.url`.
* The rest of the charts: also from `KeosCluster.spec.helm_repository.url`, when `ClusterConfig.spec.private_helm_repo` is `true` or when `--private` is passed; when not, from their public repository.
* Images: from the registry with `keos_registry: true` in `KeosCluster.spec.docker_registries`, when `ClusterConfig.spec.private_registry` is `true` or when `--private` is passed; when not, from the public registries.

TIP: Use `--private` only when private repositories are to be used, and either of the two `ClusterConfig` fields is set to `false`. When both are already on `true`, the option changes nothing.

TIP: Before the actual upgrade, always run the script with `--dry-run` to detect obvious problems without risk: an invalid Ansible Vault password or cloud credentials, the `clusterctl` version, and health-check issues, which are listed without aborting. Since it does not download any chart or check the registry, it does not detect a missing chart or image. In addition, a `--dry-run` without errors *does not guarantee* that the actual upgrade will complete without problems: the mode simulates without running any command that modifies the cluster (`apply`, `patch`, `delete`, `scale`, `create`, `annotate`, `label`, and `clusterctl upgrade apply`), so no failure that only appears on applying those changes for real is tested (a webhook that rejects a specific patch, a reconciliation of a `HelmRelease` that fails, or an actual `clusterctl upgrade apply`).

[#_prompts_interactivos]

=== Interactive prompts

The script may ask for up to three keyboard confirmations, in this order. With `--dry-run`, it only asks for the second:

. *Continue with the upgrade*: at the start, after the previous cluster checks. Press Enter to continue; to abort, type anything else and press Enter. It is skipped with `-y`/`--yes`.
. *Helm repository*: right afterward. Shows the repository configured in `KeosCluster.spec.helm_repository.url` and lets you specify a new one. Press Enter to keep the current one. *It cannot be skipped*: it is asked every time, even with `-y`.
. *`k8s_version` change* (only when `KeosCluster.spec.k8s_version` is going to change): appears when reaching the Kubernetes upgrade, when the charts and Cluster API are already upgraded. It asks for an explicit `[y/N]` confirmation before applying the patch. The uppercase `N` indicates the default response: when Enter is pressed without typing anything, the response is "no". The accepted responses are `y`, `yes`, `n`, and `no`, and they are not case-sensitive. When the response is `n` or left blank, only this step is canceled (the rest of the upgrade continues). It is skipped with `--start-from-k8s-version`. In Azure VMs, the image map is validated before this question; if it is incorrect, the script aborts, even if the response is `n`.
+
To stop the upgrade at this point, respond `n`. The script restores the `KeosCluster` webhooks, starts up its controller, resumes the `HelmRelease`, waits for the `KeosCluster` to be ready, returns cluster-autoscaler to the replicas it had at the start, performs the rest of the post-upgrade of your environment (in EKS, `mp_role_name` and `cluster-autoscaler-aws` with 0 replicas; in Azure VMs, the cloud-provider-azure image) and ends, without changing the Kubernetes version. The version change can be performed later, in another execution. *Do not use `Ctrl+C` at this question*: the script is in the critical section and its recovery is not run, so the `KeosCluster` webhooks would be left disabled and the `HelmRelease`, suspended.

WARNING: When a different Helm repository is indicated, the script saves it in `KeosCluster.spec.helm_repository.url` and in the `keos` `HelmRepository`, and uses it for the _cluster-operator_ chart and, when it is a private repository, for the rest of the charts. Change this value only when the new repository publishes the same Universe of versions (`kubernetes-universe`) that corresponds to this version of _Stratio Cloud Provisioner_: a repository from another Universe may resolve chart versions that are incompatible with each other.

== General description of the upgrade process

This section summarizes, in order, the phases that the script goes through when running. There is no need to run any of these steps; you only need to respond to the prompts (see <<_prompts_interactivos, interactive prompts>>).

. *Validation*
** Checks the `clusterctl` version, verifies that the secrets and the _kubeconfig_ exist, and decrypts the secrets.
** Configures the cloud provider credentials and checks access to the cluster. In EKS and in GKE, regenerates the _kubeconfig_ when it does not grant access.
** In GKE, adds the `event-exporter-gke` pods to the exceptions of the IMDS _GlobalNetworkPolicy_ when they are not there, and restarts the pod. It is the only change before the initial confirmation.
** Performs the automatic health check (see the <<_automatic_check, automatic check>>).
** Asks for the initial confirmation (see the <<_prompts_interactivos, interactive prompts>>).
** In EKS with cluster-autoscaler, creates the cluster-autoscaler IAM policy when it does not exist, associates it with the `eks-nodegroup` and `nodes` roles, and allows IMDS access to its pods. If either role is missing, it shows a `[WARN]` and continues. Any other error in the IAM policy or in the IMDS _GlobalNetworkPolicy_ stops the script at this step.
** Asks for the Helm repository.

. *Pre-upgrade*
** When cluster-autoscaler is deployed, scales it to 0 to prevent automatic scaling during the upgrade. In GKE, it is not deployed.
** In EKS, applies the `aws-node` and cluster-autoscaler permissions that may be missing in clusters created with earlier versions.
+
NOTE: When upgrading its chart, cluster-autoscaler reverts to 2 replicas until the other charts finish. Afterward, the script scales it to 0 again and keeps it that way until the end.

. *Backup* (unless with `--disable-backup`)
** CAPX components (with `clusterctl move`).
** Configurations of the Capsule webhooks.
** Secrets of the CAPX namespaces.

. *Capsule preparation*
** Temporarily excludes the system namespaces from the Capsule admission webhooks so they do not block the chart upgrade in the next step.

. *Upgrade of the charts*
** Upgrades the common charts (cert-manager, cluster-autoscaler, cluster-operator, flux2, and tigera-operator) and the provider charts: aws-load-balancer-controller in EKS (when installed) and azuredisk-csi-driver, azurefile-csi-driver, and cloud-provider-azure in Azure VMs (see <<_what_is_upgraded, what is upgraded>>). When any of these charts is not in the cluster, the script skips it; for example, aws-load-balancer-controller, which is optional in EKS, or cluster-autoscaler, when the cluster was created without it.
** In EKS and in Azure, sets the upstream image `v1.35.3` on cluster-autoscaler: `registry.k8s.io/autoscaling/cluster-autoscaler` without a private registry, and `<registry>/autoscaling/cluster-autoscaler` with a private registry (`<registry>/k8s/autoscaling/cluster-autoscaler` with the ECR pull-through cache).
** Keeps the override values (`02-<release>-helm-chart-override-values` `ConfigMap`) of each chart.
** On finishing the charts, scales cluster-autoscaler to 0 again, when it is deployed.
** Undoes the exclusion of the Capsule webhooks.

. *_cluster-operator_ preparation*
** When the `HelmRelease` of _cluster-operator_ was left suspended in an earlier execution, resumes it. Afterward, it waits up to 5 minutes for it to be ready.
** Suspends the `HelmRelease` of _cluster-operator_.
** Checks that the `KeosCluster` is ready (`ready`) and in the `Provisioned` phase before entering the critical section.
** Stops the `keoscluster-controller-manager` deployment.
** Backs up the configurations of the `KeosCluster` webhooks.
** Disables the `KeosCluster` validation and mutation webhooks.
** Updates `ClusterConfig` with the new component versions.

. *CAPI upgrade*
+
[source,bash]
----
clusterctl upgrade apply \
  --core cluster-api:v1.10.10 \
  --infrastructure <provider>:<version> \
  --wait-providers
----
+
`<provider>:<version>` is `aws:v2.9.3` in EKS, `azure:v1.21.3` in Azure VMs, and `gcp:1.6.1-0.4.3` in GKE.
+
It is skipped when all the providers are already on their target version and, in private mode (see the <<_use_of_the_private_option, use of the `--private` option>>), their images come from the private registry. Beforehand, when cert-manager is managed with Helm, the script removes the `clusterctl` label from it, so that `clusterctl` does not replace it. Afterward, it returns the CAPI and provider controllers to 2 replicas, with `priorityClassName: system-node-critical`.
+
NOTE: On Azure VMs, the command also includes the `--bootstrap kubeadm:v1.10.10` and `--control-plane kubeadm:v1.10.10` parameters. EKS and GKE manage their own _control-plane_ and do not need to upgrade these providers, but Azure VMs use `KubeadmControlPlane`, the CAPI kubeadm _control-plane_ provider, which must be upgraded separately.

. *Kubernetes version upgrade*: each environment performs it in a different way. See the "Before starting" section of the procedure for your environment.

. *Post-upgrade*
** Restores the `KeosCluster` webhooks, starts up `keoscluster-controller-manager` again, and resumes the `HelmRelease` of _cluster-operator_.
** Checks that the _control-plane_ is on the new Kubernetes version and that _cluster-operator_ is ready. In EKS, the worker nodes do not change: the _MachineDeployment_ groups stay on version 1.32.
** When cluster-autoscaler is deployed, it returns to the replicas it had at the start, or to 2 when it was at 0.
** In EKS, when `spec.control_plane.aws.mp_role_name` is empty and the `eks-nodegroup.cluster-api-provider-aws.sigs.k8s.io` role exists, waits for the `KeosCluster` to be ready and assigns that role to the field. If it cannot, it logs a `[WARN]` with the command to correct it manually and exits in any case.
** In Azure VMs, sets on cloud-provider-azure (`cloud-controller-manager` and `cloud-node-manager`) the image of the Kubernetes version that the cluster has on finishing (for example, `v1.35.9` on 1.35), and waits for it to be deployed.
** In EKS with cluster-autoscaler, it installs a second instance, `cluster-autoscaler-aws`, with the `aws` provider and 0 replicas: it is installed but not run. The existing instance continues to scale the _MachineDeployment_ groups.

== Final verification

* Check the images of the cluster pods:
+
[source,bash]
----
kubectl get pods -A -o json \
| jq -r '
  .items[]
  | (
      [.spec.containers[]?.image] +
      [.spec.initContainers[]?.image]
    )
  | .[]
' \
| sort -u
----
+
*Expected versions:* the images of the CAPI and provider controllers (`capi-controller-manager`, `capa-controller-manager`, `capz-controller-manager`, or `capg-controller-manager` and, in Azure VMs, the two kubeadm controllers) include the versions from the <<_what_is_upgraded, what is upgraded>> table. A chart's version is not the same as its images' versions; the charts are checked in the next step.

* Check the versions of the charts:
+
[source,bash]
----
kubectl get hr -A -o json \
| jq -r '
  .items[]
  | "\(.metadata.namespace)/\(.metadata.name) -> \(.spec.chart.spec.chart)@\(.spec.chart.spec.version)"
' \
| sort -u
----
+
*Expected versions:* those of the <<_what_is_upgraded, what is upgraded>> table. The script does not modify the other charts of the cluster.

* Check the final state:
+
[source,bash]
----
kubectl get keoscluster -A -o custom-columns=NAME:.metadata.name,K8S_VERSION:.spec.k8s_version,READY:.status.ready
kubectl get nodes -o custom-columns=NAME:.metadata.name,VERSION:.status.nodeInfo.kubeletVersion
kubectl logs -n capi-system -l cluster.x-k8s.io/provider=cluster-api --tail=-1 --since=1h | grep '^E'
kubectl logs -n kube-system -l app.kubernetes.io/name=keoscluster-controller-manager --tail=-1 --since=1h | grep -P '\tERROR\t'
----
+
*Expected output:* `K8S_VERSION` is the target version, and `READY` is `true`. Review the logs for errors before considering the upgrade finished. In the Cluster API logs, the `Unauthorized` or `connection to the workload cluster is down` errors may appear while the _control-plane_ changes version; they are only a problem when they continue to appear after the upgrade has finished. What changes in each environment are in the "Subsequent checks" section of its procedure.
