= Operations manual

== Obtaining the kubeconfig

To communicate with the _API Server_ of the created cluster, you need a kubeconfig file, which you obtain differently depending on the cloud provider and the cluster's _control-plane_ management.

* For EKS, it will be obtained in the way indicated by AWS:
+
[source,bash]
----
aws eks update-kubeconfig --region eu-west-1 --name <cluster_name> --kubeconfig ./<cluster_name>.kubeconfig
----

* For GKE, it will be obtained in the way indicated by GCP:
+
[source,bash]
----
gcloud container clusters get-credentials <cluster_name> --region <region> --project <project>
----
+
This command will generate the kubeconfig file in the kubeconfig location indicated by the `KUBECONFIG` environment variable. By default, it will be in `$HOME/.kube/config`.

* For unmanaged Azure, upon finishing provisioning, the kubeconfig is left in the execution directory (workspace):
+
[source,bash]
----
ls ./.kube/config
./.kube/config
----
+
In turn, the "kw" alias can be used from the local container to interact with the worker cluster (on EKS, the token used only lasts 10 minutes):
+
[source,bash]
----
root@example-azure-control-plane:/# kw get nodes
NAME                                STATUS   ROLES           AGE   VERSION
example-azure-control-plane-6kp94   Ready    control-plane   60m   v1.26.8
example-azure-control-plane-fgkcc   Ready    control-plane   63m   v1.26.8
...
----

== Authentication on EKS

Although it is not part of the _Stratio KEOS_ operation, it is important to highlight the way to allow the https://docs.aws.amazon.com/es_es/eks/latest/userguide/add-user-role.html[authentication of other users on an EKS cluster] (the user who created the cluster is authenticated by default).

To grant `kubernetes-admin` permissions on the cluster, add the ARN of the user to the _ConfigMap_ indicated below.

[source,bash]
----
$ kubectl -n kube-system edit cm aws-auth
..
data:
  mapUsers: |
    - groups:
      - system:masters
      userarn: <user_arn>
      username: kubernetes-admin
----

== Enable authorization through assume role in AWS for an EKS cluster

This procedure describes how to enable the assume-role authorization method on an already created EKS cluster.

=== Prerequisites

Before beginning, make sure you meet the following:

* Have an IAM role created with the necessary permissions (for example: _stratio-assume-role_).
** Role type: _AWS Account_.
** Permissions: the same as those described in the EKS prerequisites.
* Configure the _Trust Relationship_ of the role to allow the user who deployed the cluster to assume it.
+
_Trust Relationship_ example:
+
[source,json]
----
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::123456789012:user/stratio-user"
      },
      "Action": "sts:AssumeRole"
    }
  ]
}
----

* Assign the user a policy that includes the `sts:AssumeRole` action on the corresponding role.
+
Policy example:
+
[source,json]
----
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "sts:AssumeRole",
      "Resource": "arn:aws:iam::123456789012:role/stratio-assume-role"
    }
  ]
}
----

NOTE: The minimum version of _cluster-operator_ compatible with this method is 0.5.2.

=== Configure assume role on the EKS cluster

NOTE: Replace the account, the cluster name (`eks-cl01`), and the namespace (`cluster-eks-cl01`) with those of your environment.

. Create the `AWSClusterRoleIdentity` object.
+
[source,yaml]
----
apiVersion: infrastructure.cluster.x-k8s.io/v1beta2
kind: AWSClusterRoleIdentity
metadata:
  name: eks-cl01-role-identity
spec:
  roleARN: arn:aws:iam::123456789012:role/stratio-assume-role
  sessionName: eks-cl01-role-identity-session
  durationSeconds: 3600
  sourceIdentityRef:
    kind: AWSClusterControllerIdentity
    name: default
  allowedNamespaces:
    list:
    - cluster-eks-cl01
----

. Associate the `AWSClusterRoleIdentity` identity with the `AWSManagedControlPlane`.
+
[source,bash]
----
kubectl patch awsmanagedcontrolplane eks-cl01-control-plane \
  -n cluster-eks-cl01 \
  --type='merge' \
  -p '{"spec":{"identityRef":{"kind":"AWSClusterRoleIdentity","name":"eks-cl01-role-identity"}}}'
----

. Restart the `capa-controller-manager` deployment for the changes to take effect.
+
[source,bash]
----
kubectl rollout restart deployment capa-controller-manager -n capa-system
----

. Edit the `aws-auth` _ConfigMap_ to add the `iam_role`.
+
[source,yaml]
----
  mapRoles: |
    - groups:
      - system:bootstrappers
      - system:nodes
      rolearn: arn:aws:iam::123456789012:role/nodes.cluster-api-provider-aws.sigs.k8s.io
      username: system:node:{{EC2PrivateDNSName}}
    - groups:
      - capa-manager
      rolearn: arn:aws:iam::123456789012:role/stratio-assume-role
      username: stratio-assume-role
----

. Create the `ClusterRoleBinding` for the `capa-manager` group.
+
[source,bash]
----
kubectl apply -f - <<EOF
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: capa-manager-access
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: capa-manager-role
subjects:
- kind: Group
  name: capa-manager
  apiGroup: rbac.authorization.k8s.io
EOF
----

. Add permissions to the `ClusterRole` of the `capa-manager` group.
+
[source,bash]
----
kubectl patch clusterrole capa-manager-role \
  --type='json' \
  -p='[
    {"op": "add", "path": "/rules/-", "value": {"apiGroups":["apps"],"resources":["daemonsets"],"verbs":["get","list","watch","update"]}},
    {"op": "add", "path": "/rules/-", "value": {"apiGroups":[""],"resources":["pods"],"verbs":["get","list","watch"]}},
    {"op": "add", "path": "/rules/-", "value": {"apiGroups":[""],"resources":["nodes"],"verbs":["get","list","watch","patch"]}},
    {"op": "add", "path": "/rules/-", "value": {"apiGroups":[""],"resources":["pods/eviction"],"verbs":["create"]}}
  ]'
----

. Update the _cluster-operator_.
.. Update the _HelmRelease_ associated with the _cluster-operator_ to version 0.5.2 or higher.
.. Update the _ConfigMap_ corresponding to that version.
... Modify the tag in `00-cluster-operator-helm-chart-default-values` with the desired version, e.g., 0.5.2.
.. Patch the _keoscluster-settings_ secret to add the `role_arn`.
+
[source,bash]
----
kubectl -n kube-system patch secret keoscluster-settings \
  --type=json \
  -p='[{"op":"replace","path":"/data/credentials","value":"'$(kubectl -n kube-system get secret keoscluster-settings -o jsonpath="{.data.credentials}" | base64 -d | awk 'BEGIN{ORS="\n"} {print} END{print "role_arn = arn:aws:iam::123456789012:role/stratio-assume-role"}' | base64 -w0)'"}]'
----

. Verify the configuration and permissions.
+
[source,bash]
----
# Review the capi/capa logs
kubectl logs -f -n capa-system deployment/capa-controller-manager (or the pod name)
kubectl logs -f -n capi-system deployment/capi-controller-manager (or the pod name)

# Review the cluster-operator logs
kubectl logs -f -n kube-system deployment/keoscluster-controller-manager (or the pod name)

# Check state and configuration
kubectl get awsclusterroleidentity
kubectl get awsmanagedcontrolplane -n cluster-eks-cl01
kubectl get configmap aws-auth -n kube-system -o yaml

# Verify the role permissions
kubectl auth can-i get nodes --as=stratio-assume-role --as-group=capa-manager
kubectl auth can-i list nodes --as=stratio-assume-role --as-group=capa-manager
kubectl auth can-i list pods --as=stratio-assume-role --as-group=capa-manager
kubectl auth can-i update daemonsets --as=stratio-assume-role --as-group=capa-manager
----

[NOTE]
====
If the user who performs the assume role is updated, the following secrets must be updated with the new credentials and, if applicable, with the new role ARN:

* _capa-manager-bootstrap-credentials_ (for CAPA).
* _keoscluster-settings_ (for the _cluster-operator_).
====

=== Cluster operations with assume role

Once activated, you can also manage the cluster using assume-role from the command line by following these steps:

. *Verify AWS CLI*: check with this command that you have the latest version installed.
+
[source,bash]
----
aws --version
----

. *Export the AWS profile*.
+
[source,bash]
----
export AWS_PROFILE=<profile-name>
----

. *Assume the role and save the credentials*.
+
[source,bash]
----
aws sts assume-role \
  --role-arn arn:aws:iam::<accountID>:role/<role-name> \
  --role-session-name eks-session > creds.json
----

. *Export the temporary credentials*.
+
[source,bash]
----
export AWS_ACCESS_KEY_ID=$(jq -r '.Credentials.AccessKeyId' creds.json)
export AWS_SECRET_ACCESS_KEY=$(jq -r '.Credentials.SecretAccessKey' creds.json)
export AWS_SESSION_TOKEN=$(jq -r '.Credentials.SessionToken' creds.json)
----

. *Update the kubeconfig*.
+
[source,bash]
----
aws eks update-kubeconfig --region <region> --name <cluster-name>
----

== Operation of the infrastructure

image::controllers.png[]

_Stratio KEOS_ enables several advanced operations by interacting with the _Stratio Cluster Operator_ (infrastructure as code, or IaC), which, in its reconciliation cycle, interacts with the different providers to perform the requested operations.

=== Self-healing

image::self-healing.png[]

The self-healing capability of the cluster is managed by the _MachineHealthCheck_ resource:

[source,bash]
----
$ kubectl -n cluster-example get mhc -o yaml
...
  spec:
    clusterName: example
    maxUnhealthy: 100%
    nodeStartupTimeout: 5m0s
    selector:
      matchLabels:
        keos.stratio.com/machine-role: example-worker-node
    unhealthyConditions:
    - status: Unknown
      timeout: 1m0s
      type: Ready
    - status: "False"
      timeout: 1m0s
      type: Ready
...
----

NOTE: On unmanaged Azure, there will be a _MachineHealthCheck_ for the _control-plane_ and another for the worker nodes, while on managed ones (EKS, GKE) there will only be the second one.

==== Fault tolerance test on a node

If a node fails, a controller detects it and replaces it: it deletes it and creates another node in the same group, ensuring it maintains the same characteristics.

To simulate a failure on a virtual machine, delete it from the cloud provider's web console.

The recovery of the node comprises the following phases and estimated times (which may vary according to the provider and the flavor):

[source,text]
----
. Terminate VM from console: 0s
. New VM is Provisioning: 50s
. Old Machine is Deleted & the new one is Provisioned: 1m5s
. New Machine is Running & new k8s node is NotReady: 1m 50s
. New k8s node is Ready: 2m
----

=== Static scaling

Although the manual scaling of an existing node group is discouraged, these operations are presented for cases without autoscaling or for new node groups.

==== Scale a worker group

image::escalado-manual.png[]

To manually scale a worker group, the _KeosCluster_ resource is used:

[source,bash]
----
kubectl -n cluster-example-eks edit keoscluster
----

[source,yaml]
----
spec:
  ...
  worker_nodes:
    - name: eks-prod-xlarge
      quantity: 9
      ...
----

Verify the change by consulting the state of the _KeosCluster_ resource:

[source,bash]
----
kubectl -n cluster-<cluster_name> get keoscluster <cluster_name> --subresource=status
----

==== Create a new worker group

To create a new node group, simply add a new element to the _worker++_++nodes_ array of the _KeosCluster_ resource:

[source,yaml]
----
spec:
  ...
  worker_nodes:
    - ...
    - name: eks-prod-xlarge
      quantity: 6
      max_size: 18
      min_size: 6
      size: m6i.xlarge
      labels:
        disktype: standard
      root_volume:
        size: 50
        type: gp3
        encrypted: true
      ssh_key: stg-key
----

Again, verify the change by consulting the state of the _KeosCluster_ resource:

[source,bash]
----
kubectl -n cluster-<cluster_name> get keoscluster <cluster_name> --subresource=status
----

==== Vertical scaling

Vertical scaling for a node group is done by modifying the instance type of the _KeosCluster_ resource associated with that group.

[source,yaml]
----
spec:
  ...
  worker_nodes:
    - name: eks-prod-xlarge
      size: m6i.2xlarge
      ...
----

=== Autoscaling

image::autoescalado.png[]

For node autoscaling, _cluster-autoscaler_ detects pods pending due to a lack of resources and scales the node group it deems necessary based on deployment filters.

This operation runs on the _API Server_, where the controllers create virtual machines on the cloud provider and add them to the cluster as Kubernetes worker nodes.

Since autoscaling is based on _cluster-autoscaler_, the minimum and maximum in the node group will be added in the _KeosCluster_ resource:

[source,yaml]
----
spec:
  ...
  worker_nodes:
    - name: eks-prod-xlarge
      min_size: 6
      max_size: 21
      ...
----

==== Test

To test the autoscaling, a _Deployment_ can be created with enough replicas so that they cannot be scheduled on the current nodes:

[source,bash]
----
kubectl create deploy test --replicas 1500 --image nginx:alpine
----

Upon finishing the test, the _Deployment_ is deleted:

[source,bash]
----
kubectl --kubeconfig demo-eks.kubeconfig delete deploy test
----

==== Logs

The _cluster-autoscaler_ logs can be viewed from its _Deployment_:

[source,bash]
----
kubectl -n kube-system logs -f -l app.kubernetes.io/name=clusterapi-cluster-autoscaler
----

=== Kubernetes upgrade

The upgrade will be performed in two parts within the same atomic process: first the _control-plane_, and once it is on the new version, the worker nodes, iterating through each group and upgrading them one by one.

CAUTION: Upgrading the Kubernetes version of nodes on clusters where the image has not been specified may also upgrade the operating system.

image::upgrade-cp.png[]

image::upgrade-w.png[]

[CAUTION]
====
A poorly configured Pod Disruption Budget (PDB) may prevent deleting a pod. This happens if the PDB requires at least one available replica, but the resource has only one deployed replica. In that case, you can't delete the replica or drain the node, which may affect upgrades.

To avoid this problem:

. Make sure that the deployments have more than one replica if the PDB requires at least one available replica.
. Before upgrading the cluster, review the PDBs to avoid blocks.
. If a resource has only one replica, you can temporarily delete the PDB to upgrade it.

On EKS, for example, it is advisable to check whether the `coredns` PDB exists in the `kube-system` namespace and delete it before upgrading the cluster:

[source,bash]
----
kubectl -n kube-system get poddisruptionbudget coredns
kubectl -n kube-system delete poddisruptionbudget coredns
----

====

==== Prerequisites

Upgrade a cluster in production environments, especially unmanaged flavors, with extreme caution. In particular, before upgrading, it is recommended to make a backup of the objects that manage the infrastructure with the following command:

[source,bash]
----
clusterctl --kubeconfig ./kubeconfig/path move -n cluster-<cluster_name> --to-directory ./backup/path/
----

For a managed _control-plane_, verify that the provider supports the desired Kubernetes version.

===== EKS

Before upgrading EKS, make sure that the desired version is supported. To do so, you can use the following command:

[source,bash]
----
aws eks describe-addon-versions | jq -r ".addons[] | .addonVersions[] | .compatibilities[] | .clusterVersion" | sort -nr | uniq | head -4
----

===== Unmanaged Azure

The _GlobalNetworkPolicy_ created for the _control-plane_ during the _Stratio KEOS_ installation phase must be modified to *temporarily allow network traffic between all nodes* during the version upgrade.

Once finished, the internal IPs of the nodes and the tunnel IPs assigned to those nodes must be updated:

[source,bash]
----
kubectl get nodes -l node-role.kubernetes.io/control-plane= -ojson | jq -r '.items[].status.addresses[] | select(.type=="InternalIP").address + "\/32"'
----

[source,bash]
----
IPAMHANDLERS=$(kw get ipamhandles -oname | grep control-plane)
for handler in $IPAMHANDLERS; do kw get $handler -o json | jq -r '.spec.block | keys[]' | sed 's/\/.*/\/32/'; done
----

==== Start the upgrade

To start the upgrade, once the prerequisites are satisfied, a patch of _spec.k8s++_++version_ will be executed on the _KeosCluster_ resource:

[source,bash]
----
kubectl -n cluster-<cluster_name> patch KeosCluster <cluster_name> --type merge -p '{"spec": {"k8s_version": "v1.32.x"}}'
----

NOTE: The controller provisions a new node of the worker group with the updated version and, once it is _Ready_ in Kubernetes, deletes a node with the previous version. This way, the configured number of nodes is guaranteed.

==== Verification of etcd

One way to ensure etcd is correct after upgrading an unmanaged _control-plane_ is to open a terminal on any etcd pod, verify the cluster state, and compare the IP addresses of the registered members with those of the _control-plane_ nodes.

[source,bash]
----
k -n kube-system exec -ti etcd-<control-plane-node> sh

alias e="etcdctl --cert=/etc/kubernetes/pki/etcd/server.crt --key=/etc/kubernetes/pki/etcd/server.key --cacert=/etc/kubernetes/pki/etcd/ca.crt "
e endpoint status
e endpoint status -w table --cluster
e member list
e member remove <member-id>
----

=== Deletion of the cluster

[NOTE]
.Previous considerations
====
Before deleting the cloud provider resources generated by _Stratio Cloud Provisioner_, delete those created by _keos-installer_ or any external automation (for example, _Services_ of type _LoadBalancer_).

In addition, the process requires the `clusterctl` binary on the bastion machine (any computer with access to the _API Server_) where it will run.
====

Execute the following steps to carry out the deletion of the cluster:

. Create a local cluster, indicating that no resource must be created on the cloud provider.
+
[source,bash]
----
[bastion]$ sudo ./bin/cloud-provisioner create cluster --name <cluster_name> --descriptor cluster.yaml --vault-password <my-passphrase> --avoid-creation
----

. Pause the _Stratio Cluster Operator_ controller:
+
[source,bash]
----
[bastion]$ kubectl --kubeconfig $KUBECONFIG -n kube-system scale deployment keoscluster-controller-manager --replicas 0
----

. Move management of the worker cluster to the local cluster using the corresponding kubeconfig (for managed _control-planes_, you'll need the provider's kubeconfig). To confirm this step, look for the following text in the output of the command: "Moving Cluster API objects Clusters=1".
+
[source,bash]
----
[bastion]$ sudo clusterctl --kubeconfig $KUBECONFIG move -n cluster-<cluster_name> --to-kubeconfig /root/.kube/config
----

. Access the local cluster and delete the worker cluster.
+
[source,bash]
----
[bastion]$ sudo docker exec -ti <cluster_name>-control-plane bash
root@<cluster_name>-control-plane:/# kubectl -n cluster-<cluster_name> delete cl --all
cluster.cluster.x-k8s.io "<cluster_name>" deleted
root@<cluster_name>-control-plane:/#
----

. Finally, delete the local cluster.
+
[source,bash]
----
[bastion]$ sudo ./bin/cloud-provisioner delete cluster --name <cluster_name>
----

== Troubleshooting

=== Reconciliation loop on GKE due to automatic labels

On clusters managed with the Cluster API Provider GCP (CAPG), the CAPG controller responsible for the `GCPManagedMachinePool` resource may enter an infinite reconciliation loop if it detects discrepancies between the labels (`additional_labels`) defined in the object specification (or not defined) and the labels actually present in the GKE node pool. This behavior appears in the logs as repeated messages like `Node pool config update required` and `Node pool config updating in progress`. This is a known CAPG issue related to label reconciliation in node pools managed by the `GCPManagedMachinePool` object.

The main cause is that Google Cloud GKE automatically adds labels to the node pools (for example, `goog-gke-node-pool-provisioning-model: on-demand`) that are not present by default in the `GCPManagedMachinePool` resource generated by Cluster API. This value is just an example: it can be any label added by Google.

To resolve this and stop the loop, manually add the label in the `KeosCluster` configuration to match the one applied by the provider. You can follow these steps:

. Edit the `KeosCluster` resource:
+
[source,bash]
----
kubectl edit keoscluster <cluster_name> -n <namespace>
----

. Add the label in the _additional++_++labels_ field of the definition of the `worker_nodes`:
+
[source,yaml]
----
spec:
  ...
  worker_nodes:
    - name: <node_pool_name>
      ...
      additional_labels:
        "goog-gke-node-pool-provisioning-model": "on-demand"
----

CAUTION: Modifying the _additional++_++labels_ field in the `worker_nodes` of a `KeosCluster` managed by CAPG will cause the recreation of the nodes associated with the node pool. This means the current nodes will be deleted and replaced with new ones with the updated configuration. Plan this operation to avoid interruptions or impacts to the service.

==== Clusters created with _Stratio Cloud Provisioner_ 0.7.x

On clusters created with _Stratio Cloud Provisioner_ 0.7.x, the `KeosCluster` object does not support the _additional++_++labels_ field, which was added in version 0.8.0; while the cluster is not _ready_, you also cannot modify its specification. In that case, add the label directly on the `GCPManagedMachinePools` of the cluster, with the same value that GKE shows for the node pool:

[source,bash]
----
gcloud container node-pools describe <node_pool_name> --cluster <cluster_name> --region <region> \
  --format='value(config.resourceLabels)'

for mp in $(kubectl -n cluster-<cluster_name> get gcpmanagedmachinepool -o name); do
  kubectl -n cluster-<cluster_name> patch $mp --type=merge \
    -p '{"spec":{"additionalLabels":{"goog-gke-node-pool-provisioning-model":"on-demand"}}}'
done
----

When the `KeosCluster` returns to `READY = true` and the cluster is on a version that supports the field, also declare the label in the _additional++_++labels_ of each group of the `KeosCluster`, as indicated above, so that it is maintained if _cluster-operator_ regenerates the `GCPManagedMachinePool`.
