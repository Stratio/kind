= Upgrade from 0.7.x to 0.9.x

This fact sheet summarizes the impact of upgrading _Stratio Cloud Provisioner_ from 0.7.x to 0.9.x, the upgrade that accompanies the move to Universe 15.1 from 14.8.x, 14.9.x, or 14.10.x on cloud deployments. It includes the Kubernetes jump from 1.32 to 1.35, which in these environments is _Stratio Cloud Provisioner_'s responsibility and not _Stratio KEOS_'. Use it to plan the maintenance window, to know what to prepare beforehand, and to know what to check afterwards.

Each section answers one question and links to the page that details the procedure. When the maintenance window starts, follow the xref:operations-manual:upgrade.adoc[upgrade procedure] step by step.

IMPORTANT: _Stratio Cloud Provisioner_ owns the cluster's infrastructure and its Kubernetes version, so *its window goes first*: the _Stratio KEOS_ upgrade from 1.2.x to 1.4 comes afterwards, in a separate window. See <<modules,Relationship with other modules>>.

[#summary]

== Summary

IMPORTANT: *The upgrade does not stop the cluster, but it does replace every worker node.* The infrastructure is immutable: raising a node's Kubernetes version does not upgrade it in place, it creates a new one and retires the old one. Every workload with a single replica is down while it is rescheduled and, unlike on-premise installations, here *a badly sized Pod Disruption Budget blocks the node drain*: the component that drains is Cluster API, which honors the eviction API and never forces. Size the window by the number of nodes and review the PDBs before opening it.

IMPORTANT: *In the cloud there are two windows.* This upgrade leaves the cluster on Kubernetes 1.35 with _Stratio KEOS_ still on 1.2.x; the final state arrives with the _Stratio KEOS_ window, which comes afterwards.

The table answers, with one row per decision, what you need in order to size the window:

[cols="2,3,1", options="header"]
|===
| Question | Answer | Detail

| How much downtime is there in the worst case?
| *None at cluster level, but there is per component.* On EKS and on GKE the control plane is raised by the provider, with no node replacement. On Azure VMs the `KubeadmControlPlane` replicas are replaced one at a time, and with them the etcd members: with three replicas the _API Server_ keeps answering. Worker nodes are replaced group by group, and every workload hosted on them is rescheduled; the ones with a single replica are down until they start on another node.
| <<outage,Downtime>>

| What does the duration depend on?
| On the *number of nodes* and on the *number of minor version jumps*, which are three: 1.32 → 1.33 → 1.34 → 1.35. On Azure VMs the control plane goes through all three explicitly, with a settle time between them; on EKS and on GKE the provider steps them internally.
| <<phases,Steps>>

| How long is the maintenance window in total?
| Pending. No duration has been measured. The script reports the real elapsed time when it finishes, so the first run in preproduction already gives you a figure to plan with.
| <<phases,Steps>>

| Can the work be split across several windows?
| *No, except for the Kubernetes jump.* It is a single run that chains the charts, Cluster API, and the version jump, with a critical section in which `cluster-operator`'s webhooks are disabled: you have to reach the end. The only separable part is the Kubernetes jump, which asks for its own confirmation and can be left for another window by answering no.
| <<phases,Steps>>

| Does anything stop working until another module is upgraded?
| *Yes, by design of the order.* When this window closes, _Stratio KEOS_ 1.2.x keeps running on Kubernetes 1.35 until its own upgrade runs. That is an expected intermediate state, not a final one.
| <<modules,Relationship with other modules>>

| Does the data model change, and is a backup needed?
| There is no application data migration: the provider's volumes survive the node replacement. What does change, *on Azure VMs only*, is the control plane's etcd, which goes from the v3.5 series to the v3.6 series and cannot be reverted. The backup of the Cluster API objects *is taken by the script itself* at the start, and does not have to be requested.
| <<data,Data and consistency>>

| Can you go back at any point?
| *No.* There is no version rollback: `cluster-operator`'s webhook rejects lowering `k8s_version`, and there is no procedure for downgrading the Cluster API providers. Before launching the script, not continuing is enough; afterwards, the way out is forwards.
| <<rollback,Rollback>>

| Does the previous version work on Universe 15.1?
| _Stratio Cloud Provisioner_ does not run inside the cluster as one more application: it is the tool that provisions it and the `cluster-operator` that reconciles it. What matters is that the modules running on top, _Stratio KEOS_ 1.2.x included, keep working on the upgraded cluster.
| <<coexistence,Version coexistence>>

| What is the overall risk?
| *High.* There is no rollback, the Kubernetes jump is irreversible, a badly sized PDB blocks the drain with nothing forcing it, on Azure VMs the control plane's network policy is temporarily opened, and there is a critical section where a failure can leave the cluster with `cluster-operator`'s webhooks disabled and its controller stopped.
| <<known-issues,Known issues>>
|===

.Message to communicate
[caption=]
====
The platform raises the cluster's Kubernetes version. It does not stop: nodes are replaced one by one with new ones running the new version, and applications are rescheduled between them. Services with a single replica will be unresponsive for a few minutes when their turn to change node comes, so it is worth checking beforehand that everything important has more than one. The window is sized by the number of nodes in the cluster. After this intervention a second one will be needed, the _Stratio KEOS_ upgrade, for the environment to reach its final version.
====

[#scope]

== Scope of the upgrade

All three source Universes carry _Stratio Cloud Provisioner_ 0.7.x and Kubernetes 1.32, so the procedure is the same for all three.

The supported source version is 0.7.x, which is the one the upgrade script itself declares. Note that *nothing validates it*: the script does not check which version the cluster comes from, so running it against an earlier source does not abort, it simply is not supported. If the cluster comes from an earlier version, upgrade it to 0.7.x first.

The upgrade is only supported on three environments, and any other combination of provider and control-plane type is rejected:

* *EKS* on Amazon Web Services, with a managed control plane.
* *Azure VMs* on Microsoft Azure, with an unmanaged control plane. Microsoft AKS is not supported.
* *GKE* on Google Cloud Platform, with a managed control plane.

Out of scope for this fact sheet is the migration of `MachineDeployment` node groups to `MachinePool`, which is a separate, assisted, EKS-only operation that comes after this upgrade: see xref:operations-manual:upgrade.adoc#_eks_clusters_with_machinepools[EKS clusters with MachinePools].

=== Components and upgrade order

The upgrade is a single run of `upgrade-provisioner.py`, which walks the components in a fixed order. The order matters and cannot be altered: each block depends on the previous one.

|===
| Order | Block | Components | Own storage | Why it goes in that position

| 1
| Cluster charts
| cert-manager, cluster-autoscaler, `cluster-operator`, flux2, and the Tigera operator, which governs Calico. Plus, depending on the provider: aws-load-balancer-controller on EKS — only if it is installed — and the disk and file CSI drivers and the Azure cloud provider on Azure VMs.
| None.
| Cluster API is deployed on top of `cert-manager`, and the rest of the process relies on Flux to reconcile the charts. They have to be on their new version before touching the providers.

| 2

| The Cluster API core and its bootstrap and control-plane providers, plus the matching infrastructure provider: CAPA on Amazon Web Services, CAPZ on Microsoft Azure, or CAPG on Google Cloud Platform.
| None.

| 3

| The control plane and every worker node group, from version 1.32 to 1.35.

| It goes last because it is carried out by the components of the two previous blocks: `cluster-operator` translates the `k8s_version` change and Cluster API replaces the machines.

[#modules]

=== Relationship with other modules

_Stratio Cloud Provisioner_ sits below everything else: it creates the cluster and raises its Kubernetes version. That is why its window is the first one in the Universe sequence.

[cols="2,2,4,4", options="header"]
|===
| Related module | What the relationship is | When upgrading _Stratio Cloud Provisioner_ | When upgrading the related module

| _Stratio KEOS_
| It is installed on the cluster that _Stratio Cloud Provisioner_ provisions and, in the cloud, delegates the Kubernetes version to it.
| *It goes first*, and not only as a planning choice: in the cloud, Calico and Flux are deployed and upgraded by _Stratio Cloud Provisioner_, not by _Stratio KEOS_, and version 1.4's system services are deployed through that Flux. When this window closes, _Stratio KEOS_ 1.2.x stays on Kubernetes 1.35 until its own upgrade. Its workloads are rescheduled like any other when the nodes are replaced.
| The _Stratio KEOS_ upgrade from 1.2.x to 1.4 goes *after* this one, in its own window, and does not touch the Kubernetes version again. See the xref:stratio-keos:operations-guide:cluster-operation/upgrade-overview/from-1-2-x-to-1-4-x.adoc[_Stratio KEOS_ planning fact sheet].

| `cluster-operator`
| It is not a separate module: it is the controller that _Stratio Cloud Provisioner_ deploys in the cluster to reconcile the `KeosCluster` object.
| It is upgraded as part of this intervention, from 0.5.x to 0.7.2, and during the critical section it is stopped and its webhooks disabled.
| It is not upgraded separately.

| _Stratio Command Center_ and the data modules
| They run on the cluster.
| No impact of their own beyond their workloads being rescheduled when the nodes are replaced. The ones with a single replica are down while they start on another node.
| No impact on _Stratio Cloud Provisioner_. Each one is upgraded according to its own fact sheet, after _Stratio KEOS_.
|===

Upgrade the platform in this order: first _Stratio Cloud Provisioner_, in its own window; then _Stratio KEOS_; and last the data modules, each according to its fact sheet.

[cols="2,1,3", options="header"]
|===
| Scenario | Supported? | Limitations

| _Stratio KEOS_ 1.2.x on Kubernetes 1.35

* *90 minutes* for each convergence wait: the control plane's and each node group's. When it runs out, the script aborts.
* *Each chart's timeout scales with the size of the cluster*, with a minimum of 15 minutes and two more minutes per node.

[#no-return]

=== Point of no return

The point of no return is *the Kubernetes version jump*, and it is crossed in step 7. There is no downgrade operation:

[cols="2,1,2,2", options="header"]
|===
| What changes | Step | How you know it has been passed | When it applies

| The control plane's Kubernetes version
| 7
| The control plane reports the target version: on EKS and on GKE, in the provider's API; on Azure VMs, in the `KubeadmControlPlane`.
| Always.

| The control plane's etcd, which goes *from the v3.5 series to the v3.6 series*
| 7
| The etcd containers on the control-plane nodes report a version in the v3.6 series, and their members are different ones: the nodes have been replaced.
| On Azure VMs only. On EKS and on GKE etcd belongs to the provider and is not touched.

| The Cluster API CRDs and controllers
| 6
| The providers report the target versions.
| Always.
|===

IMPORTANT: On Azure VMs the control plane's etcd is managed by kubeadm and its version is set by the target Kubernetes minor, not by the repository: 1.32 goes with the v3.5 series and 1.35 with the v3.6 series. The jump therefore crosses an *etcd major-series upgrade, which cannot be reverted once applied*, just as it happens on _Stratio KEOS_ on-premise installations. Confirm before the window which etcd version kubeadm deploys on the target minor.

* *What stops being possible from then on.* Going back to the previous Kubernetes version: `cluster-operator`'s webhook rejects any `k8s_version` lower than the installed one, and the script itself aborts if the target is lower than the current version. There is no procedure for downgrading the Cluster API providers either, nor, on Azure VMs, for going back to etcd's v3.5 series.
* *What can be done before crossing it.* Up to and including step 6, the cluster keeps its Kubernetes version: the charts and Cluster API are already upgraded, but the nodes have not been touched. It is the last point at which the intervention can stop without having altered the data plane.

[#data]

=== Data and consistency

* *What changes in the data model.* Nothing in application data. What changes is the infrastructure: the nodes are replaced and, on Azure VMs, with them the members of the control plane's etcd, which also *goes from the v3.5 series to the v3.6 series*, an irreversible change of storage format. See <<no-return,Point of no return>>. The Cluster API CRDs move to the 0.9.x versions, which converts the existing objects.
* *Is a mandatory backup needed beforehand?* The script takes it at the start, and it does not have to be requested: it exports to disk the Cluster API objects, the Capsule webhooks, and the secrets of the Cluster API and provider namespaces. It is worth not disabling it and keeping that directory until the window is closed.
* *What that backup covers and what it does not.* It serves to rebuild the infrastructure objects if they are corrupted or deleted. *It does not serve to go back to the previous version*: the objects it contains describe the cluster as it was, but restoring them downgrades neither Kubernetes nor the providers.
* *What happens to the volumes.* The provider's disks survive the node replacement: they are detached from the retired node and attached to the new one. What lives on a node's local disk, by contrast, is lost with it.
* *Can the data be left in an intermediate state?* The cluster can, the data cannot. If the process is interrupted, it may be left with the new charts and the old providers, or with the control plane on the target version and some node groups still on the previous one. Both are supported states and are resolved by completing the upgrade.
* *What to do if something fails halfway.* Fix the cause and relaunch, with one important caveat covered in <<rollback,Rollback>>: if the version change has already been written to the descriptor but never propagated, a relaunch skips it.
* *How to check the data is fine after migrating.* The `KeosCluster` returns to `ready` and to phase `Provisioned`, every node reports the target version, and the applications with volumes start again. On Azure VMs, in addition, the control plane's etcd answers, forms quorum, and its registered members match the control-plane nodes. It is covered in <<checks,Post-upgrade checks>>.

[#outage]

=== Downtime and availability

* *What has been done to reduce it.* Preparation and the backup happen inside the run but before anything is touched. The control plane keeps serving: on EKS and on GKE the provider raises it without replacing nodes, and on Azure VMs its replicas are replaced one at a time. Node groups are upgraded one at a time, waiting for each one to converge before moving on to the next. And each node is replaced by bringing the new one up first and retiring the old one afterwards, so the configured node count is maintained at all times.
* *What cannot be avoided, and why.* The node replacement. The infrastructure is immutable: there is no way to raise a node's kubelet version without replacing it, so its workloads are necessarily rescheduled. The real impact depends on how the applications are sized, more than on the upgrade process.
* *What determines the impact on each service.* The number of replicas. A service with several replicas spread across nodes is not interrupted; one with a single replica is down while it starts on another node.
* *The most important warning about PDBs.* Here the component that drains the nodes is Cluster API, which honors the eviction API and *never forces the eviction*. A Pod Disruption Budget that cannot be satisfied does not delay the drain: it blocks it, and with it the upgrade of the node group, until the 90-minute limit runs out and the script aborts. This is a fundamental difference from the _Stratio KEOS_ upgrade on on-premise installations, where the drain ends up being forced.
* *What happens to autoscaling.* It is off from step 4 to step 8. If the cluster's load grows during the window, no nodes are added.
* *Who is notified, and how far in advance.* Announce that applications will be rescheduled, which services with a single replica will be unresponsive for a few minutes, and that there will be no autoscaling during the intervention. Follow each environment's change management policy: _Stratio Cloud Provisioner_ imposes no notice period.
* *What happens if a step fails.* The script aborts. If the failure falls inside the critical section, before aborting it attempts a controlled recovery: it re-enables `cluster-operator`'s webhooks, starts its controller, and resumes its reconciliation. If that recovery also fails, the cluster is left with the webhooks disabled and the controller stopped, and they have to be restored by hand before anything else.
* *Recommendation for planning the window.* Measure the complete run in preproduction with a similar node count and communicate a range, not an exact figure. And count on step 7 being the one that rules: on Azure VMs it is three full rotations of the control plane and of every node group.

[#work-in-flight]

=== Work in flight during the window

Since the cluster is not stopped to upgrade it, this table summarizes what happens to work already running and how it recovers:

[cols="2,4,2,4", options="header"]
|===
| What may be running | What happens to it | What to do beforehand | How it recovers afterwards

| Workloads with several replicas spread across nodes
| They carry on unaffected: the replicas on the node being retired are rescheduled onto others and the service is never left without instances.
| Nothing
| Nothing needed.

| Workloads with a single replica
| They are down from the moment their node is drained until they start on another one. This is the real impact of the window.
| Add a second replica to anything that cannot be interrupted, or accept the cut and announce it.
| Kubernetes starts them again on its own. Check they ended up in `Running`.

| Workloads with a Pod Disruption Budget that cannot be satisfied
| *They block the drain of their node*, and with it the upgrade of its whole node group. Nothing forces the eviction.
| Review them: it is the most important prerequisite in <<before,Before the window>>.
| It does not recover on its own. The PDB or the replica count has to be fixed and the upgrade relaunched.

| Pods with exclusive-access volumes
| They are rescheduled, but do not start until the volume is detached from the retired node and attached to the new one, which lengthens their unavailability.
| Nothing, but count on these services taking longer to come back than the rest.
| They start on their own once the volume is available. If one stays waiting, check the volume's state.

| DaemonSets
| They are excluded from the node drain and go away with the node; the new node brings them up again.
| Nothing
| Nothing needed.

| Running Jobs and CronJobs
| Those running on a node being retired are interrupted. If they are not idempotent, repeating them may duplicate data.
| Avoid launching long jobs during the window, and review which ones can be repeated without side effects.
| Check the state of the ones that were running and relaunch them if appropriate.

| Changes to the cluster descriptor
| They are not applied: during the critical section, `cluster-operator` is stopped and its webhooks disabled. A change made in that period goes unreconciled and can be mistaken for an upgrade failure.
| Do not touch the `KeosCluster` during the window, and warn whoever might. Bear in mind, too, that it must never be modified with `kubectl apply`: see <<known-issues,Known issues>>.
| Apply the change again once the window is closed and `cluster-operator` is back.

| Node autoscaling
| It does not happen: autoscaling is off for the whole intervention.
| If you expect a load peak, size the node groups before the window.
| It comes back on its own at the end of step 8. Check it has recovered its replicas.

| _API Server_ calls and external orchestrators
| On EKS and on GKE they are not interrupted. On Azure VMs they fail during the seconds in which each control-plane replica is replaced; with a single replica, the cut lasts for its whole replacement.
| Pause external orchestration during the window so that it does not pile up failed attempts.
| Relaunch the affected flows from the orchestrator.

| _Stratio KEOS_ monitoring and centralized logging
| They lose samples and events while their own pods are rescheduled from one node to another.
| Nothing
| They recover on their own, but the gap in the time series is not backfilled.

| Open sessions on the Stratio interfaces
| They are closed when the ingress controller changes node, which happens at some point during step 7 without it being possible to choose when.
| Warn users that they will have to log in again.
| Log in again.

| _Stratio KEOS_ scheduled backups
| A backup that coincides with its node being replaced is interrupted.
| Do not overlap the window with their schedule. By default they run at 00:00, 00:05, and 00:10.
| Run the backup by hand once the window is over.
|===

== After the upgrade

[#regressions]

=== Regressions to expect

None of these regressions blocks the upgrade, but each one affects specific functionality:

[cols="1,1,2,1", options="header"]
|===
| What stops working or changes | Cause | How to resolve it | In the meantime

| Calico's observability components, Whisker and Goldmane
| 0.9.2 stopped deploying them during the upgrade and forces them to the descriptor's default value, which is disabled.
| Enable them explicitly in the cluster descriptor if you need them.
| They are not deployed, even though the Calico chart ships them.

| Node groups remain `MachineDeployment` on EKS
| EKS-managed node groups are only created on new clusters: the upgrade does not convert existing groups.
| Migrating them is a separate, assisted, phased operation that comes after this upgrade: see xref:operations-manual:upgrade.adoc#_eks_clusters_with_machinepools[EKS clusters with MachinePools].
| The existing groups keep working as self-managed instances.

| The flux2 version ends up below the one 0.8.x shipped
| 0.9.0 deliberately lowered it from 2.18.4 to 2.17.2.
| Nothing: it is the target version for this version of _Stratio Cloud Provisioner_.
| Flux works normally on the pinned version.

| Autoscaling does not come back on its own if the upgrade aborts
| The script turns it off at the start and restores it in the closing step, which does not run if it aborts earlier.
| Take it back to its replicas by hand and check the deployment is available again.
| The cluster does not add or remove nodes based on load.
|===

[#problems]

== If something goes wrong

[#rollback]

=== Rollback

*There is no rollback procedure.* It is the most important limitation of this intervention: the way out is always forwards, and what determines the options is the moment at which it is decided.

[cols="2,1,4,2", options="header"]
|===
| Point in the process | Possible? | What is done | How long it takes and whether data is lost

| Before launching the script, during preparation
| Yes
| Nothing: no cluster component has been modified. Not continuing is enough.
| Immediate. No data is lost.

| During steps 2 to 4
| Yes, almost entirely
| The script aborts on its own and only two things are left to revert by hand: the autoscaling replicas and, if the run died midway, the Capsule webhooks.
| Minutes (estimated). No data is lost.

| A chart fails in step 5
| Partially
| Fix the cause and relaunch: the script walks the charts again and skips the ones already on the target version. Those already upgraded stay as they are, without being downgraded.
| Depends on the charts left (estimated). No data is lost.

| Step 6 fails inside the critical section
| Forwards only
| The script attempts a controlled recovery: it re-enables `cluster-operator`'s webhooks, starts its controller, and resumes its reconciliation. *Check that recovery completed*: if it also fails, the webhooks have to be re-enabled and the controller started by hand before anything else. Then fix the cause and relaunch.
| Minutes (estimated). No data is lost.

| The Kubernetes jump fails halfway, in step 7
| Forwards only
| Fix the cause and relaunch. It is safe: each step checks the real state before acting and skips whatever is already on the target version. *With one critical exception:* if the version change was already written to the descriptor but never propagated to the infrastructure, a relaunch skips the step because the descriptor already matches the target. Review `cluster-operator`'s tracking annotation and its logs before retrying.
| Depends on the nodes left (estimated). No data is lost.

| After the control plane's version goes up
| No
| There is no possible downgrade. The cluster stays on the new version and the upgrade of any remaining node groups has to be completed.
| Not applicable. No data is lost.
|===

And what is *not* reversible under any circumstances: *the Kubernetes version*. `cluster-operator`'s webhook rejects any version lower than the installed one and the script itself aborts if the target is lower than the current version. There is no procedure for downgrading the Cluster API providers or the `cluster-operator` either.

So what is the backup the script takes for: rebuilding the Cluster API objects if they are corrupted or deleted, not going back to the previous version. See <<data,Data and consistency>>.

[#known-issues]

=== Known issues

[cols="2,2,3,2", options="header"]
|===
| Warning or issue | When it shows up | What to do | Reference

| A Pod Disruption Budget that cannot be satisfied blocks the drain of its node
| In step 7, when replacing the nodes of a group
| Fix the resource's replica count or remove its PDB temporarily, and relaunch. There is no forced eviction: the phase keeps waiting until the script aborts at 90 minutes. On EKS, review the `coredns` PDB in the `kube-system` namespace beforehand.
| xref:operations-manual:operations-manual.adoc#_kubernetes_upgrade[Kubernetes upgrade]

| The version jump is written to the descriptor but never propagated
| In step 7, if `cluster-operator`'s controller restarted in the middle of the upgrade
| Do not simply relaunch the script: since the descriptor already matches the target, the step would be skipped. Review `cluster-operator`'s tracking annotation and its logs before retrying.
| <<rollback,Rollback>>

| `cluster-operator`'s reconciliation is left suspended after an interrupted run
| On relaunch, after a run died inside the critical section
| The script detects it and resumes it by itself before waiting. If you do not get to relaunch it, resume it by hand: while it stays suspended, no descriptor change is applied.
| <<outage,Downtime and availability>>

| Modifying the `KeosCluster` with `kubectl apply`
| At any time, outside the window too
| Do not do it: `cluster-operator` detects the annotation `apply` generates and skips the real reconciliation cycle, so the changes are never processed. Use `patch`.
| xref:operations-manual:upgrade.adoc#_eks_clusters_with_machinepools[EKS clusters with MachinePools]

| On GKE, the version jump's wait is not validated in a real environment
| In step 7, on Google Cloud Platform
| Follow the state of the `KeosCluster` and of the nodes yourself during the step, instead of taking the wait at face value, and reserve slack in the window.
| <<providers,Differences by provider>>

| cluster-autoscaler's scale-down on EKS managed groups
| After the window, when removing nodes from a managed group
| Nothing: the cluster-autoscaler image is pinned precisely to work around the problem. It is a known and accepted risk until the fix lands in a published release.
| Issue `kubernetes/autoscaler#9693`

| On Azure, an expired kubeconfig aborts the run
| In step 2
| Update the file's credentials by hand and launch the script again. Unlike on Amazon Web Services and on Google Cloud Platform, here it is not refreshed automatically.
| <<before,Before the window>>

| On Azure, the control plane's network policy is left open during the jump
| Throughout step 7
| Nothing while it lasts: it is required for the new control-plane replicas to join the cluster. Check when closing the window that it has been restricted again, because while it is open it allows traffic from the whole VPC and pod networks.
| <<checks,Post-upgrade checks>>
|===

TIP: Keep the script's full output. It reports every step, the planned version change of every component, and the total time, so it is what lets you know exactly where the upgrade stopped and in what state, instead of reconstructing it afterwards.

*What counts as blocking.* Any of the checks marked as such in <<checks,Post-upgrade checks>> failing, and in particular the control plane not having converged, nodes being left on the previous version, or `cluster-operator` not having recovered its webhooks and its reconciliation. Everything else can be resolved with the window already closed.

*What to do if a step takes longer than expected.* The script reports every wait and its limit, so the first thing is to check whether it is still making progress: in step 7, if new nodes with the target version keep appearing, it is going fine even if it is slow. If it is not progressing, find the cause before interrupting — the most frequent one is a PDB that cannot be satisfied or a new node that never reaches `Ready` — because interrupting halfway through the jump leaves the cluster with nodes on two versions and, if it happens inside the critical section, with `cluster-operator` stopped.
