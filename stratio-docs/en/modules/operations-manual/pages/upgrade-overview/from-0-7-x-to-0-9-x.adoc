= Upgrade from 0.7.x to 0.9.x

This sheet summarizes the impact of upgrading _Stratio Cloud Provisioner_ from 0.7.x to 0.9.x, which accompanies the move to Universe 15.1 from 14.8.x, 14.9.x, or 14.10.x in the environments deployed on the cloud. It includes the Kubernetes jump from version 1.32 to 1.35, which in these environments is the responsibility of _Stratio Cloud Provisioner_, not _Stratio KEOS_. Use it to plan the maintenance window, know what to prepare beforehand, and what to check afterward.

Each section answers a question and links to the page that details the procedure. When you reach the intervention window, follow the xref:operations-manual:upgrade.adoc[upgrade procedure] step by step.

IMPORTANT: _Stratio Cloud Provisioner_ is the owner of the cluster infrastructure and of its Kubernetes version, so *its window goes first*: the _Stratio KEOS_ upgrade from 1.2.x to 1.4 comes afterward, in a different window. See <<modules, Relationship with other modules>>.

[#summary]

== Summary

IMPORTANT: *The upgrade does not stop the cluster, but it does replace all its worker nodes.* The infrastructure is immutable: raising the Kubernetes version of a node does not upgrade the node in place, but creates a new one and retires the previous one. Each workload with a single replica remains down while it is rescheduled, and unlike on-premises installations, here *a poorly sized _Pod Disruption Budget_ blocks draining*: Cluster API drains the node, respects the _eviction_ API, and never forces. Size the window based on the number of nodes, and review the PDBs before opening it.

IMPORTANT: *On cloud, there are two windows.* This upgrade leaves the cluster on Kubernetes 1.35 and _Stratio KEOS_ still on 1.2.x; the final state arrives with the _Stratio KEOS_ window, which goes afterward.

The table answers, with one row per decision, what you need to size the window:

[cols="2,3,1", options="header"]
|===
| Question | Answer | Detail

| How much downtime is there in the worst case?
| *None at the cluster level, but yes at the component level.* On EKS and on GKE, the _control-plane_ is upgraded by the provider, without needing to replace nodes. On Azure VMs, the `KubeadmControlPlane` replicas are replaced one by one and, with them, the etcd members; with three replicas, the _API Server_ keeps responding. The worker nodes are replaced group by group, and each workload hosted on them is rescheduled; the one with a single replica remains down until it starts on another node.
| <<outage, Downtime>>

| What does the duration depend on?
| The *number of nodes* and the *number of minor version jumps*, which are three: 1.32 → 1.33 → 1.34 → 1.35. On Azure VMs and on GKE, the script explicitly passes the _control-plane_ through the three, with a wait between them; on EKS, the provider staggers them.
| <<phases, Steps>>

| How long does the maintenance window last in total?
| Pending. There is no measured duration. The script reports the real time it took when it finishes, so the first execution in preproduction already gives a figure to plan around.
| <<phases, Steps>>

| Can the work be divided into several windows?
| *No, except for the Kubernetes jump.* It is a single execution that chains the charts, Cluster API, and the version jump, with a critical section in which the `cluster-operator` webhooks are deactivated: you have to reach the end. The only separable part is the Kubernetes jump, which requests confirmation separately and can be left for another window by responding no.
| <<phases, Steps>>

| Does anything stop working until another module is upgraded?
| *Yes, by design of the order.* Upon closing this window, _Stratio KEOS_ 1.2.x remains in operation on Kubernetes 1.35 until its own upgrade is executed. It is a planned intermediate state, not a final state.
| <<modules, Relationship with other modules>>

| Does the data model change and is a backup necessary?
| There is no migration of application data: the provider volumes survive the replacement of the nodes. What does change, *only on Azure VMs*, is the etcd version of the _control-plane_, which goes up from v3.5 to v3.6 and cannot be reverted. The script backs up the Cluster API objects at the start, so you don't need to request it.
| <<data, Data and consistency>>

| Can you go back at any moment?
| *No.* There is no version rollback: the `cluster-operator` webhook rejects lowering the `k8s_version`, and there is no procedure to downgrade the Cluster API providers. Before launching the script, it is enough not to continue; afterward, the way out is forward.
| <<rollback, Rollback>>

| Does the previous version work on Universe 15.1?
| _Stratio Cloud Provisioner_ is not executed inside the cluster as another application: it is the tool that provisions it, and `cluster-operator` reconciles it. The key point is that the modules running on top, including _Stratio KEOS_ 1.2.x, keep working on the already upgraded cluster.
| <<coexistence, Version coexistence>>

| What is the overall risk?
| *High.* There is no rollback; the Kubernetes jump is irreversible. A poorly sized PDB blocks the drain without anything forcing it. On Azure VMs, the _control-plane_ network policy is temporarily opened, and there is a critical section in which a failure can leave the cluster with the `cluster-operator` webhooks deactivated and its controller stopped.
| <<known-issues, Known warnings and incidents>>
|===

.Message to communicate
[caption=]
====
The platform raises the cluster's Kubernetes version. It does not stop: nodes are gradually replaced with the new version, and applications are rescheduled across them. Services that have a single replica will be unresponsive for a few minutes when it is their turn to change nodes, so it is advisable to check beforehand that everything important has more than one replica. The window depends on the number of nodes in the cluster. After this intervention, a second one will be necessary: _Stratio KEOS_, so the environment is left in its final version.
====

[#scope]

== Scope of the upgrade

The three source Universes have _Stratio Cloud Provisioner_ 0.7.x and Kubernetes 1.32, so the procedure is the same in all three.

The upgrade script itself indicates that the supported source version is 0.7.x. Bear in mind that *nothing validates it*: the script does not check which version the cluster comes from, so launching it on an earlier source does not abort; it is simply not supported. If the cluster is from an earlier version, upgrade it to version 0.7.x first.

The upgrade is only supported in three environments, and any other combination of provider and _control-plane_ type is rejected:

* *EKS* on Amazon Web Services, with a managed _control-plane_.
* *Azure VMs* on Microsoft Azure, with an unmanaged _control-plane_. Microsoft AKS is not supported.
* *GKE* on Google Cloud Platform, with a managed _control-plane_.

Migrating `MachineDeployment` node groups to `MachinePool` is outside the scope of this sheet; it is a separate, assisted operation exclusive to EKS and occurs after this upgrade. See the xref:operations-manual:upgrade.adoc#_eks_clusters_with_machinepools[EKS clusters with _MachinePools_].

=== Components and upgrade order

The upgrade runs a single execution of `upgrade-provisioner.py`, which processes the components in a fixed order. The order matters and cannot be altered: each block depends on the previous one.

[cols="4%,18%,34%,18%,26%", options="header"]
|===
| Order | Block | Components | Own store | Why it goes in that position

| 1
| Cluster charts
| cert-manager, cluster-autoscaler, `cluster-operator`, flux2, and the Tigera operator, which manages Calico. In addition, depending on the provider: _aws-load-balancer-controller_ on EKS (if installed), and the disk and file CSI drivers and the Azure cloud provider on Azure VMs.
| None.
| Cluster API is deployed on top of `cert-manager`, and the rest of the process relies on Flux to reconcile the charts. They must be on their latest version before the providers are upgraded.

| 2
| Cluster API and its provider
| The Cluster API core and its bootstrap and _control-plane_ providers, plus the corresponding infrastructure provider: CAPA on Amazon Web Services, CAPZ on Microsoft Azure, or CAPG on Google Cloud Platform.
| None.
| It is what materializes the Kubernetes version jump: without the updated providers, the target version cannot be reconciled.

| 3
| Kubernetes
| The _control-plane_ and all worker node groups, from version 1.32 to 1.35.
| The _control-plane_ etcd, only on Azure VMs. On EKS and on GKE, it belongs to the provider.
| It goes at the end because it is executed by the components of the two previous blocks: `cluster-operator` translates the `k8s_version` change, and Cluster API replaces the machines.

[#modules]

=== Relationship with other modules

_Stratio Cloud Provisioner_ is below everything else: it creates the cluster and raises its Kubernetes version. That is why its window is the first in the Universe sequence.

[cols="2,2,4,4", options="header"]
|===
| Related module | What relationship there is | When upgrading _Stratio Cloud Provisioner_ | When upgrading the related module

| _Stratio KEOS_
| It is installed on top of the cluster that _Stratio Cloud Provisioner_ provisions and, in the cloud, delegates the Kubernetes version to it.
| *It goes first*, and not only for planning criteria: in the cloud, Calico and Flux are deployed and upgraded by _Stratio Cloud Provisioner_, not by _Stratio KEOS_, and the version 1.4 _system-services_ are deployed through that Flux. Upon closing this window, _Stratio KEOS_ 1.2.x remains on Kubernetes 1.35 until its own upgrade. Its workloads are rescheduled, like the others, when the nodes are replaced.
| The _Stratio KEOS_ upgrade from 1.2.x to 1.4 goes *after* this one, in its own window, and does not touch the Kubernetes version again. See the xref:stratio-keos:operations-guide:cluster-operation/upgrade-overview/from-1-2-x-to-1-4-x.adoc[_Stratio KEOS_ planning sheet].

| `cluster-operator`
| It is not a separate module: it is the controller that _Stratio Cloud Provisioner_ deploys on the cluster to reconcile the `KeosCluster` object.
| It is upgraded as part of this intervention, from 0.5.x to 0.7.3, and during the critical section it remains stopped and with its webhooks deactivated.
| It is not upgraded separately.

| _Stratio Command Center_ and the data modules
| They run on top of the cluster.
| No impact beyond rescheduling their workloads when nodes are replaced. Those that have a single replica remain down while they start on another node.
| No impact on _Stratio Cloud Provisioner_. Upgrade each one according to its own sheet, after _Stratio KEOS_.
|===

Upgrade the platform in this order: first _Stratio Cloud Provisioner_ in its own window; then _Stratio KEOS_; and finally the data modules, each according to its sheet.

[#coexistence]

=== Version coexistence

[cols="2,1,3", options="header"]
|===
| Scenario | Supported? | Limitations

| _Stratio KEOS_ 1.2.x on Kubernetes 1.35
| Yes, as an intermediate state
| It is the expected result upon closing this window before that of _Stratio KEOS_. It is not a final state: complete it by upgrading _Stratio KEOS_ to version 1.4.

| The _control-plane_ and the worker nodes on different Kubernetes versions
| Yes
| Up to 3 minor versions of difference and never with the workers ahead, according to the _Version Skew Policy_. This is a transient state during the upgrade: the _control-plane_ goes up first, and the node groups follow, one by one.

| `MachineDeployment` and `MachinePool` groups on the same cluster
| Yes, on EKS
| A descriptor can combine both group types. What there is not is automatic migration from one to the other: see <<regressions, Regressions to expect>>.

| Charts already upgraded with Cluster API still on their previous version
| Yes, transiently
| It is the state in which the cluster remains between blocks 1 and 2 of the execution itself. If the script fails there, the cluster remains like this until it is relaunched.
|===

The following steps constitute the sequence of a single execution of `upgrade-provisioner.py`, except for the first and the last. The script goes through them on its own: the column "Own window?" indicates whether the step can be taken out of the window, not whether it is launched separately.

[cols="3%,15%,38%,14%,16%,14%", options="header"]

| Days or weeks
| None
| Yes, days before

| 2
| Validation and health checks
| The script validates `clusterctl`, the kubeconfig, and the secrets, configures the provider CLI, and checks the cluster state. If it finds something, it aborts before touching anything. On Amazon Web Services, it also corrects an obsolete security group in the pod network configuration.
| Pending
| None
| No

| 3

| Pending
| None
| No

| 5
| Cluster charts

| Pending
| None direct

The _control-plane_ goes up first, then each node group, one by one: the nodes are replaced with new ones running the target version. WARNING: *No duration is measured yet, so all appear as "Pending".* Before committing to a window, measure them in a preproduction environment with a representative node topology: the script reports, when finishing, the real time it took.

The only numbers that are set are the limits beyond which the script stops waiting, and it is convenient to know them because they mark when a phase is considered failed rather than slow:

* *90 minutes* for each wait on the control-plane. When exhausted, the script aborts. It is adjusted with `--control-plane-timeout`.
* *90 minutes without progress* on the upgrade of the node groups. This is not a total limit: the deadline resets each time an additional node reaches the new version, so the total duration can grow with the number of nodes and groups without the script stopping. It only aborts if the replacement stops. It is adjusted with `--node-convergence-timeout`.
* *The timeout of each chart scales with the size of the cluster*: the greater of 15 minutes and 5 minutes plus 2 minutes per node.
* *90 seconds of settling* between minor versions on Azure VMs, so that the _control-plane_ rotation does not drag the `cluster-operator` controller.

[#no-return]

=== Point of no return

The point of no return is *the Kubernetes version jump*, and it is crossed in step 7. There is no downgrade operation:

[cols="2,1,2,2", options="header"]
|===
| What changes | Step | How to know it has been passed | When it applies

| The Kubernetes version of the control-plane
| 7
| The _control-plane_ reports the target version: on EKS and on GKE, in the provider API; on Azure VMs, in the `KubeadmControlPlane`.
| Always.

| The _control-plane_ etcd, which goes up *from the v3.5 series to v3.6*
| 7
| The etcd containers on the _control-plane_ nodes report a v3.6 version, and their members differ: the nodes have been replaced.
| Only on Azure VMs. On EKS and on GKE, etcd belongs to the provider and is not touched.

| The Cluster API CRDs and controllers
| 6
| The providers report the target versions.
| Always.
|===

IMPORTANT: On Azure VMs, the _control-plane_ etcd is managed by kubeadm and its version is set by the target Kubernetes minor, not by the repository: 1.32 goes with the v3.5 series and 1.35 with v3.6. The jump therefore implies a *major series upgrade of etcd, which cannot be reverted once applied*, as also happens in on-premises installations of _Stratio KEOS_. Confirm, before the window, which etcd version kubeadm deploys in the target minor.

* *What ceases to be possible from there on.* Going back to the previous Kubernetes version: the `cluster-operator` webhook rejects any `k8s_version` lower than the installed one, and the script itself aborts if the target is lower than the current version. There is also no procedure to downgrade the Cluster API providers, or to return Azure VMs to the v3.5 series of etcd.
* *What can be done before crossing it.* Up to and including step 6, the cluster preserves its Kubernetes version: the charts and Cluster API are already upgraded, but the nodes have not been modified. It is the last point at which the intervention can be stopped without altering the data plane.

[#data]

=== Data and consistency

* *What changes in the data model.* Nothing in the application data. The infrastructure changes: the nodes are replaced and, on Azure VMs, the _control-plane_ etcd members are upgraded *from the v3.5 series to v3.6*, an irreversible storage-format change. See <<no-return, Point of no return>>. The Cluster API CRDs move to the versions shipped with 0.9.x, which requires converting existing objects.
* *Is a mandatory backup needed before?* The script itself makes it at the start, and it does not have to be requested: it exports to disk the Cluster API objects, the Capsule webhooks, and the secrets of the Cluster API and provider namespaces. It is advisable not to deactivate it and to keep that directory until the window is closed.
* *What that backup covers and what it does not cover.* It serves to reconstruct the infrastructure objects if they are corrupted or deleted. *It does not serve to go back to the previous version*: the objects it contains describe the cluster as it was, but restoring them does not downgrade Kubernetes or the providers.
* *What happens to the volumes.* The provider disks survive the replacement of the nodes: they are detached from the retired node and attached to the new one. What lives on a node's local disk, by contrast, is lost.
* *Can the data be left in an intermediate state?* The cluster, yes; the data, no. If the process is interrupted, it can be left with the new charts and the old providers, or with the _control-plane_ in the target version and some node groups still in the previous version. Both are supported states and are resolved by completing the upgrade.
* *What to do if something fails midway.* Correct the cause and relaunch, with an important caveat recorded in <<rollback, Rollback>>: if the version change was already applied to the descriptor but not propagated, a relaunch skips that step.
* *How to check that everything is fine after the migration.* The `KeosCluster` returns to `ready` and to the `Provisioned` phase, all nodes report the target version, and the applications with volumes start again. On Azure VMs, in addition, the _control-plane_ etcd responds, forms quorum, and its registered members match the _control-plane_ nodes. It is recorded in <<checks, Post-upgrade checks>>.

[#outage]

=== Downtime and availability

* *What has been done to reduce it.* The preparation and the backup occur during the execution, but before touching anything. The _control-plane_ preserves the service: on EKS and GKE, the provider upgrades it without replacing nodes, and on Azure VMs its replicas are replaced one by one. The node groups are upgraded one by one, waiting for each to converge before moving on to the next. Each node is replaced by first bringing up the new one and then retiring the old one, so the configured number of nodes is maintained throughout.
* *What part cannot be avoided and why.* The replacement of the nodes. The infrastructure is immutable: you can't upgrade a node's kubelet version without replacing it, so its workloads are necessarily rescheduled. The real impact depends more on how the applications are sized than on the upgrade process.
* *What determines the impact on each service.* The number of replicas. A service with several replicas distributed across nodes isn't interrupted; one with a single replica goes down while it starts on another node.
* *The most important warning about PDBs:* Here, the one who drains the nodes is Cluster API, which respects the _eviction_ API and *does not force the eviction at any time*. A _Pod Disruption Budget_ that cannot be met does not delay the drain; it blocks it, and with it the node-group upgrade, until 90 minutes pass without any more nodes being upgraded and the script aborts. This differs from the _Stratio KEOS_ upgrade in on-premises installations, where the drain ends up being forced.
* *What happens with autoscaling.* It is turned off from before the charts step until step 8. If the cluster load increases during the window, no nodes are added.
* *Who to notify and with how much advance notice.* Announce that the applications will be rescheduled, that services with a single replica will be unresponsive for a few minutes, and that there will be no autoscaling during the intervention. Follow each environment's change management policy: _Stratio Cloud Provisioner_ does not require a notice period.
* *What happens if a step fails.* The script aborts. If the failure occurs in the critical section, before aborting, it attempts a controlled recovery: it reactivates the `cluster-operator` webhooks, starts its controller, and resumes its reconciliation. If that recovery also fails, the cluster is left with the webhooks deactivated and the controller stopped; you must restore them manually before doing anything else.
* *Recommendation for planning the window.* Measure the complete execution in preproduction with a similar number of nodes and communicate a range, not an exact figure. And count on step 7 being the one that rules: on Azure VMs, there are three complete rotations of the _control-plane_ and all node groups.

[#work-in-flight]

=== Work in progress during the window

Since the cluster does not stop to be upgraded, this table summarizes what happens to the work that is already running and how it is recovered:

[cols="2,4,2,4", options="header"]
|===
| What may be running | What happens to it | What to do before | How it recovers afterwards

| Workloads with several replicas distributed among nodes
| They continue without effect: the replicas of the node that is retired are rescheduled on other nodes, and the service is never left without instances.
| Nothing
| No need.

| Workloads with a single replica
| They are left down from when their node is drained until they start on another. It is the real impact of the window.
| Add a second replica to what cannot be interrupted, or accept the cut and announce it.
| Kubernetes starts them again by itself. Check that they have been left in the `Running` state.

| Workloads with a _Pod Disruption Budget_ that cannot be met
| *They block the drain of their node* and, with it, the upgrade of its entire node group. Nothing forces the eviction.
| Review them: it is the most important prerequisite of <<before, Before the window>>.
| It does not recover on its own. You must correct the PDB or replica count, then restart the upgrade.

| Pods with volumes of exclusive access
| They are rescheduled but don't start until the volume is detached from the retired node and attached to the new one, which prolongs their unavailability.
| Nothing, but bear in mind that these services take longer to return than the rest.
| They start on their own when the volume is available. If one is left waiting, check the state of the volume.

| _DaemonSets_
| They are excluded from node drains and disappear with the node; the new node brings them back up.
| Nothing
| No need.

| _Jobs_ and _CronJobs_ in execution
| Jobs running on a retired node are interrupted. If they are not idempotent, repeating them may duplicate data.
| Avoid launching long jobs during the window, and review which ones can be repeated without effects.
| Check the state of those that were in progress and relaunch them if applicable.

| Changes in the cluster descriptor
| They are not applied: during the critical section, `cluster-operator` is stopped and its webhooks are deactivated. Changes made during that stretch remain unreconciled and can be mistaken for an upgrade failure.
| Do not touch the `KeosCluster` during the window, and warn anyone who can. Also note that it must never be modified with `kubectl apply`; see <<known-issues, Known warnings and incidents>>.
| Apply the change again when the window is closed and `cluster-operator` has returned.

| Automatic node scaling
| It does not happen: autoscaling is turned off throughout the intervention.
| If you expect a load peak, size the node groups before the window.
| It only returns at the end of step 8. Check that it has recovered its replicas.

| Calls to the _API Server_ and external orchestrators
| On EKS and on GKE, they are not interrupted. On Azure VMs, they fail during the seconds in which each _control-plane_ replica is replaced; with a single replica, the cut lasts throughout the entire replacement.
| Pause external orchestration during the window so that it does not accumulate failed attempts.
| Relaunch the affected flows from the orchestrator.

| Monitoring and centralized log of _Stratio KEOS_
| They lose samples and events while their own pods are rescheduled from one node to another.
| Nothing
| They recover on their own, but the time-series gap is not filled.

| Sessions open in the Stratio interfaces
| They close when the ingress-controller changes nodes, which occurs at some point in step 7, but you can't determine when.
| Warn users that they will have to log in again.
| Log in again.

| Scheduled backups of _Stratio KEOS_
| A backup that coincides with a node replacement is interrupted.
| Do not overlap the window with its schedule. By default, they are launched at 12:00 a.m., 12:05 a.m., and 12:10 a.m.
| Launch the backup manually upon closing the window.
|===

[#problems]

== If something goes wrong

[#rollback]

=== Rollback

*There is no rollback procedure.* It is the most important limitation of this intervention: the way out is always forward, and what determines the options is the moment at which it is decided.

[cols="2,1,4,2", options="header"]
|===
| Moment of the process | Can it be done? | What is done | How long it takes and whether data is lost

| Before launching the script, during preparation
| Yes
| Nothing: no cluster component has been modified. It is enough not to continue.
| Immediate. No data is lost.

| During steps 2 to 4
| Yes, almost entirely
| The script aborts on its own, and only two things remain to be reverted manually: the autoscaling replicas and, if the execution died midway, the Capsule webhooks.
| Minutes (estimated). No data is lost.

| A chart fails in step 5
| Partially
| Correct the cause and relaunch: the script goes through the charts again and skips those that are already in the target version. Upgraded charts remain as they are, without being downgraded.
| Depends on the remaining charts (estimated). No data is lost.

| Step 6 fails within the critical section
| Only forward
| The script attempts a controlled recovery: it reactivates the `cluster-operator` webhooks, starts its controller, and resumes the reconciliation. *Check that this recovery has completed*: if it also fails, the webhooks must be reactivated, and the controller must be started manually before anything else. Afterward, correct the cause and relaunch.
| Minutes (estimated). No data is lost.

| The Kubernetes jump fails midway, in step 7
| Only forward
| Correct the cause and relaunch. It is safe: each step checks the current state before acting and skips what is already in the target version. *With one critical exception:* if the version change was already written to the descriptor but did not manage to propagate to the infrastructure, a relaunch skips that step because the descriptor already matches the target. Review the `cluster-operator` tracking annotation and its logs before retrying.
| Depends on the remaining nodes (estimated). No data is lost.

| After the _control-plane_ goes up in version
| No
| No downgrade is possible. The cluster stays on the new version, and the remaining node groups must be upgraded.
| Does not apply. No data is lost.
|===

And what is *not* reversible in any case: *the Kubernetes version*. The `cluster-operator` webhook rejects any version lower than the installed one, and the script itself aborts if the target is lower than the current one. There is also no procedure to downgrade the Cluster API providers or the `cluster-operator`.

What the backup that the script makes serves for, then: to reconstruct the Cluster API objects if they are corrupted or deleted, not to return to the previous version. See <<data, Data and consistency>>.

[#known-issues]

=== Known warnings and incidents

[cols="2,2,3,2", options="header"]
|===
| Warning or incident | When it manifests | What to do | Reference

| A _Pod Disruption Budget_ that cannot be met blocks the drain of its node
| In step 7, when replacing the nodes of a group
| Correct the resource's replica count or temporarily withdraw its PDB and relaunch the upgrade. There is no forced eviction: the phase remains waiting until the script aborts after 90 minutes without progress (`--node-convergence-timeout`). On EKS, first check the `coredns` PDB in the `kube-system` namespace.
| xref:operations-manual:operations-manual.adoc#_kubernetes_upgrade[Kubernetes upgrade]

| On GKE, the `KeosCluster` does not reach `ready = true` due to a CAPG reconciliation loop
| In the pre-upgrade check, or while waiting after each minor version jump
| Add the `goog-gke-node-pool-provisioning-model` label to `additionalLabels` of each `GCPManagedMachinePool` and wait for the `KeosCluster` to return to `ready = true` before relaunching. Skipping the pre-upgrade check does not help: the script waits for `ready = true` again at each minor version jump. After the upgrade, declare the label in `additional_labels` of each group of the `KeosCluster`.
| xref:operations-manual:operations-manual.adoc#_reconciliation_loop_in_gke_due_to_automatic_labels[Reconciliation loop on GKE due to automatic labels]

| The version jump is left written in the descriptor but without propagating
| In step 7, if the `cluster-operator` controller was restarted in the middle of the upgrade
| Do not just relaunch the script: since the descriptor already matches the target, the step would be skipped. Review the `cluster-operator` tracking annotation and its logs before retrying.
| <<rollback, Rollback>>

| The `cluster-operator` reconciliation remains suspended after an interrupted execution
| When relaunching after an execution died within the critical section
| The script detects it and resumes it on its own before waiting. If you can't relaunch it, resume it manually; while it remains suspended, it applies no descriptor changes.
| <<outage, Downtime and availability>>

| Modifying the `KeosCluster` with `kubectl apply`
| At any time, also outside the window
| Do not do it: `cluster-operator` detects the annotation that `apply` generates and skips the real reconciliation cycle, so the changes are never processed. Use `patch`.
| xref:operations-manual:upgrade.adoc#_eks_clusters_with_machinepools[EKS clusters with _MachinePools_]

| The scale-down of cluster-autoscaler on managed EKS groups
| After the window, when retiring nodes from a managed group
| Nothing: the cluster-autoscaler image is pinned precisely to avoid the problem. It is a known and accepted risk until the fix is published.
| Issue `kubernetes/autoscaler#9693`

| On Azure, the expired kubeconfig aborts the execution
| In step 2
| Manually update the file's credentials and run the script again. Unlike Amazon Web Services and Google Cloud Platform, it doesn't refresh automatically.
| <<before, Before the window>>

| On Azure, the _control-plane_ network policy is left open during the jump
| Throughout step 7
| Nothing while it lasts: it is necessary for the new _control-plane_ replicas to join the cluster. Check, upon closing the window, that it has been restricted again, because while it is open it admits traffic from the entire VPC and pod network.
| <<checks, Post-upgrade checks>>
|===

TIP: Save the complete output of the script. It reports each step, the expected version change for each component, and the total time, so you know exactly where the upgrade stopped and what state it left it in, instead of reconstructing it afterward.

*What is considered blocking.* That any of the checks marked as such in <<checks, Post-upgrade checks>> fails, and in particular that the _control-plane_ has not converged, that nodes remain in the previous version, or that `cluster-operator` has not recovered its webhooks or completed its reconciliation. You can resolve the rest once the window is closed.

*What to do if a step takes longer than expected.* The script reports each wait and its limit, so the first thing is to check whether it is still progressing: in step 7, if new nodes appear with the target version, it is going well even if it is slow. If it does not progress, look for the cause before interrupting (the most frequent cause is a PDB that cannot be met or a new node that does not reach `Ready`), because interrupting midway through the jump leaves the cluster with nodes in two versions and, if it occurs within the critical section, with `cluster-operator` stopped.
