= Upgrade in GKE

:sectnums:
:sectnumlevels: 1

This procedure upgrades a GKE cluster created with _Stratio Cloud Provisioner_ 0.7.x and Kubernetes 1.32 to version 0.9.9 and Kubernetes 1.35. Read the complete procedure before applying it, and afterward follow the sections in order.

== Before starting

In GKE, the upgrade changes the following:

* The components of the GKE column of the xref:operations-manual:upgrade.adoc#_what_is_upgraded[what is upgraded] table.
* The Kubernetes version of the _control-plane_ and of all the node pools, from minor to minor: 1.33, 1.34, and 1.35. In each step, the script waits for the _control-plane_, the node pools, and their nodes to reach the version before moving on to the next step (see the <<_cambio_de_versión_de_kubernetes_en_gke, Kubernetes version change in GKE>>).
* The `allow-traffic-to-gcp-imds-capg` `GlobalNetworkPolicy`, which specifies which pods can access the VM metadata server. The script adds the `event-exporter-gke` pods to its exceptions.

IMPORTANT: The Kubernetes version change is the point of no return. The script asks for confirmation before applying it (see the xref:operations-manual:upgrade.adoc#_prompts_interactivos[interactive prompts]) and does not allow going back to an earlier version.

In GKE, only the `upgrade-provisioner.py` script of the upgrade image is used.

[#_cambio_de_versión_de_kubernetes_en_gke]

=== Kubernetes version change in GKE

GKE does not upgrade the _control-plane_ by more than one minor at a time, so the script applies one change per minor (1.32 → 1.33 → 1.34 → 1.35) and waits for each one to finish before applying the next.

In each step, the script:

. Chooses the target version. GKE does not accept a generic `X.Y.0` version, so the script uses the highest patch of that minor among the valid versions of the cluster's release channel or, when the cluster has no channel, among the valid _control-plane_ versions.
. Changes the Kubernetes version in the `KeosCluster`.
. Waits for the _control-plane_ to reach `RUNNING` on the new version, according to the GKE API. The limit is `--control-plane-timeout` (90 minutes by default).
. Waits for all node pools to be in `RUNNING` on the new version and for all nodes' `kubeletVersion` to match that version. The limit is `--node-convergence-timeout` (90 minutes by default): it only aborts when no node pool or node advances during that time.
. Waits for the `KeosCluster` to return to `ready: true` and `phase: Provisioned`, with a 30-minute limit.

For this reason, when it finishes, the `k8s_version` of the `KeosCluster` is left with the patch the script chose (for example, `v1.35.8`), not `v1.35.0`.

== Requirements

In addition to the xref:operations-manual:upgrade.adoc#_common_requirements[common requirements], in GKE the following are needed:

* That the service account in `secrets.yml` continues to be valid. The script activates it with `gcloud` on startup and verifies it is the active account.
* That each intermediate minor (1.33 and 1.34) and the target one (1.35) are available in the cluster's release channel. If any is missing, the script stops at that step with the error "No valid GKE version found for minor <minor>". Check it before starting:
+
[source,bash]
----
gcloud container clusters describe <cluster-name> --region <region> --format='value(releaseChannel.channel)'
gcloud container get-server-config --region <region> --format='yaml(channels)'
----
+
*Expected output:* in the `validVersions` list of the cluster's channel, at least one version of 1.33, of 1.34, and of 1.35.

NOTE: On startup, the script rewrites the mounted kubeconfig by regenerating it with `gcloud container clusters get-credentials` using the cluster's Cluster API service account (`capg-manager-bootstrap-credentials`). For this reason, do not mount the file in read-only mode (`:ro`). After the execution, to use that kubeconfig from your machine, `gcloud` and `gke-gcloud-auth-plugin` must be installed and authenticated. To keep the original, copy it before launching the container.

NOTE: The container uses the host machine's network (`--net host`). In a GKE cluster with a private endpoint, launch it from a machine that can access that endpoint (for example, from inside the cluster's VPC). That machine also needs access to the Google APIs, because the script calls `gcloud`.

== Permissions

Before starting, check the permissions of the service accounts that the script uses:

* *Service account of `secrets.yml`*: the same as in the installation. It needs the permissions of xref:attachment$stratio-gcp-permissions.list[`stratio-gcp-permissions.list`] and of xref:attachment$stratio-gke-permissions.list[`stratio-gke-permissions.list`].
* *Cluster API service account of the cluster* (the `capg-manager-bootstrap-credentials` secret of the `capg-system` namespace): the script switches to it at the start and uses it for the rest of the `gcloud` calls.

== Upgrade container

=== Preparation

Go to the working directory from which you will run the container. Usually, it is the same workspace from which the cluster and _keos-installer_ were installed, because it probably already contains several of the necessary files (see the <<_estructura_necesaria, necessary structure>>); if not, use a specific directory.

Create a local directory for the backups:

[source,bash]
----
mkdir -p $PWD/backup
----

[#_estructura_necesaria]

=== Necessary structure

Make sure that the working directory includes the following elements. Only what is mounted from the host is needed; the main script, the Jinja2 templates, and the dependencies are already in the image, and there is no need to have them here:

* `secrets.yml`: the cluster credentials.
* `.kube/config`: the cluster _kubeconfig_ file.
* `backup/`: the directory for the backups (can be empty at the start).

=== Container execution

Download the image:

[source,bash]
----
docker pull <registry>/cloud-provisioner-upgrade:0.9.9
----

Start the container:

[source,bash]
----
docker run \
  --name cloud-provisioner-upgrade-0.9.9 \
  --net host \
  -it \
  -v $PWD/secrets.yml:/upgrade/secrets.yml \
  -v $PWD/.kube/config:/upgrade/.kube/config \
  -v $PWD/backup:/upgrade/backup \
  <registry>/cloud-provisioner-upgrade:0.9.9
----

NOTE: The script does not generate its own timestamped log file; all output is sent to the container console. To keep a complete record of the execution, redirect the output to a file on the mounted volume; for example, add `2>&1 | tee /upgrade/backup/upgrade-$(date +%Y%m%d-%H%M%S).log` to the script command.

Run the `kubectl` commands in this procedure inside the container, using the mounted kubeconfig.

== Prior checks

In addition to the functional checks in xref:operations-manual:upgrade.adoc#_common_requirements[common requirements], in GKE check the following:

* _MachinePools_:
+
[source,bash]
----
kubectl get machinepools -A
----
+
*Expected output:* all with `PHASE = Running`.
+
In GKE, `kubectl get machinedeployments -A` always returns an empty list, because all the worker groups are _MachinePool_.

* Provider pods:
+
[source,bash]
----
kubectl get pods -n capg-system
----
+
*Expected output:* all the pods in `Running` state.

* Provider logs:
+
[source,bash]
----
kubectl logs -n capg-system -l control-plane=capg-controller-manager --tail=-1 --since=1h | grep '^E'
----
+
NOTE: When any error appears, review it before continuing.

NOTE: The pod checks the script performs includes add-ons managed by Google, such as `event-exporter-gke` or `konnectivity-agent`. If any pod is in `CrashLoopBackOff`, `ImagePullBackOff`, `ErrImagePull`, `CreateContainerConfigError`, or in the `Failed` phase, the script stops, even if it is not part of _Stratio KEOS_. Before using `--skip-preflight-checks`, which lets the script continue even when it finds problems in any check, identify whose pod it is: if its image comes from `gke-release`, it is a Google component.

NOTE: GKE installs `event-exporter-gke` when the cluster has `logging_config` enabled. That pod queries the VM metadata server, and the network policy that restricts that access leaves it in `CrashLoopBackOff`. Before the pod check, the script adds `event-exporter-gke` to the exceptions of the `allow-traffic-to-gcp-imds-capg` `GlobalNetworkPolicy` and, when it modifies it, restarts the pod. This way, that failure no longer stops the upgrade.

== Dry-run of `upgrade-provisioner.py`

Inside the container, run the script with the `--dry-run` option. It does not change anything in the cluster:

[source,bash]
----
python3 upgrade-provisioner.py -p <vault-password> --dry-run 2>&1 | tee /upgrade/backup/upgrade-dry-run-$(date +%Y%m%d-%H%M%S).log
----

In the dry-run, the script only asks about the Helm repository: press Enter to keep the current one if there is no repository change, or type the URL of the target repository.

*Expected output:*

* At the start, "[INFO] Mode: DRY-RUN (no changes will be applied)".
* "[INFO] Planned k8s_version bump: <current version> -> v1.35.<patch>", with the patch that the script will use, and "[INFO] Bumping k8s_version: DRY-RUN".
* At the end, "[INFO] Upgrade process finished successfully in ..." and "[INFO] Mode was: DRY-RUN (no changes were applied)".

If any `[WARN]` or `[ERROR]` appears, correct it and repeat the dry-run before the actual upgrade. The exception is the `event-exporter-gke` pod in `CrashLoopBackOff` when "[INFO] Allowing IMDS egress to the event-exporter pods (GlobalNetworkPolicy allow-traffic-to-gcp-imds-capg): DRY-RUN" appears beforehand: the dry-run does not change the policy; the actual execution does.

NOTE: Even though it does not change anything in the cluster, the dry-run also activates the service accounts in `gcloud` and rewrites the mounted kubeconfig.

== Execution of `upgrade-provisioner.py`

Inside the container, launch the upgrade:

[source,bash]
----
python3 upgrade-provisioner.py -p <vault-password> 2>&1 | tee /upgrade/backup/upgrade-$(date +%Y%m%d-%H%M%S).log
----

Respond to the prompts in this order:

. "Press ENTER to continue upgrading the cluster or any other key to abort:": press Enter.
. "The current helm repository is: <url>. Do you want to indicate a new helm repository? Press enter or specify new repository:": press Enter to keep the current repository, when there is no change of repository, or type the URL of the target repository.
. "Proceed with the k8s_version bump <current version> -> v1.35.<patch>? [y/N]:": type `y`. It is the point of no return.

*Expected output on finishing:* "[INFO] Upgrade process finished successfully in ..." and "[INFO] Mode was: REAL — changes were applied".

== Tracking the upgrade

While the script runs, follow the state of the cluster from your machine, in another terminal, with your own kubeconfig and your Google Cloud credentials:

include::partial$upgrade-monitoring.adoc[]

=== `k8s_version` change

During the version change, the script shows one line per step: "Stepping control plane to v1.3X.<patch>", "Waiting for the real GKE control plane to reach 1.3X", "Waiting for every GKE node pool and node to reach 1.3X", and "Waiting for the KeosCluster to settle before the next step".

Follow the _control-plane_ and the node pools separately; the _control-plane_ reaches each version before the nodes:

[source,bash]
----
watch -n30 'gcloud container clusters describe <cluster-name> --region <region> --format="value(status,currentMasterVersion)"; gcloud container node-pools list --cluster <cluster-name> --region <region> --format="table(name,version,status)"'
----

The signal that the nodes have finished is the `kubeletVersion` of each node, not the `version` field of the node pool:

[source,bash]
----
watch -n30 kubectl get nodes -o custom-columns=NAME:.metadata.name,VERSION:.status.nodeInfo.kubeletVersion
----

NOTE: During the upgrade, the list of GKE operations (`gcloud container operations list`) repeatedly shows `UPGRADE_NODES` operations of a few seconds on all the node pools. They are label changes that CAPG tries to apply, not node replacements, and they do not prevent the version change. They disappear when the GKE label is added in the <<_etiqueta_de_gke_en_cada_grupo_de_trabajo, subsequent tasks>>.

== Subsequent checks

In addition to the common xref:operations-manual:upgrade.adoc#_final_verification[final verification], in GKE check the following:

* Version of the `KeosCluster`, of the node pools, and of the nodes:
+
[source,bash]
----
kubectl -n cluster-<cluster-name> get keoscluster <cluster-name> -o jsonpath='{.spec.k8s_version}{"\n"}'
kubectl get machinepools -A
kubectl get nodes -o custom-columns=NAME:.metadata.name,VERSION:.status.nodeInfo.kubeletVersion
----
+
*Expected output:*
+
** `k8s_version` with the patch that the script chose (for example, `v1.35.8`), not `v1.35.0`.
** All the _MachinePools_ with `PHASE = Running`.
** All the nodes with a `kubeletVersion` of 1.35.

* Provider logs:
+
[source,bash]
----
kubectl logs -n capg-system -l control-plane=capg-controller-manager --tail=-1 --since=1h | grep '^E'
----
+
NOTE: When any error appears, review it before continuing.

== Subsequent tasks

After the upgrade, only one task remains: declaring the GKE label in each worker group.

[#_etiqueta_de_gke_en_cada_grupo_de_trabajo]

=== GKE label on each worker group

GKE adds the `goog-gke-node-pool-provisioning-model` label to each node pool. When the worker group does not declare it, CAPG tries to remove it repeatedly. The `KeosCluster` of version 0.7.x does not support the `additional_labels` field, so this step is performed after finishing the upgrade.

. Check the value of the label in each node pool:
+
[source,bash]
----
gcloud container node-pools list --cluster <cluster-name> --region <region> \
  --format='table(name,config.resourceLabels.goog-gke-node-pool-provisioning-model)'
----
+
*Expected output:* the value of each node pool. The node pools that _Stratio Cloud Provisioner_ creates are of type `on-demand`.

. Check the labels of each group. The position of each group in the output, starting from 0, is the one used by the following commands:
+
[source,bash]
----
kubectl -n cluster-<cluster-name> get keoscluster <cluster-name> \
  -o jsonpath='{range .spec.worker_nodes[*]}{.name}{"\t"}{.additional_labels}{"\n"}{end}'
----

. With a single command, add the label, with the value of its node pool (`<value>`), to all groups that don't have it, with one operation per group. For example, for a group without `additional_labels` (position 0) and another that already has labels (position 1):
+
[source,bash]
----
kubectl -n cluster-<cluster-name> patch keoscluster <cluster-name> --type=json -p '[
  {"op":"add","path":"/spec/worker_nodes/0/additional_labels","value":{"goog-gke-node-pool-provisioning-model":"<value>"}},
  {"op":"add","path":"/spec/worker_nodes/1/additional_labels/goog-gke-node-pool-provisioning-model","value":"<value>"}
]'
----
+
WARNING: Do not apply one command per group, one after another, because some group may be left without the label.

. Check the result:
+
[source,bash]
----
kubectl -n cluster-<cluster-name> get keoscluster <cluster-name> \
  -o jsonpath='{range .spec.worker_nodes[*]}{.name}{"\t"}{.additional_labels}{"\n"}{end}'
----
+
*Expected output:* on each group, `"goog-gke-node-pool-provisioning-model"` with the value of its node pool, together with the labels it already has.

NOTE: The node pool already has this label, so the change does not replace nodes.

== Troubleshooting

include::partial$upgrade-recovery.adoc[]

=== Failure during the version change

When the script stops during the version change, the `KeosCluster` is left on the minor it had reached; the script does not return it to the previous version. When it is relaunched with the same command, it continues from that minor:

* When the `KeosCluster` is already on version 1.35, the script only waits for the node pools to finish.
* When it is on an intermediate minor, it applies the steps that are missing.

When the script fails with an error, the automatic recovery restores the `KeosCluster` webhooks and resumes the `HelmRelease` of cluster-operator before aborting. When the process is interrupted (for example, when the container is stopped), the webhooks remain disabled and the `HelmRelease` stays suspended until the script is run again, which restores them.

Before relaunching, check that the _control-plane_ and all node pools are in `RUNNING` and on the same minor as the `k8s_version` of the `KeosCluster`. When any node pool is still on the previous minor, wait for it to finish, because, on being relaunched, the script moves on to the next minor without waiting for the node pools:

[source,bash]
----
gcloud container clusters describe <cluster-name> --region <region> --format="value(status,currentMasterVersion)"
gcloud container node-pools list --cluster <cluster-name> --region <region> --format="table(name,version,status)"
----
